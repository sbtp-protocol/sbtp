## Verdict

**Mergeable into `main`. Not exposable to the Internet as milestone 1b** (no rate limiter yet, prior
I-1, `HOOK(1c)` in `server.rs`). No blocking finding. One medium finding (M-1, a one-line fix) should
be fixed in this branch before the merge; a re-review can be limited to that change and its test.

The properties that matter hold: no client byte reaches a path; nothing reaches a final name before
F1 to F9, P1, C1, C2, C3; a valid stored file can never be moved (quarantine compares the re-read
bytes with the bytes judged damaged, and the judgement is deterministic); every `GET` `200` carries
bytes that passed full validation; every error carries `no-store`; no `block_id` at `warn`.

## Findings

### M-1 (medium): the `PUT` id lock is in practice one global lock

- Where: `crates/sbtp-relay/src/blocks.rs` lines 144 to 149 (`lock_id`), comment at lines 79 to 81
  and 91 to 94.
- `lock_id` picks the stripe with `id[0] % 64`. C1 requires `d` leading zero bits of the `block_id`
  (spec §3.3). At the default `min_pow_difficulty = 16`, `id[0] == 0` for every accepted block (and
  `id[1] == 0`); from `d = 6` there are at most 4 stripes, from `d = 8` exactly one. The lock is taken
  after C1 and held through `settle`, up to two signature verifications, the temporary write and its
  `fsync`, the `link`, the shard `fsync` and the index insert.
- Scenario: any sender, default settings. Every `PUT` of every block serialises on stripe 0, so the
  write stage runs one at a time whatever `put_max_in_flight` says (4 by default, up to 1,024). Three
  `fsync`s per new block bound the relay to roughly 1 / (3 × fsync latency) new blocks per second,
  shared by all clients; the other permits wait on a `std::sync::Mutex` inside blocking threads. A
  flooder therefore needs `put_max_in_flight` times less effort to saturate the `PUT` class than
  ADR 0018 rule 18 sizes for. Mutual exclusion itself is correct (over-serialisation is safe), which is
  why this is not blocking.
- This is the same trap ADR 0009 avoided for the shard layout by using the trailing bytes.
- Fix: stripe on a byte PoW does not touch, e.g. `id[31]` (the shard byte), or fold several trailing
  bytes. Add a unit test: two blocks mined at difficulty 16 with different `id[31]` take different
  stripes (or simply: the stripe of `BlockId` with `[0; 31] ++ [k]` is `k % 64`).

### L-1 (low): `EDQUOT` is answered `500`

- Where: `crates/sbtp-relay/src/store.rs` line 504; `crates/sbtp-relay/src/blocks.rs` line 215.
- Only `ENOSPC` maps to `507`. A file-system quota (XFS project quota, container ephemeral-storage
  limits, user quotas) returns `EDQUOT`, which becomes `StoreError::Io` → `500 Internal` and a
  `store_write_failed op=write` line; the same at the index insert.
- Scenario: a relay deployed on a volume with a project quota smaller than the disk. When the quota is
  reached, every new `PUT` gets `500`: clients are told to retry (a relay fault) instead of trying
  another relay (`507`), and the operator sees write errors instead of `storage_full`.
- Fix: treat `EDQUOT` as `ENOSPC` in both places (reason label `enospc`, so no new label; or a new
  label, which needs one line in ADR 0021 rule 41). ADR 0013 rule 19 should name both errnos.

### L-2 (low): one unreadable orphan stops the start-up

- Where: `crates/sbtp-relay/src/store.rs` lines 776 to 783 (`reconcile`), documented at 735 to 736.
- A read error on an unindexed file (EIO from a bad sector, EACCES after a `chmod 000`) aborts the
  walk, and `run` refuses to start. ADR 0023 rule 2 says an I/O error "gives `500` and changes
  nothing" for a request; for the walk the ADR is silent.
- Scenario (damaged disk, the threat model of ADR 0023): one sector of one orphan file is unreadable;
  the relay cannot start until an operator finds and removes that file, although every other block is
  fine and `GET` would answer `500` for that one id at run time.
- Fix (recommended): on a per-file read error, log `store_write_failed op=read` (throttled), leave the
  file unindexed in place, count it in the quota (already done) and continue; stop only on listing or
  index errors. ADR 0023 rule 15 should say which.

### L-3 (low): the bound of rule 15 is a property of relay-written data, not an enforced bound

- Where: `crates/sbtp-relay/src/store.rs` lines 204 to 206 (`cost`), 585 to 624 (`scan`), 737 to 813.
- What the code does: the walk visits every entry under `blocks/`, `tmp/` and `quarantine/`. Nothing
  counts or caps the entries. `cost(0) == 0`, so a zero-length file at a final name costs no quota;
  entries with a non-canonical name, symbolic links and non-regular files are skipped and cost nothing.
  Each unindexed tiny file is read, fails `parse` (cheap) and is quarantined: a purge listing of
  `quarantine/`, `link`, `unlink` and two directory `fsync`s, before the listener starts.
- For data the relay wrote the bound holds: every block file costs at least 4,096 quota bytes, the
  quota is re-summed at start, `tmp/` holds at most the in-flight writes of one run, `quarantine/` at
  most 64 files. It does not hold against a local writer (or a file-system fault that multiplies
  entries): one million zero-length files under valid names give one million quarantine moves, i.e.
  minutes to hours of start-up with no listener, and quota accounting that ignores them.
- Judgement: acceptable for 1b (local attacker only; the directory modes of L-4 of the prior review now
  protect `data_dir`). The ADR must reword rule 15: "bounded by `max_store_bytes / 4,096` files written
  by the relay" rather than an unconditional bound.
- Cheap hardening: charge at least one quota block per file (`cost(0) = 4,096`, which is also closer to
  the truth: a file takes an inode and a directory entry); optionally stop quarantining after a fixed
  number of moves per walk (log the count) so that a flood degrades into "left unindexed" rather than
  a slow start.

### L-4 (low): no test discriminates the clock of `received_at` on the `PUT` paths

- Where: `crates/sbtp-relay/src/blocks.rs` lines 207 and 346 (`log::unix_ms()`); tests in
  `crates/sbtp-relay/tests/blocks.rs` and `integrity.rs`.
- The code is correct now (see question 1). But the only assertion on `received_at` is the start-up
  orphan path (`blocks.rs` test line 583, file mtime). A regression to the monotonic `log::now_ms()` on
  the `201` path or in `index_orphan` (exactly the bug commit `8f019da` fixes) passes the whole suite.
- Fix: after a `201`, assert `index.contains(&id).received_at.abs_diff(unix_ms()) < 60_000`; same after
  a `PUT` that indexes an orphan (identical-bytes shortcut, rule 8.4 and rule 8.7 with no entry).

### Info

- **I-1. Second "changed" on `PUT` is a silent `500`** (`blocks.rs` line 318). No log line, no counter.
  Only a local writer can produce two changes in a row under the id lock (see question 3); add a
  throttled `store_write_failed op=quarantine` so the operator sees why.
- **I-2. `PUT` after a `GET` quarantined the file: `201` and a new position** (question 6). Consistent
  with rules 9 and 10 (phantom, then the normal path; `insert(Created)` replaces the stale entry,
  ADR 0013 rule 13) and tested (`crash_between_move_and_link`). It contradicts the reasoning of rule 8.7
  ("already accepted, so no new position"): the outcome depends on which request saw the damage first.
  Harmless (a `/query` client may see the id once more, at a later position). ADR 0023 should state it
  in one sentence; no code change.
- **I-3. Directory `fsync` failure after a quarantine move** (question 4). Acceptable as coded; the ADR
  should record it. After a crash both names may exist (hard links to one inode): the walk counts the
  inode twice (over-count, safe) and the next `GET` miss quarantines it again under a new name.
- **I-4. Orphan `received_at` from the file mtime** (`store.rs` lines 614 to 619, 789). An mtime in the
  future (clock wrong when the file was written, a restored backup, a local `touch`) becomes `last`, and
  every later position reuses that `received_at` (ADR 0013 rule 3). In 1c this also delays TTL eviction.
  Cap at `min(mtime, unix_ms())`.
- **I-5. Retention of 7 days runs only at start-up in 1b** (`store.rs` line 394, `HOOK(1c)`). Rule 6
  wants the sweeper too, even with `block_ttl_ms = 0`. The 64-file bound applies at every move, so disk
  use stays bounded. Must land with the 1c sweeper.
- **I-6. Shortcut with a known-invalid signature still answers `200`** (`blocks.rs` lines 284 to 293).
  When the identical stored file is unindexed, the code runs C2/C3, sees them fail, and still answers
  `200` (the "remaining case" of ADR 0023). Nobody can realistically submit bytes identical to a
  damaged file that was never served; answering `422` and quarantining would cost nothing extra. Not
  worth an ADR change now.
- **I-7. Quarantine accounting relies on relay-written lengths.** Files in `quarantine/` without a
  quarantine name are neither counted nor purged; a damaged file whose length was changed by a local
  writer releases its new length at purge, not the length that was charged. `release` saturates, so the
  sum cannot wrap. Local writer only.
- **I-8. Supply chain and MSRV.** No new dependency; `moka` removed from `[workspace.dependencies]` and
  the stale `TODO(1b)` removed (prior I-8 fixed). No `unsafe`; `O_NOFOLLOW | O_NONBLOCK` go through the
  safe `OpenOptionsExt::custom_flags`. `slice::as_chunks` (stable in 1.88) is used in `store.rs` line
  237, but `sbtp-relay` declares `rust-version = "1.90"` (ADR 0013 rule 25, redb), and the workspace
  value 1.85 applies only to the other crates: no MSRV issue. `Option::is_none_or` (1.82) and inline
  `const` array repeat (1.79) are fine for both. Unrelated and pre-existing: cargo warns that the
  workspace dependency `thiserror` is unused.
- **I-9. Query string still ignored on `GET /block`** (prior I-2, unchanged): `?x` varies a CDN key.
- **I-10. Logs and counters.** `block_quarantined` (warn) has no `block` field (tested in
  `tests/logging.rs`); ids appear only as 8-character suffixes at `debug`. `store_write_failed` carries
  `io::Error` text, which holds no path. All new labels are fixed sets. `store_errors_total{op}` can be
  inflated by repeated `GET`s only while a quarantine move keeps failing (fixed cardinality).

## The seven questions

1. **Clocks.** P1 (`blocks.rs` line 175), `received_at` of a `201` (line 207) and of a `PUT`-path orphan
   (line 346), and quarantine names (`store.rs` line 376) all use `log::unix_ms()`: `SystemTime` since
   the Unix epoch, in ms, `0` before 1970. Correct per spec §2.1, ADR 0007 and ADR 0013 rule 2. Start-up
   orphans use the file mtime (ADR 0013 rule 9). Throttles and durations use the monotonic `now_ms`.
   Tests: P1 is discriminated (a block at `now + 30 s` must get `201`; a monotonic or a seconds clock
   rejects it); quarantine names are discriminated (`moved.abs_diff(unix_ms()) < 60_000`); `received_at`
   on the `PUT` paths is not (L-4).
2. **Walk bound.** Not enforced; it holds for relay-written data only. Zero-length and foreign entries
   cost nothing and a flood of tiny files makes start-up slow (L-3). Acceptable; the ADR must reword.
3. **Rule 7, decide again once.** `PUT` (`settle`): first `Changed` → re-read and decide again; second
   `Changed` → `500`, nothing moved, nothing logged (I-1). `GET` (`load`): two passes; a second
   `Changed` → `404`, nothing logged. Under the id lock, a concurrent `GET` can cause one change for a
   `PUT` (the file disappears, then the normal path), and a concurrent `PUT` can cause one for a `GET`
   (valid bytes appear, then served). Two changes in a row need a local writer. Behaviour acceptable;
   the ADR should name the outcome (`500` on `PUT`, `404` on `GET`) and the code should log the `PUT`
   case.
4. **Directory `fsync` failure after a quarantine move.** `quarantine` returns `MovedUnsynced`; the gauge
   counts the file. `PUT`: logged, counted, `500`, the block is not linked over it; the final name is
   now empty, so the retry gets `201` (I-2). `GET`: logged, counted, `404`. Start-up: logged, counted as
   quarantined, the walk continues. Acceptable: not linking after a failed directory `fsync` is the
   conservative choice and matches the spirit of rule 16. The ADR is silent; record it (I-3).
5. **Rule 8.4, orphan with a valid stored file.** Indexed, under the id lock, with `AlreadyHeld` (never
   moves an existing position). The row is built from the submitted block, not from the stored bytes;
   this is correct because the `block_id` covers everything but the 64 signature bytes (spec §3.1) and
   R1 passed on the stored file, so length and parents are equal. The comment of `index_orphan`
   (line 341, "are the stored bytes") is inaccurate for this one call; worth a word.
6. **`PUT` after a `GET` quarantined the file.** `201`, a new position (the stale entry is replaced).
   Consistent with rules 9 and 10, not with the reasoning of rule 8.7. Acceptable; the ADR should say so
   (I-2).
7. **`EDQUOT` vs `ENOSPC`.** Only `ENOSPC` gives `507`; `EDQUOT` gives `500` (L-1). The ADR should
   decide; recommended: both `507`.

### Regression analysis of `fa96c97`

1. **`GET` takes the id lock around the quarantine move** (`blocks.rs` 407 to 419). Taken only after a
   read and a failed full validation, inside the `spawn_blocking` of the read permit, and dropped at the
   end of each pass (also on `continue`). Lock order is id stripe, then `qlock` (inside
   `Store::quarantine`), the same as `PUT`'s `settle` and `quarantine_identical`; nothing takes `qlock`
   and then an id lock (`purge_quarantine` and `reconcile` take no id lock), and no path holds two id
   stripes. No deadlock. Held across: the re-read, the quarantine purge (at most 65 entries), `link`,
   `unlink` and two directory `fsync`s. Only a damaged file reaches it, and a remote client cannot
   damage a stored file, so the extra contention on a `PUT` stripe is not attacker-controllable. A move
   that keeps failing makes each `GET` of that id take the stripe again; bounded by the read permits,
   local-fault only. No finding.
2. **`write_new` at the quota** (`store.rs` 507 to 516) now answers `AlreadyPresent` only if
   `Store::read` (regular file, `O_NOFOLLOW`) returns exactly the submitted bytes; anything else is
   `Full`. Tested for differing bytes and a symbolic link. Under the id lock `settle` has just seen the
   final name empty, so this branch is reached only after a local writer; the extra read is one `open`
   that usually fails with `ENOENT`. A read I/O error there gives `507 quota` instead of `500` (I-11).
3. **C6 path.** Cannot move a valid file: the quarantine compares the re-read bytes with the bytes that
   failed, and the verification is deterministic, so identical bytes of a valid file pass. Cost to a
   sender: one signature verification (already spent before) plus one move per damaged file, after
   which the file is gone. If the index lookup fails, `unindexed` answers `false` and the shortcut gives
   `200` (pre-existing, logged). No finding.
4. **Gauges moved to the callers.** `write_new` publishes on every result except `Created` (and not on
   the early quota return, as before). Every `Created` caller publishes after the index insert, error or
   not: the new block (`blocks.rs` 216), the replacement (206 or inside `index_orphan`, 385). `Unsynced`
   publishes twice (harmless). The only non-test caller of `write_new` is `process`. No missed path.
5. **Orphan `received_at` cap** and **unreadable orphan skip**: see I-4 and L-2 above; both use
   saturating or total operations.
6. **Panics.** No new `unwrap`, `expect`, indexing or unchecked arithmetic outside tests. Patterns
   `let [first, ..] = &self.ids` and `let [.., last] = *id.as_bytes()` are irrefutable on fixed-size
   arrays; `% ID_STRIPES` on a non-zero constant; `STORAGE_FULL.get(..)`; `u32::try_from(..).unwrap_or`.
