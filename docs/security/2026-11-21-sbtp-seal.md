# Security review: `sbtp-seal` (sealed envelope)

- Date: 2026-11-21
- Scope: branch `feat/sbtp-seal`, commit `748c5ce` (`git diff main...feat/sbtp-seal`: the new crate
  `crates/sbtp-seal`, root `Cargo.toml`, `Cargo.lock`).
- Reference: `docs/spec/l2-grammar.md` §5 (§5.1 to §5.5), `docs/spec/sbtp-core-v0.2.md` §3.2 and §3.5,
  ADR 0016, ADR 0039, and the conditions of `docs/security/2026-11-20-hpke-dependency.md`.
- Method: read-only review of the diff and of the `sbtp-core` / `sbtp-l2` / `hpke` code it calls;
  `cargo test -p sbtp-seal`, `cargo clippy -p sbtp-seal --all-targets -- -D warnings`,

## Verdict

**Mergeable.** No blocking, high or medium finding. The code follows §5.1 to §5.3 in order, uses only
the single-shot base-mode HPKE API with the suite fixed by type parameters, and handles hostile
plaintexts without a panic. All conditions of the 2026-11-20 dependency review hold. The low and info
findings below can go to the roadmap; L-1 and L-2 are a few lines each and worth fixing before the
WASM bindings start using the crate.

## Conformance to the spec

- **Suite and parameters (§5.1).** KEM `X25519HkdfSha256`, KDF `HkdfSha256` and AEAD
  `ChaCha20Poly1305` are fixed by type aliases (`keys.rs:10-14`). `info` is `SEALED_HPKE_INFO`, the
  27-byte registry string. `aad` is `PubKey ‖ tag`, 64 bytes (`seal.rs:170`), and both sides use the
  same function. The all-zero shared secret check is the library's (`dhkex/x25519.rs`, reviewed
  2026-11-20). `seal_all_zero_shared_secret` exercises it with the zero point and the point of order 1.
- **Outer block (§5.2).** The payload is built through `sbtp_l2::Payload::encode` against the single
  tag parent, and its length is checked again against the bucket (`seal.rs:158`). The ephemeral signer
  comes from 32 bytes of the caller's RNG, held in a `Zeroizing` seed. It is refused if it equals
  `from` (`seal.rs:91`). `Sealed` is neither `Clone` nor `Copy`, and `SigningKey` wipes itself on drop
  (`ed25519-dalek` 3.0.0 `Drop`, `zeroize` feature on).
- **Buckets (§5.2).** 512, 2,048, 8,192 and 65,535 come from `sbtp_l2::ENC_PAYLOAD_LENS`; plaintexts are
  406, 1,942, 8,086 and 65,429. Tested in `bucket.rs`. The const-array indexing in `payload_len` uses
  literal indices on a fixed-size const array, so no runtime panic is possible.
- **Order of checks (§5.3, ADR 0016 rule 17).** `open` runs, in this order: a redundant bucket check
  on `ct`, before any HPKE work; (4) HPKE Open with each key in the caller's order, first success wins;
  (5) `Reader::skip` of one item from the start, then every remaining byte must be `0x00`; (6)
  `check_profile` on the item, the closed map `{from, msg, sig}` with exact sizes, then
  `from != outer PubKey`; (7) `verify_sealed`, strict V1 to V6, over the message rebuilt with the
  caller's own `recipient_id` and the public key that opened the block; (8)
  `validate_l2_invariants(&[], msg)` (0 parents, which rejects every causal edge and the `sbtp.enc` and
  `sbtp.enc_key` rows), then the allowed kinds. Steps (1) to (3), (9) and (10) are documented as the
  caller's. This matches the spec and the 2026-11-20 clarification that places the `from` check in
  step 6.
- **Padding strictness (§5.3).** Strict. The item length comes from a full structural skip, and a
  single non-zero byte anywhere after it is rejected. The tests flip both the first padding byte and
  the last byte. A plaintext of all zeros decodes as the integer `0` and fails at step 6, as it should.
  An item that fills the bucket with no padding is accepted (`crafted_positive`), which matches "zero
  or more `0x00`".
- **Tags (§5.4, §5.5, core §3.5).** `directory_tag` is `blake3::derive_key(ENC_KEY_DIRECTORY_CONTEXT,
  pubkey)`. `application_tag` refuses `SBTP ` and `SBTP-` prefixes and any prefix of a registry string,
  which includes the empty string and `SBTP`. It then hashes in `derive_key` mode under the
  application's context. This is correct domain separation: no SBTP context can be reached, and `hash`
  mode is never used.

## Silence and oracles

`open` returns a typed `OpenError` for local diagnostics. Nothing in the crate logs, prints or sends
anything. Failures are therefore as silent as the caller makes them. Before step (4) succeeds, every
failure path is the same `NoKeyOpens`: a bad `enc`, a wrong key, an empty key list, a wrong `aad` or a
tampered `ct`. Errors from step (5) onwards can only be produced by someone who sealed to the
recipient's public key. The only timing difference visible from outside is how many keys were tried
before one succeeded, and it is measurable only on the recipient's machine. ChaCha20Poly1305 is not
key-committing, so a sender could craft one ciphertext that opens under two of the recipient's keys.
Keys are tried in a fixed order and the result is never reported, so this gives no oracle. Nothing at
this layer needs constant time beyond what the AEAD tag check already provides.

## Findings

### L-1 (low): plaintext copies are left in freed heap memory on the seal side

- Where: `crates/sbtp-seal/src/seal.rs:115-125`.
- Scenario: `cbor::encode` grows its `Vec` while encoding `{from, msg, sig}`, and `plaintext.resize(
  bucket.plaintext_len(), 0)` almost always reallocates (an item of about 150 bytes grows to 406 or
  more). Each reallocation frees the previous buffer without wiping it. `Zeroizing` wipes only the
  final allocation. An attacker who can later read the process heap (a memory dump, or a heap read in
  the WASM linear memory) may find `msg` in clear. The impact is low: such an attacker usually has
  better targets, and the caller's own `request.msg` is in memory anyway.
- Fix: allocate the final buffer once, `Zeroizing::new(vec![0u8; bucket.plaintext_len()])`, and copy
  the encoded item into it. Pick the bucket from the item length first; the `Zeroizing` encode output
  is wiped on drop. The growth inside `cbor::encode` stays. To remove it, add an
  `encode_into(&mut Vec)` with a reserved capacity to `sbtp-l2`, or accept it as best effort and say so
  in the doc comment as `keys.rs` does.

### L-2 (low): `Debug` of `SealRequest` prints the plaintext, and `Debug` of `Opened` prints the sender

- Where: `seal.rs:22` (`#[derive(Debug)]` on `SealRequest`, which holds `msg`); `open.rs:77-85`
  (`Opened` prints `from`).
- Scenario: a client logs `{request:?}` while debugging a failed seal, and the whole `msg` ends up in
  the log in clear. `from` is the sender's identity, which the envelope exists to hide from everyone
  except the recipient (§5.9 lists what is visible; the sender is not on that list). Printing it in
  `Debug` turns any stray log line into a metadata leak. `SigningKey`'s own `Debug` is safe (it prints
  the verifying key only), and so is `RecipientKey`'s.
- Fix: write `Debug` by hand for `SealRequest` (print `msg.len()` and the bucket only) and drop
  `from` from `Opened`'s `Debug` (or print only that it is present). Keep the accessors as they are.

### L-3 (low): a deterministic RNG would reuse the AEAD key and nonce, and nothing in the API prevents it

- Where: `seal.rs:80` (`rng: &mut impl CryptoRng`), `keys.rs:33`.
- Scenario: a caller passes a seeded `CryptoRng` (rand's `StdRng` and `ChaCha20Rng` implement the
  trait) with a fixed or reused seed. Two seals to the same recipient then use the same HPKE ephemeral
  key: same shared secret, same key and nonce (single-shot, sequence 0). That is ChaCha20Poly1305
  nonce reuse: the XOR of the plaintexts leaks and tags can be forged. The outer Ed25519 key also
  repeats, which links the blocks. The spec requires the OS source (§5.1), and the crate documents it,
  but the type system cannot tell the difference. A related point carries over from the 2026-11-20
  review (F-4): the usual adapter, `UnwrapErr(getrandom::SysRng)`, panics when the OS source fails.
- Fix: none required in this crate for the MVP. When the CLI and WASM bindings are reviewed, check that
  they pass `getrandom`'s system source and nothing else. Optionally, add an `os-rng` feature to
  `sbtp-seal` with `seal_os(request)` / `RecipientKey::generate_os()` built on `getrandom::fill`. These
  would return an error instead of panicking, so callers never pick an RNG themselves.

### I-1 (info): `application_tag` concatenates variable-length inputs with no framing

- Where: `tag.rs:38-58`; the test `application_tag_concatenates` asserts that `["ab","cd"]` and
  `["abcd"]` give the same tag.
- Point: this matches §5.4 ("the inputs of the derivation"), but an application that uses two
  variable-length inputs gets colliding tags for different tuples. For a delivery tag the effect is
  mostly linkability and mixed inboxes, not forgery (step 9 is the application's own check).
- Fix: in the rustdoc, say that inputs SHOULD be of fixed length, or length-prefixed by the
  application's own specification.

### I-2 (info): `RecipientKey::derive` is public in production builds

- Where: `keys.rs:47-53`.
- Point: the doc already says "never with low-entropy input in production". A public deterministic
  constructor still invites deriving encryption keys from passwords or from the identity seed, which
  §5.5 forbids ("generated independently").
- Fix: gate it behind `#[cfg(any(test, feature = "test-keys"))]`, or at least `#[doc(hidden)]`.

### I-3 (info): test coverage gaps

- `prop_open_no_panic` (`tests.rs:665`) draws `ct` lengths from 0 to 599, so almost every case stops
  at `CiphertextLength`. Only length 422 reaches HPKE, and even then the tag check fails. Draw the
  length from the bucket set instead. `prop_plaintext_no_panic` mostly stops at the first CBOR head.
  Neither is a real fuzzer. A `fuzz/` target for steps 5 to 8, with a fixed test key that seals the
  fuzzed plaintext, would cover the hostile-plaintext path properly (scope of `fuzz/`).
- On the open side, nothing checks that a `msg` of kind `sbtp.enc` is rejected (only the seal side
  checks it, `seal_msg_invalid`). Add it to `open_msg_invalid`.
- `open_item_encoding` matches `ItemEncoding(_)` without the inner error. It could assert
  `MapKeysUnsorted` for the second case, so that it cannot pass for the wrong reason.
- Otherwise every `OpenError` variant has a test that discriminates it from its neighbours.
  `open_signature` separately covers a wrong `recipient_x25519`, a wrong outer `PubKey`, a wrong
  `recipient_id` and a flipped signature. `SealError::Signing` and `SealError::Encoding` are
  documented as unreachable, and they are.

### I-4 (info): the diagnostic detail of `OpenError` must not cross the API boundary

- Where: `error.rs:44-74`.
- Point: the variants and their `Display` text tell which check failed. That is fine locally, but a
  binding that turns them into a JS exception message, or a client that sends them to telemetry or
  answers the sender, would break the §5.3 "tells no one" rule.
- Fix: when the WASM bindings are reviewed, check that they collapse every `OpenError` into a single
  "not for us" result. No change needed here.

### I-5 (info): `poly1305` state is still not wiped (carry-over F-3)

- The `zeroize` feature of `poly1305` is still not unified; `sbtp-seal` does not add it. This was
  optional in the earlier review and remains so.
