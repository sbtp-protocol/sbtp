## Verdict

**Mergeable.** No blocking or medium finding. The pool keeps the number of threads that touch the
index at `index_max_readers + 1` whatever clients do; the reader queue is bounded and refuses at once;
expired and cancelled jobs never run; the writer bound cannot be reached in service because every write
caller owns a `PUT` permit. The token bucket runs before any parameter check, body read or index work,
uses exact integer arithmetic with no overflow path, and its table is bounded. Finding L-2 of the 1c-a
review is closed. The low findings below can be fixed in 1c; none needs a re-review.

## Low

### L-1. A writer panic during shutdown is reported as a clean shutdown

`crates/sbtp-relay/src/pool.rs:290-302` (`IndexPool::stop`), with `Supervised` at `pool.rs:397-408`.

`stop` sets `stopping` before it tells the threads to stop. From then on `Supervised` no longer exits the
process, and a writer that panics while draining the queued writes or inside the final `index.flush()`
returns `Err(_)` from `join`, which is mapped to `Ok(())`. The comment says this cannot happen ("A
panicked writer exits the process (rule 37) before this is reached"), but it is only true before
`stopping` is set.

Scenario: SIGTERM, then a redb panic in the final flush (for example on an I/O fault that redb does not
turn into an error). `run` reports `durable = Ok(())`, then tries `close()` on a database whose internal
locks may be poisoned, and the process can exit 0 with no `fatal` line. The operator sees a clean stop;
the non-durable tail of the index (at most `DURABLE_COMMIT_INTERVAL`) is lost silently. The next start's
walk repairs the orphans and renews the epoch (ADR 0023 rule 15, ADR 0024), so no data is lost on disk
and no cursor is wrong: the impact is a misleading exit status and log, not integrity.

Fix: map `Some(Err(_))` to an error (for example `StartError::Shutdown("the index writer panicked")`, or
an `IndexError` variant) and emit a `fatal` line, so the exit status is non-zero. Same for a panicked
reader `join` (currently `let _ = t.join()`), at least logged. Correct the comment.

### L-2. Required tests of ADR 0020 rule 25 and of rule 37 supervision are missing

`crates/sbtp-relay/src/server.rs:464-497` (`admit`), `crates/sbtp-relay/src/pool.rs:397-408`.

ADR 0020 rule 25 requires, in milestone 1c: (a) a client at its in-flight bound that keeps sending
exhausts its bucket and its `429` then carries the `Retry-After` of ADR 0018 rule 29; (b) a request
refused for an empty bucket leaves the in-flight count unchanged. The code is right on both (the bucket
is taken before `try_acquire`, and the bucket refusal returns before it), but nothing pins it: the
`limiter.rs` unit tests do not go through `admit`, and `tests/query.rs::query_bucket_gives_429_with_retry_after`
uses a direct connection, where there is no in-flight count. Part (c) (preflight and unknown path cost
one `block` token) cannot be tested until the `block` bucket exists; it must not be forgotten in 1c.
Rule 24 (the in-flight count of an overflow request is taken on `ClientKey::OVERFLOW`) is not tested
either. Rule 37 (a pool thread that ends makes the process exit non-zero) has no test.

A regression that swaps steps (c) and (d), or that counts a bucket-refused request in flight, would
let a client hold its in-flight slots with refused requests or lose the rule 29 `Retry-After`; nothing
would fail.

Fix: unit tests on `admit` with a `Limiter` of burst 1 and `Admission::Proxied(Counts::new(1))`:
(a) hold the slot, send again until the refusal is `EmptyBucket` with the rule 29 value; (b) after an
`EmptyBucket` refusal, `Counts` still has exactly the held slot; a table of `max_clients` active keys
sends an unknown key's in-flight count to `OVERFLOW`. For rule 37, the child-process pattern already used
in `index.rs` tests (a job that panics, then check exit status 70).

### L-3. `PUT` of a held block gets `503` when the reader queue is full, and is shed with `/query`

`crates/sbtp-relay/src/blocks.rs:367-381` (`unindexed`), called at `blocks.rs:203, 241-242, 298, 316`.

The repair lookup of a repeated `PUT` is now a reader job, in the same queue as `/query` pages. A queue
refusal or expiry answers `503 Unavailable` with `shed_retry_after_s`, after the body was read and, on
the paths of rule 8.4 and 8.7, after the signature was verified or a damaged file rewritten. This is
literally what ADR 0018 rules 13 and 30 say ("a request gets `503`"), and the test
`repeated_put_goes_through_the_reader_pool` pins it. Two points are less consistent:

- ADR 0018 rule 32 orders shedding: `/query` first, `PUT` second. Since both share one reader queue, a
  `/query` flood that fills it also sheds every repeated `PUT` of a held block at the same moment.
  Fresh `PUT`s are not affected (they never do a lookup). The reverse direction is bounded: at most
  `put_max_in_flight` reader jobs come from `PUT`.
- A lookup that *fails* answers `Ok(false)` (treated as indexed, `200`, repaired later), while a lookup
  that is *refused* answers `503`. The client then re-sends up to 65,909 bytes and the relay re-parses
  (and possibly re-verifies) during the very saturation that caused the refusal.

Not exploitable beyond a `503` the client retries (ADR 0008 idempotence); hence low. Recommended: ask
the specification editor to decide. The cheaper option is to treat a refused lookup like a failed one (`200`,
the block is held; the orphan, if any, is repaired by a later `PUT` or at start-up), counted as
`index_queue`. Otherwise state in ADR 0018 rule 32 that repeated `PUT`s share the `/query` shed point.

### L-4. The limiter sweep is `O(rate_limit_max_clients)` under one global mutex on a runtime worker

`crates/sbtp-relay/src/limiter.rs:155-180` (`take_at`), setting range at `config.rs:120`.

When the table is full and an unknown key arrives, `retain` refills and tests every entry while holding
the single `std::sync::Mutex` of the limiter, on a tokio worker thread. `SWEEP_MS` caps this at one pass
per second, which is correct, but the pass itself is unbounded by anything but the setting. At the
default (4,096 keys) it is microseconds; at the profile values (32,768 and 262,144) about 0.1 to a few
milliseconds; at the accepted maximum (16,777,216) it is in the order of 100 ms or more per second,
during which every worker that admits a `/query` blocks on the mutex. With `block` and `put` buckets
in 1c, every request will. Triggering it needs a full table of active keys: an attacker with a large
IPv6 allocation (a /40 holds 2^24 /64 keys) and an operator who raised the setting to its maximum.

Fix (any one): bound the work of one pass (walk at most N entries per call from a rotating position,
or shard the table into M independently locked parts with M sweeps of `max/M`); or lower the upper
bound of `rate_limit_max_clients` to a value whose sweep is measured under 1 ms on the gate VM; or at
least document the cost next to the setting. Also worth noting for ADR 0018 rule 35: a full table of
16.7 M entries is about 1.3 GB with `HashMap` overhead, which is inside the "100 bytes per entry"
estimate only loosely.

## Info

### I-1. A panic inside an index job now ends the process (rule 37), instead of a `500`

`crates/sbtp-relay/src/pool.rs:77-84, 410-424`. Before this branch a panic in the `/query` closure was a
`JoinError` mapped to `500`. Now the closure runs on a supervised reader thread with no `catch_unwind`,
so any panic in it exits the process with status 70. This matches ADR 0018 rule 37 and is the safe
choice (a panic inside redb poisons its internal locks, review 2026-11-18 F-7), but it turns any
reachable panic in a job into a remote restart, and `overflow-checks = true` applies to
`sbtp-relay`. I checked every closure: the `/query` page (`expiry_floor` uses `checked_sub` and
`saturating_add`; `RedbIndex::query` clamps `limit`, its ranges cannot be inverted, cursor fields only
feed `max` and range bounds; `Position::next` saturates), `contains`, `insert` (`ROW_HEAD + 32 * parents`
with at most 8 parents) and the reconciliation walk. No panic path reachable from network input was
found. Recommended: state the exception in the comment of `[profile.release]` in `Cargo.toml` ("one
panicking request must not stop the relay", except inside an index job) and in the module doc, and keep
new index-job code free of indexing and unchecked arithmetic.

### I-2. A read job that starts just before its deadline still answers `503` at the deadline

`crates/sbtp-relay/src/pool.rs:336-339, 359-360`. The caller waits `timeout_at(deadline)` for the reply,
so the deadline covers queue wait *and* run time. A job taken at `deadline - ε` runs to its end (rule 13,
correct), but its requester has already answered `503` and counted `index_queue`. Rule 13 gives `503`
"for a job still queued at its deadline". The work is bounded (one page, rule 14) and the thread count
is unaffected; only the response and the counter differ from the rule. Optionally: let the job signal
when it starts and, once started, wait for the result up to `request_timeout_ms` (rule 25 still bounds
the request).

### I-3. The reconciliation walk does its lookups on the writer thread, not through the reader queue

`crates/sbtp-relay/src/lib.rs:145-156`. Rule 9 says every index read runs on a reader thread, and rule
13 says the reconciliation uses "the same queue". The walk is one writer job, so its `contains` calls run
on the writer. The invariant that matters (rule 10: only these `index_max_readers + 1` threads touch the
index) holds, and the walk runs before the relay listens. A wording issue for the specification editor, not a
risk.

### I-4. A CORS preflight to `/sbtp/v1/query` takes a `query` token

`crates/sbtp-relay/src/server.rs:151-159`. ADR 0020 rule 23 says both "path `/sbtp/v1/query`: `query`"
and "a CORS preflight ... takes one `block` token". The code follows the first sentence. A browser sends
no preflight for a plain `GET /query`, so the impact is small; the specification editor should settle which
sentence wins.

### I-5. Overflow attribution is not visible to handlers

`crates/sbtp-relay/src/server.rs:449, 470-471`. `RequestClient` is inserted with the real key before the
limiter runs; only the local `key` used for the in-flight count becomes `ClientKey::OVERFLOW`. Correct
for rule 24 today. When the `put` bucket arrives (1c), decide whether the per-client `PUT` bound
(`blocks.rs`, `put_per_client`) of an overflow request counts on the overflow key too; otherwise a
flood of unknown keys bypasses nothing (each key still has its own bound of 1 table entry), but the
behaviour should be stated.

### I-6. Filling the table pushes new clients onto one shared allowance (accepted residual)

ADR 0018 rule 21 by design. Cost for the attacker, with the defaults (4,096 keys, query burst 20, 300
per minute): a key stays non-full for 4 s after spending its burst, so keeping the table full takes
about 4,096 × 5 = 20,000 served queries per second, which saturates the reader queue on its own. This
is the "distributed senders" residual of ADR 0018, not a cheaper attack. No action.

### I-7. Verified and holds

- `limiter.rs`: refill `saturating_mul` / `saturating_add` and `min(cap)`; `take` subtracts only when
  `level >= UNIT`; `Retry-After` is in `1..=60` for the accepted range (`per_min >= 1`, rule 29 rounding
  up); the clock is monotonic (`Instant`) and `at = max(at, now)`. `HashMap` uses std's randomly keyed
  SipHash: no hash flooding. `ClientKey::OVERFLOW` has prefix 255 and cannot equal a real key. Table size
  bounded by `rate_limit_max_clients`; unknown keys never insert past it.
- Admission order (ADR 0018 rule 28, ADR 0020 rule 22): exemption first; class from method and path
  only, compared as the exact raw path, the same string the router matches (no bypass by trailing
  slash, `HEAD`, absolute-form target); token before the in-flight count; bucket refusal not counted in
  flight; in-flight refusal keeps the token; both before parameter checks (`limit=0` still gets `429`,
  tested) and before the body.
- `pool.rs` queue accounting: `jobs.len() < idle + max_queue` admits exactly the idle threads plus
  `index_max_queue` waiters; no lost wakeup (the queue is checked under the lock before waiting);
  queued jobs are drained after a stop, abandoned ones dropped; pushes after a stop refused.
- Cancellation: a dropped `/query` future closes the `oneshot`, and the reader drops the job unrun
  (tested). Expired jobs never run (tested). At most `index_max_readers` reads run at once (tested).
- Writer bound: the `PUT` permit and the per-client slot move into the blocking closure
  (`blocks.rs:583-589`), so at most `put_max_in_flight` write callers exist and the writer queue of
  `put_max_in_flight + 1` is never full in service.
- Shutdown and durability: the runtime is dropped at the end of `serve`, which waits for running
  blocking tasks (the `PUT` pipelines) before `pool.shutdown()`; the writer drains, then `flush()`s,
  then `close()` runs. Periodic `flush_pending` is not starved by a busy writer because `insert`
  itself commits durably once `DURABLE_COMMIT_INTERVAL` has passed. The epoch refresh after each
  writer job covers the walk's `renew_epoch`.
- `page_body`: exact capacity (`67n - 1` for `n` identifiers, 40 for the cursor), only hexadecimal and
  booleans, so no escaping is needed; output equals the previous `serde_json` form (tested).
- Previous review: L-2 (index reads on the shared blocking pool) is closed; L-1 (expiry floor read after
  the wait) still holds, the clock is read inside the job.
- No new dependency, no `unsafe`, no address logged by the limiter.

### I-8. Minor

- `tests/query.rs::repeated_put_goes_through_the_reader_pool` relies on `sleep(100 ms)` for the slow
  `/query` to occupy the reader; on a loaded CI host it can flake. Wait on an observable condition
  instead (the slow backend can signal when its query starts).
- The `index_migration` example and `index.rs` tests call the index directly while a pool exists. Fine
  for tools and tests; not a path of the relay.
- Supervision covers threads that end, not a reader stuck forever in the backend; the deadline of
  rule 13 then refuses requests (`503`) without restarting. Acceptable for milestone 1.
