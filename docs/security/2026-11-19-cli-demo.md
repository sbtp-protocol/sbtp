## Verdict

**Mergeable after one fix (M-1).** No blocking finding. M-1 is a one-line correctness fix with a test;
it fails closed, so it is not a security hole, but it breaks interoperability for spec-valid blocks.
A re-review can be limited to that change and its test.

What holds: the secret key never reaches argv, environment, stdout, stderr or error text; the key file
is created with `O_CREAT|O_EXCL` and mode `0600` and read with `O_NOFOLLOW`, `fstat` on the open
descriptor (no TOCTOU), a group/other mode check and a 256-byte cap; `ed25519_dalek::SigningKey`
zeroizes on drop. Every relay byte is bounded (16 KiB for JSON, `MAX_BLOCK_LEN` for blocks), every
request has a 30 s end-to-end deadline, redirects are not followed, environment proxies are disabled.
`get` writes and prints nothing before `validate_requested` (F1-F9, R1, C1, C2, C3), in the order of
§3.4. Relay text reaching the terminal goes through `untrusted()` (C0/C1 control characters escaped,
length capped). No `unwrap`, indexing or `unsafe` on network input.

## Findings

### M-1 (medium): `get` refuses every block of exactly `MAX_BLOCK_LEN` bytes

`examples/cli-demo/src/relay.rs:162-163`:

```rust
let limit = MAX_BLOCK_LEN as u64;
read_limited(&mut response, limit).map_err(|e| match e { ureq::Error::BodyExceedsLimit(_) => ...
```

`ureq` 3.5.1's `LimitReader::read` (`src/body/limit.rs:23`) returns `BodyExceedsLimit` as soon as it is
called with `left == 0`, without asking the inner reader whether the body has ended. `read_to_end` always
makes one more `read` call after the last byte to observe EOF. A body of exactly `limit` bytes therefore
fails.

- Scenario (reproduced): a block with 8 parents and a 65,535-byte payload (65,909 bytes, accepted by
  `inspect` and by any conformant relay, whose `PUT` limit is 65,909 bytes per §4) is served with
  `200 OK`. `cli-demo get` prints `error: the relay sent more than 65909 bytes ... (TooLong)` and exits 4,
  blaming the relay for a spec-valid block.
- Effect: fail-closed, so no security impact, but a correctness and interoperability bug: a block the CLI
  can mine and publish cannot be fetched back, and the error accuses an honest relay.
- Fix: read with `limit = MAX_BLOCK_LEN as u64 + 1` and map `BodyExceedsLimit` to `TooLong` (same pattern
  as `read_bounded` in `commands.rs`); a body of `MAX_BLOCK_LEN + 1` bytes or more is still refused
  before parsing. Add an end-to-end test with `fake_relay` serving a maximum-length block (must succeed)
  and one serving `MAX_BLOCK_LEN + 1` bytes (must exit 4 with `TooLong`, nothing written). The same
  off-by-one affects `MAX_JSON_LEN` (a 16,384-byte `/info` fails); harmless, but fix it the same way for
  consistency.

### L-1 (low): `untrusted()` lets bidi and invisible characters through

`examples/cli-demo/src/fail.rs:72` escapes `char::is_control()`, that is Unicode category Cc (C0, DEL,
C1). This blocks every terminal escape sequence (ESC, CSI U+009B, OSC, BEL), which is the property that
matters. It does not escape category Cf: bidi overrides and isolates (U+202A-U+202E, U+2066-U+2069),
zero-width characters (U+200B-U+200F), U+FEFF.

- Scenario: an author publishes a block whose UTF-8 payload contains U+202E; `get` / `inspect` show
  `text: "..."` with the order of the following characters reversed on a bidi-capable terminal, or a
  relay's `message` hides text with zero-width characters. Visual spoofing of a preview only: the
  payload bytes, `block_id`, pubkey and validity line are not affected, and no terminal state changes.
- Fix: also escape `c.is_whitespace() && c != ' '` and the Cf ranges above (or any char outside a
  printable allow-list), with a unit test using U+202E. Worth doing before the PWA reuses the idea.

### L-2 (low): freed copies of the seed are not wiped

`examples/cli-demo/src/keyfile.rs:127`: `Zeroizing::new(Vec::new())` then `read_to_end`. The `Vec` starts
with capacity 0; `read_to_end` grows it (and uses a 32-byte stack probe), so the hex seed is copied into
heap buffers that are freed on reallocation without being wiped; only the final buffer is zeroized.
Similarly `hex::decode::<32>` returns the seed by value through an `Option` before `Zeroizing::new`
(stack copies). This weakens the "buffers that held it are wiped" claim of the module doc.

- Scenario: needs a memory disclosure in a process that lives a few milliseconds and runs as the key
  owner, who can read the file anyway. Low.
- Fix: `Zeroizing::new(Vec::with_capacity(MAX_KEY_FILE_LEN as usize + 1))` so no reallocation happens;
  reword the module doc to "the buffers the CLI owns are wiped" (stack copies cannot be guaranteed).

### L-3 (low): output files of `get` and `--force`

`examples/cli-demo/src/commands.rs:248-255, 322-339`.

- `get --out A --payload-out B`: `A` is written, then `B` fails (exists, permission): exit 1 with `A`
  left in place. Validation happened first, so the content of `A` is correct; only the "nothing written
  on failure" expectation is broken. Fix: check that both paths can be created before writing, or
  document it.
- `--force` opens with `create(true).truncate(true)`: follows a symlink at the final component and
  truncates in place. In a shared directory (`/tmp`) another user can pre-plant `out -> ~/.bashrc` and
  have it overwritten with block bytes. The paths are the user's own choice, `--force` is explicit, and
  without `--force` `create_new` (O_EXCL) refuses symlinks. Fix if cheap: `O_NOFOLLOW` on the `--force`
  path too, or write to a temporary file in the same directory and `rename` (also makes it atomic).
- `write_output` and `keyfile::write_new` leave a partial file if `write_all` fails midway (disk full).
  For the key file this means a corrupt 0600 file and a refused retry; no leak.

### L-4 (low): tests do not cover several claimed security properties

The existing tests discriminate what they claim: the R1 test serves a valid block for another id and
checks `BlockIdMismatch`, empty stdout and no file; the C3 test flips the last byte (inside the
signature, which is the last field, so R1 still passes) and checks `InvalidSignature`; the
`InsufficientPow` test picks a timestamp whose nonce-0 block provably fails 8 bits; keygen checks mode
0600 and that the secret hex appears in neither stream. Missing, each cheap with `fake_relay`:

- a maximum-length block (M-1) and a `MAX_BLOCK_LEN + 1` body;
- a payload and an error `message` containing ESC/CSI sequences, asserting no raw `\x1b` on stdout or
  stderr (only a unit test of `error_body` exists);
- a `3xx` with `Location`, asserting it is not followed (exit 3);
- `mine --relay` against an `/info` announcing 25, asserting refusal without hashing;
- a key file that is a symlink to a 0600 file (refused by `O_NOFOLLOW`) and a 0640 file (group bit).

## Informational

- **I-1. Plain HTTP only.** §4 requires a public relay to be reachable over HTTPS; this build has no
  TLS and says so (help, `https://` refused with exit 2). On a hostile network a MITM cannot forge a
  block for `get` (R1 and the signature bind it), but can fake a `PUT` success (`201`), fake errors
  (escaped), or inflate `/info` difficulty (capped at 24 by `MAX_RELAY_DIFFICULTY`: seconds of CPU).
  Acceptable for a demonstrator used against loopback or an SSH tunnel. Revisit when TLS is added
  (`ureq` `rustls` feature pulls `ring`/`rustls`: a separate supply-chain review).
- **I-2. Unbounded mining above difficulty 26** (`commands.rs:97-98`): `--difficulty 256` loops through
  the nonce space. Explicit user choice, documented; a warning above, say, 32 would be friendlier.
- **I-3. Exit code 3 for a local policy refusal** (`commands.rs:144`): a relay asking for more than 24 is
  reported as "the relay refused the request". Cosmetic; exit 1 would match the help text better.
- **I-4. Key file opened without `O_NONBLOCK`**: a FIFO at the key path blocks `open` before the
  `is_file` check. Requires write access to the directory; adding `O_NONBLOCK` (harmless for a regular
  file) closes it.
- **I-5. Randomness** from `/dev/urandom` with `read_exact`: correct on Linux and macOS. `getrandom`
  would also cover a chroot without `/dev`, but would add a crate; not worth it here.
- **I-6. Hex decoding of the seed is not constant time** (`hex.rs:28-35`): local file, the attacker
  would need a timing oracle on the user's own machine. Negligible.
- **I-7. Unescaped argv in usage errors** (`args.rs:44`, `positionals`): the user's own input echoed to
  the user's own terminal. Harmless; mention only for consistency with `untrusted()` elsewhere.
- **I-8. MSRV split**: the dev-dependency on `sbtp-relay` makes `cargo test -p cli-demo` need Rust 1.90
  (redb 4.x), as documented in `examples/cli-demo/Cargo.toml`; building the CLI stays at 1.85.
  `rust-toolchain.toml` covers CI.

### New findings

No blocking or medium finding. The new code introduces no path that writes outside the named
destination or its directory, follows a symlink, or overwrites an existing file without `--force`.

#### L-5 (low): the `link` rollback is never exercised by a test

`output.rs:64-70`. The both-or-neither property without `--force` is held by two layers: the
pre-check `check_destination` (line 50-52) and the removal of already-linked destinations when a later
`link` fails. Every test that exercises the property is stopped by the pre-check, so the rollback
(the only layer that covers a destination created between the pre-check and the `link`) could be
deleted without any test failing (confirmed by mutation). Its logic is three lines and reads correct.

- Scenario: a later refactoring drops or breaks the rollback; nothing turns red, and a race (another
  process creating the second destination during the run) again leaves the first file behind. No
  security impact, it only weakens a correctness guarantee.
- Fix: a unit test that calls the placement step directly with the pre-check bypassed (for example
  split `write_all` into `check` + `place`, and test `place` with the second destination already
  present), asserting the first destination is removed and no temporary file remains.

#### I-9 (info): invisible characters outside Cf still pass `untrusted()`

Characters that render blank or stack but are letters or marks are not escaped: Hangul fillers
(U+115F, U+1160, U+3164, U+FFA0, category Lo), variation selectors (U+FE00-FE0F, U+E0100-E01EF,
Mn), U+034F combining grapheme joiner, unbounded combining-mark stacks, U+2800 braille blank, private
use (Co) and unassigned (Cn) code points. Effect: a payload preview can hide or pad text, as with
L-1, but cannot reorder it or reach the terminal's state. Not worth a table in the CLI; record it
for the PWA, where a printable allow-list (or rendering with explicit markers) is the right design.

#### I-10 (info): two outputs that name the same file under different spellings

`output.rs:42-48` compares the two `Path` values by component, so `--out a --payload-out ./a`
(or `x/../a`, or through a symlinked directory) is not detected. Without `--force`: the second
`link` fails with `EEXIST`, the first is rolled back, and the message says "./a already exists"
(fail-closed, misleading). With `--force`: both renames succeed, `a` holds the payload, and the CLI
reports "Block written to a" and "Payload written to ./a". User error only, no attacker involved.
Fix if cheap: compare `(dev, ino)` of the parent directories plus the file name, or document it.

#### I-11 (info): `link(2)` is unavailable on some filesystems

FAT/exFAT volumes, and some SMB mounts, do not support hard links: `get --out` or `mine --out`
without `--force` then always fails with "cannot write ...: Operation not supported" (fail-closed);
`--force` (rename) works. A usability regression on USB sticks, not a security issue. Either document
it, or on `ENOTSUP`/`EPERM` from `link` fall back to `rename` after re-checking that the destination
does not exist (accepting the small race on such filesystems).

#### I-12 (info): smaller side effects of the temporary-file placement

- `--force` replaces the directory entry, so the destination's previous mode, owner and hard links
  are not carried over (new file at `0666 & ~umask`). Correct for "replace"; mention in the help if
  users rely on a restrictive mode on an output file. Block and payload bytes are public data.
- With `--force` and two outputs, a destination that did not exist before and was already renamed
  into place is not removed when the second rename fails (documented in the module; only
  pre-existing files truly cannot be restored).
- A `SIGINT`/`SIGKILL` between staging and placement leaves a hidden `.<name>.<pid>.<n>.tmp`
  (`Drop` does not run on a signal). Harmless; at most `MAX_BLOCK_LEN` bytes each.
- A destination file name within about 20 bytes of `NAME_MAX` makes the temporary name too long:
  fail-closed with a `File name too long` error naming the destination.
- In a world-writable directory without the sticky bit, another user could swap the staged
  temporary file before `link`/`rename`; such a user can replace the destination afterwards anyway,
  and `/tmp` is sticky on macOS and Linux. Not a finding.
