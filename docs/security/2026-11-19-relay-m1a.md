# Security review: relay milestone 1a, server foundation (2026-11-19)

Scope: `git diff main..6ff5f64` (branch `feat/relay-m1a-foundation`): `crates/sbtp-relay/src/config.rs`,
`server.rs`, `api.rs`, `error.rs`, `lib.rs`, `main.rs`, the three test files, the workspace manifests and
`Cargo.lock`. Also the shutdown and close path merged with the redb 4.6 bump (`ec3e850`), which this commit
moves from `main.rs` to `lib.rs::run` and which had no dedicated review. Independent review from the diff,
ADR 0018 (accepted), ADRs 0012, 0007, 0003 rule 16, the crate sources in the local registry and crates.io,
and scratch clients run against the built binary on loopback. All file and line references are at commit
`6ff5f64`.

**Verdict: OK to merge.** No critical or high finding. The relay listens on `127.0.0.1` by default, serves
one static route, and every timer, limit and refusal named in ADR 0018 rules 6, 7, 22 to 27, 31, 33 and 37
behaved as specified under attack. Two medium findings (F-1, F-2) are not exploitable through the documented
deployment (loopback behind Caddy) with the 1a routes, but MUST be closed, and re-reviewed, before the relay
is exposed and before milestone 1c is declared complete. Neither blocks this merge.

## Findings

### F-1 (medium): a silent connection holds a permit for `idle_timeout_ms`

`crates/sbtp-relay/src/server.rs:232-239`: a new connection starts in phase `IDLE` with the deadline
`idle_timeout_ms`. The header deadline starts only at the first byte (`bytes_read`, line 252).

Scenario: the relay is reachable directly (`listen = 0.0.0.0:…`, or a proxy that opens upstream connections
before it has a request head). The attacker opens `max_connections` TCP connections and sends nothing, then
re-opens each one when it is closed. Cost with the defaults: 32 sockets, about one new connection per second,
no payload. Effect: every permit is held, new connections wait in the listen queue, the relay serves nobody.
Measured: 8 sockets against a cap of 4, zero legitimate requests served.

This conforms to the letter of ADR 0018 rule 26, and rule 31 accepts that the cap is a hard stop. Behind
Caddy on loopback it is not reachable from the Internet, because Caddy dials the upstream only once it holds
a complete request head. It is therefore not blocking for 1a.

Fix (small): give a connection that has not yet received a byte the deadline `header_timeout_ms` (5 s)
instead of `idle_timeout_ms`, and keep `idle_timeout_ms` for the wait **between** requests. This divides the
hold time by 6; it does not remove the attack (see F-2). State in the deployment documentation that the
relay MUST NOT be exposed without a reverse proxy that buffers request heads.

### F-2 (medium): nothing bounds one client's share of `max_connections`

`server.rs:98-139`: one global semaphore. A connection that sends one valid request every
`idle_timeout_ms - 1` stays open forever; there is no cap on requests per connection, on connection age, or
on connections per peer address.

Scenario: 32 connections, one `GET /info` every 29 s each (about 1 request per second in total, well inside
the default `rate_block_per_min` of 3,000). Every permit is held without breaking a single rule. Once 1b
adds `PUT`, the same result is available **through Caddy**: Caddy streams request bodies, so 32 slow bodies
hold 32 upstream connections for `body_timeout_ms` (10 s) each, about 3 requests per second for a permanent
lock-out, unless the per-client bound refuses them before the body is read.

Fix, for 1c and before exposure: a bound on connections (or requests in flight) per client key, enforced
at accept or at admission step 3 of rule 28, with the proxy case handled through `trusted_proxies`; and a
maximum connection age or request count for keep-alive. This needs an ADR 0018 amendment (no rule covers
it today). Until then the proxy's own limits are the only protection: say so in `deploy/`.

### F-3 (low): two paths get the idle deadline where a shorter one is intended

- `server.rs:269-275`: `Done` is dropped when hyper has taken the last body frame into its write buffer,
  not when the bytes are flushed. A client that stops reading then sits in `IDLE`, so the unflushed tail of a
  response is bounded by `idle_timeout_ms` instead of `request_timeout_ms + 1 s` (rule 25). With the 70 KiB
  responses of 1b the worst case is 15 + 30 s instead of 16 s.
- `server.rs:252-256`: bytes of the next request read while the phase is `BUSY` do not start the header
  timer. A partial pipelined head then waits `idle_timeout_ms`, and one more byte adds `header_timeout_ms`.

Both are bounded (measured), neither extends without limit. Fix: on `response_done`, if the read buffer is
known to be non-empty or the write is not flushed, enter `HEAD` instead of `IDLE`; simplest is to track
"bytes seen since the last request started" in `Watched` and choose the phase from it.

### F-4 (low): shutdown cannot be hurried, and will be able to hang in 1b

- `lib.rs:175-185`: tokio keeps its handlers installed after the first signal, and nothing listens any more.
  A second `SIGTERM` or `SIGINT` is ignored while `server.rs:143-149` drains, for up to
  `request_timeout_ms + 1 s` (301 s at the top of the range). Only `SIGKILL` stops the relay sooner, which
  skips the flush. Fix: on a second signal, skip the drain and go straight to flusher stop, flush and close.
- `lib.rs:145-166`: the runtime is dropped at the end of `serve`. Dropping a tokio runtime waits for running
  `spawn_blocking` tasks without a time limit. There is none in 1a. In 1b a blocking task stuck on disk IO
  would hang shutdown before the index is flushed. Fix in 1b: `Runtime::shutdown_timeout`, and flush the
  index even if a task still holds it (today `Arc::try_unwrap` failing skips only `close`, which is right).

The reviewed order itself is correct: accept loop ends, flusher stopped (it cannot return while the flusher
holds a strong reference, `index.rs:295-299`), `flush`, `close`, each step run even if an earlier one failed,
first error returned. A failed bind takes the same path. A panic in the flusher is reported, not unwrapped.

### F-5 (low): tests to add

The suite covers the cap, slow headers, idle, slow body, slow handler, `431`, CORS, panic and shutdown. It
does not cover what this review had to check by hand: the silent connection; a client that never reads;
a partial pipelined head; `Content-Length` with `Transfer-Encoding` (the connection closes and the tail is
not parsed); that a connection task which ends by deadline, by error or by panic returns its permit
(`connection_cap` shows it for a clean close only); an unknown `SBTP_RELAY_*` variable through the binary's
exit status. Add them with 1b, so that a hyper upgrade that changes any of these is caught.

### F-6 (low): preflight runs outside every other layer

`api.rs:70-74`: `CorsLayer` is outermost and answers every `OPTIONS` that carries
`Access-Control-Request-Method` itself, for any path. Cost today: a few header writes, no allocation of
note, `Access-Control-Request-Headers` is not mirrored (measured). Correct for 1a. In 1c the limiter must be
placed with this in mind: if it sits inside `CorsLayer`, preflights are never rate limited; if it sits
outside, `429` loses its CORS headers (rule 34). Decide and test it.

### F-7 (info): defaults and logs

- Default bind is `127.0.0.1:8080` (`config.rs:567-569`), tested. A non-loopback `listen` is accepted
  without a word; one warning line at start-up would help an operator who exposes the relay by mistake.
- `server.rs:122`: `accept failed` is printed every 50 ms while the error lasts (file descriptor
  exhaustion): 20 lines per second in the journal. Log the first, then count.
- Logs carry no peer address, no header, no path. Panic text goes to standard error only; the `500` body is
  `{"error":"Internal"}`. No `Server` header, no version in `/info` or in any error body. Good.

### F-8 (info): hyper's parser

Accepted: bare `LF` line ends, a request without `Host`, an absolute-form URI, a tab after
`Transfer-Encoding:`. Rejected: everything in the table above. Go's HTTP server (Caddy) frames the same
cases the same way, so no disagreement to exploit was found; this was reasoned, not tested against Caddy.
A client that sends `FIN` right after its request gets no response (hyper default `half_close(false)`);
Caddy does not do that.

### F-9 (info): configuration input

- All derived values were checked for overflow: `blocking_floor` is at most 1,282 and is rejected above 512
  by the constraint (tested through the binary); `open_files_needed` and `memory_bound_bytes` cannot
  overflow within the ranges; `u64` to `usize` and `u32` conversions fall back safely. Values of 2^64 and
  `-1` are refused with the setting named. An unknown, lower-case or empty `SBTP_RELAY_*` name is an error,
  as are an unknown or nested TOML key, a duplicate key, a float, and 200,000 nested brackets (parser
  recursion limit, no stack overflow).
- `u64::MAX` is accepted for `max_future_ms`, `block_ttl_ms` and `sweep_interval_ms` (the ADR says
  "operator's choice"). 1b and 1c MUST add them to timestamps with checked or saturating arithmetic.
- `config.rs:373`: a TOML syntax error prints the offending line. Pointing `SBTP_RELAY_CONFIG` at another
  file the relay user can read shows one line of it on standard error. The operator controls both: no fix.
- `config.rs:351`: an environment variable whose **name** is not UTF-8 is skipped even if it starts with
  `SBTP_RELAY_`. Harmless; make it an error for consistency with rule 7.

## Answers to the review questions

1. **Slowloris, slow read.** No connection can be held past its deadlines; the head deadline is not
   extended by trickling. Permits can be held by silent connections for 30 s (F-1) and by polite keep-alive
   clients without limit (F-2). A half-open peer is closed at `idle_timeout_ms`.
2. **Limits, smuggling, pipelining.** No smuggling vector found; conflicting framing closes the connection.
   Pipelining is served in order with a bounded buffer.
3. **Permit leaks.** None. The permit is owned by the spawned future (`server.rs:135-138`) and is dropped on
   return, on panic (unwinding; `panic = "abort"` is not set) and on runtime shutdown. A handler panic is
   caught and counted; a dropped request leaves the phase `BUSY`, which the deadline closes. The index and
   the flusher are not reachable from a handler in 1a.
4. **Configuration.** See F-9. Unknown variable: error. Default bind: loopback.
5. **Disclosure.** None found (F-7).
6. **CORS.** `*` without credentials; allow-list compared byte for byte (case, suffix, port and `null`
   variants refused), `Vary: Origin` on every response including refusals and preflights; preflight is cheap
   (F-6 for 1c).
7. **Start-up order.** `self_test`, settings, router, data directory, index, flusher, runtime, signal
   handlers, bind. Nothing listens before the self-test and the settings pass; both refusals are tested and
   leave no file behind.
8. **New crates.** Clean (F-10).

  connections. Set Caddy's `keepalive` below 30 s in `deploy/`.
- Linux: the open-file check (`/proc/self/limits`), the listen backlog under a real storm, the musl build.
  Everything here ran on macOS, debug profile.
- The release profile (`opt-level = "s"`, LTO) and `cargo clippy` were not run.
- A line-by-line read of `toml`, `toml_parser` and `tower-http`; only manifests, build scripts, `unsafe`
  and the paths used were inspected.
- hyper internals were exercised as a black box at version 1.12.0; the phase logic depends on when hyper

## Re-review of e064e22 (2026-11-19)

Scope: `git diff 6ff5f64 e064e22`, read from the branch; scratch export built and attacked on loopback
(macOS, debug). `cargo test -p sbtp-relay --offline --locked`: 17 unit, 19 + 7 integration tests pass.
`cargo deny --offline check`: ok. Probe settings: header 1 s, request 2 s, idle 6 s, `max_connections` 4.

**Verdict: OK to merge.** F-1, F-3, F-4 and F-5 are closed. F-2 stays open as planned (1c, gates
exposure). One new low finding (R-1), not blocking.

| Point | Result |
|---|---|
| F-1, fresh connection | Closed. A silent connection, and one that sends a single byte, are cut at 1.0 s (`header_timeout_ms`). Keep-alive idle after `GET`, `HEAD`, a preflight, a `404` and a `POST` with a body is still 6.0 s. |
| F-3, response end tied to the flush | Closed. A flood whose responses are never read is cut 3.1 s after the socket stalls (`request_timeout_ms` + 1 s, not idle). The claim that hyper calls `poll_flush` on the IO only once its buffer is written out holds at hyper 1.12.0 and is pinned by `never_reading_client_is_cut_at_the_request_deadline`. Responses without a body leave the busy phase correctly. |
| F-3, pipelined bytes | Closed. Request plus partial head: cut at 1.0 s, also after a `Content-Length` body that contains blank lines, after leading `CRLF` and with bare `LF` line ends. |
| Fallback to the idle deadline | Not exploitable. Chunked request plus partial head, and third request of a burst: closed at 6.0 s, or 6.8 s when a byte is added just before, never beyond `idle_timeout_ms + header_timeout_ms`. Further bytes do not extend it. The deadline moves only on a complete request head or a completed response, so each extension costs one full request: that is an ordinary keep-alive client, already F-2. A scanner that disagrees with hyper can only pick the other of the two bounded timers; at worst a connection is closed early (a stray `CRLF` after a request closes it at `header_timeout_ms`). |
| Accept backoff | Correct for `EMFILE`, `ENFILE`, `ENOBUFS`, `ENOMEM`; `libc` 0.2.191 was already in the graph, constants only, lock entry unchanged. See R-1. |
| F-4, second signal | Closed. With a connection held in the drain: the listener closes on the first signal, the process is still draining 2 s later, a second signal ends it in 0.06 s with exit status 0, the log line is printed, and the index opens again at the next start without repair. `lib.rs::run` still runs flusher stop, `flush` and `close` after `serve` returns. |
| Smuggling, pipelining | Unchanged: `Content-Length` with `Transfer-Encoding` gives one response and a closed connection; 5,000 pipelined requests give 5,000 responses. |
| Other changes | Origins lowercased and stored as header values at load; `read_body` refuses an announced length over the limit before reading and sizes its buffer by at most the limit. No issue. |

**R-1 (low): an `accept` error outside the four classes is retried at once, without a log line**
(`server.rs`, `Err(e)` arm of the accept loop). If such an error is persistent (an `errno` not foreseen
here, or one specific to a platform), the loop spins on one core and prints nothing. No way for a remote
client to cause this was found. Fix: invert the default: continue at once only for the errors known to
concern one connection (`ECONNABORTED`, `ECONNRESET`, `EINTR`, `EPROTO`, and the network errors Linux
reports from `accept`), and log and pause for everything else.

**Still open.** F-1 is shorter, not gone: with the cap at 4, 8 sockets re-opened as they are cut still
starved every legitimate request. The defaults now need about 6 new connections per second instead of 1.
The bound per client of F-2 remains the real fix, and the relay still MUST NOT be exposed without a
reverse proxy that buffers request heads. F-6 (preflight and the 1c limiter) is unchanged.

Not checked in this pass: Linux and musl; the release profile; `cargo clippy`; a real Caddy in front.
