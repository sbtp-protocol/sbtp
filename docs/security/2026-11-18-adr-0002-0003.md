# Security review: ADR 0002 (domain separation) and ADR 0003 (strict verification, identity)

- Date: 2026-11-18
- Author: security reviewer
- Subject: `docs/decisions/0002-domain-separation.md`, `docs/decisions/0003-strict-verification-and-identity.md`,
  status "proposed", before acceptance and before any test vector.
- Context read: `docs/spec/sbtp-core-v0.2.md`, ADR 0001 and 0004, the open questions (not published),
  root `Cargo.toml`, `deny.toml`, `crates/sbtp-core/src/layout.rs`.

## Summary

No critical or high finding. Both constructions are sound and I recommend changing neither the BLAKE3
mode, nor the two strings, nor the signed message, nor criteria V1 to V6.

| ADR | Verdict |
|---|---|
| 0002 | **Acceptable as is.** Two wording clarifications desirable (B-5), non-blocking. |
| 0003 | **Acceptable with changes**: M-1, M-2, M-3 and B-1 to be integrated before acceptance. None of them touches V1 to V6 or the binary format. |

Three medium-severity findings, all on ADR 0003, all fixed by one normative sentence:

- M-1: batch verification in `ed25519-dalek` is **not** equivalent to V1-V6 (confirmed in the source); it must be explicitly forbidden.
- M-2: rule 12 (`legacy_compatibility`) has no agreed control mechanism; combined with "first write wins", a silent activation lets a third party neutralise a block on a relay.
- M-3: nothing requires the recipient of a `GET` to check that the received block has the requested `block_id`; this is the only real poisoning path for a relay.

No Rust toolchain on the machine (`cargo` missing), no `Cargo.lock`, no crypto code in the repository:
the review covers the text of the ADRs and the source of the crates. The published archives were downloaded
from `static.crates.io`, their SHA-256 compared with the one from the crates.io API (identical), then read

## Medium-severity findings

### M-1. Batch verification in `ed25519-dalek` 3.0.0 diverges from V1-V6

- **Severity:** medium (none as long as the `batch` feature is not used; network partition otherwise).
- **Where:** ADR 0003, rule 3 and the "Not confirmed" paragraph (lines 59-61, 82-83).
- **Finding.** The "not confirmed" point is **refuted**. `verify_batch` (`ed25519-dalek-3.0.0/src/batch.rs`,
  lines 150-250):
  - decompresses `R` (`sig.R.decompress()`) instead of comparing bytes: a non-canonical `R` is accepted;
  - tests neither `R` nor `A` for small order;
  - multiplies each equation by a 128-bit pseudo-random coefficient: a torsion component vanishes or not
    depending on that coefficient.

  The crate's README says so itself: the same edge case can pass in one batch and fail in another
  ("21% chance that one fails and the other succeeds"), and "`verify_batch()` does not do the weak key
  testing of `verify_strict()`".
- **Scenario.** A hostile sender crafts a block whose `A` or `R` carries a torsion component. A relay
  that verifies in batches accepts or rejects it depending on the batch composition; a relay using `verify_strict`
  returns a fixed verdict. The same block is stored here and refused there: the DAG diverges, with no stolen key.
- **Fix.** Replace rule 3 with a clear prohibition, for example: "`ed25519_dalek::verify_batch`
  MUST NOT be used to validate a block; its verdict differs from V1-V6 (non-canonical R, small order,
  torsion)." Keep the general wording for third-party implementations. Do not enable the `batch`
  feature in the workspace (it also pulls in `keccak`, `strobe-rs`, `rand_core`).

### M-2. Rule 12 with no agreed control: an activation of `legacy_compatibility` makes "first write wins" exploitable by a third party

- **Severity:** medium (conditional on a configuration error, but silent and with a large effect).
- **Where:** ADR 0003, rule 12 and "Supply chain" (lines 109-111, 135-136).
- **Finding.** Checked in `ed25519-dalek-3.0.0/src/signature.rs` lines 67-94: with the feature, `check_scalar`
  only tests `bytes[31] & 224`; `S + L` is accepted for almost any signature. The ADR leaves the control
  "to cargo deny or to a test", without choosing. Clarification: it is the `ed25519-dalek` feature that weakens
  V3; the `curve25519-dalek` feature alone only makes `Scalar::from_bits` public
  (`curve25519-dalek-5.0.0/src/scalar.rs` line 271).
- **Scenario.** A transitive dependency of the relay enables the feature (Cargo feature unification is enough). A third party
  sees a valid block `(R, S)` propagating and sends `(R, S + L)` to the lax relay before the original. The relay
  stores it; rule 8 then forbids it from replacing it with the correct signature. Every strict client that
  reads this block on this relay rejects it: the block is censored on this relay, permanently, without knowing the key.
- **Fix.** Make the control normative and executable, rather than declarative:
  1. a negative test vector `S + L` (expected: `InvalidSignature`), run by `cargo test --workspace`
     **and** by every shipped binary; the relay replays it at startup and refuses to start if it passes;
  2. as a complement only, a `cargo deny` rule on the feature (syntax to be checked in the
     cargo-deny docs, not checked here).

  The test also protects against a regression in the crate, which `cargo deny` does not.

### M-3. No obligation to check that the received block carries the requested `block_id`

- **Severity:** medium (this is the answer to "can a relay serve a variant": not through the signature,
  but through this gap).
- **Where:** ADR 0003, rules 7 to 10 and new §3.4; spec §4 (`GET /sbtp/v1/block/{block_id}`) and §5 step 4.
- **Finding.** The ADR settles storage on the relay side (rule 9: validation before storage). Nothing is said about
  the recipient of a `GET` or of a synchronisation: §5 requires the block to be "validated independently", not
  that it match the requested identifier.
- **Scenario.** A hostile relay answers `GET /block/X` with a perfectly valid block `Y` (the attacker's PoW and
  signature). A client that validates "the block" then files it under the requested key `X` now has
  arbitrary content in place of a parent, and "first write wins" freezes it in its cache. A
  third-party JavaScript implementation will make this mistake.
- **Fix.** Add to §3.4: "Every recipient (client, peer, cache) MUST recompute the `block_id` of the
  received bytes, reject the block if it differs from the requested identifier, and apply V1-V6 before any storage
  or display. The "first write wins" rule applies only to fully validated bytes." Plan a
  "valid block, wrong identifier" test vector.

## Low-severity findings

### B-1. Non-canonical PubKey: rule in "MAY", non-deterministic error variant, inaccurate RFC reference

- **Where:** ADR 0003, V1 (line 73), rule 4, rule 11, "Non-canonical PubKey" (lines 124-129).
- **Finding.** The ADR's analysis is right in substance; I recomputed it: 12 values `y < 19` are on the
  curve (0, 1, 3, 4, 5, 6, 9, 10, 14, 15, 16, 18). With both signs and the two "x = 0, sign bit set to 1"
  encodings, this gives 26 non-canonical encodings: 6 of small order (rejected by V2), 20 denoting
  points with no known discrete logarithm. No valid block can therefore carry such a key. But:
  - V1 refers to RFC 8032 §5.1.3, which **rejects** `y ≥ p`, while rule 11 implements V1 with
    `VerifyingKey::from_bytes`, which **accepts** it (`curve25519-dalek`: `FieldElement::from_bytes` masks the high
    bit and does not test canonicity; `from_bytes` documentation: "valid under ZIP-215 rules");
  - the returned variant differs by implementation (`InvalidPublicKey` or `InvalidSignature`), which
    contradicts ADR 0004 ("the first check that fails determines the error") and makes these vectors
    non-portable.
- **Scenario.** No attack. A test vector with a non-canonical key yields two different errors depending on the
  library; an "RFC-compliant" third-party implementation and `sbtp-core` diverge on the error.
- **Fix.** Make rule 4 a MUST: "V1bis: `A` is not the canonical encoding of the decoded point",
  variant `InvalidPublicKey`. Cost: one recompression (`key.to_edwards().compress().as_bytes() != &pubkey`;
  `to_edwards` exists in 3.0.0, `verifying.rs` line 489). This is what the RFC and most strict
  libraries do, and it is testable by vector. Failing that, reword V1 without the RFC and fix the
  expected variant.

### B-2. Rule 6: an unverifiable "MUST NOT"

- **Where:** ADR 0003, rule 6.
- **Finding.** No validator can detect the violation, and a legitimate randomised signer (HSM,
  "hedged" signature) that re-signs a block whose signature it lost violates it without knowing. The ADR
  itself rejects the deterministic "MUST" for this reason.
- **Fix.** "SHOULD NOT". Add: a layer (L1, L2) MUST NOT make any state depend on the signature
  bytes (sorting, random draw, deduplication).

### B-3. Rule 9: replaying an already stored block costs the relay an Ed25519 verification and the attacker nothing

- **Where:** ADR 0003, rule 9.
- **Finding.** The PoW does not protect this path: a valid block that is already public can be replayed for free, and the rule
  requires hashing, PoW then `verify_strict` (about 30 to 45 µs per call according to the measurements in the crate's
  README, more without the `fast` feature, see B-4) before looking at storage.
- **Scenario.** An attacker replays popular blocks in a loop: CPU load with no mining cost. Rate
  limiting remains the real defence; this only reduces the unit cost.
- **Fix.** Allow the equivalent shortcut: after the format check and C1, if the `block_id` is stored **and**
  the received bytes are identical to the stored bytes, answer "already present" without re-verifying; if the
  bytes differ, verify the signature as today. Observable behaviour is unchanged.

### B-4. Features and pinning of the crypto crates (outside the ADRs, to handle before Phase 1)

- **Where:** root `Cargo.toml`, lines 25-26.
- **Finding.** Confirmed in the `ed25519-dalek` 3.0.0 manifest: `default = ["fast", "zeroize"]`.
  `default-features = false` therefore removes the wiping of `SigningKey` on drop (`signing.rs` lines
  718-726, under `cfg(feature = "zeroize")`) and the precomputed tables. Also, `version = "3.0.0"` is
  a `^3.0.0` constraint, not a pin, and there is no `Cargo.lock` yet.
- **Fix.** `features = ["zeroize"]` at the workspace level (`no_std` compatible); `fast` at least for the
  relay. Generate and commit `Cargo.lock` as soon as a toolchain is available, CI with `--locked`.

### B-5. ADR 0002: two wording clarifications

- **Where:** ADR 0002, rules 8 to 10.
- **Finding.** (a) The signed message has neither a length nor a terminator; separation between future uses relies
  on the prefix alone. Rule 10 requires "distinct" strings, which does not prevent one string from being the
  prefix of another (`SBTP-v1-block-sig` and a hypothetical `SBTP-v1-block-sig-ack`). (b) Rule 9
  only requires new strings if the version "changes the covered bytes or the algorithm".
- **Scenario.** A future 49-byte message `SBTP-v1-block-sig-ack ‖ …`, whose remainder is chosen by a
  third party, would be a valid block signature. Rule 8 already forbids this in implementations; it should
  also be forbidden in the design.
- **Fix.** Rule 10: "no SBTP signature prefix is the prefix of another". Rule 9: every
  new value of the Version field defines new strings, unconditionally. Keep the list of strings
  in the spec.

### B-6. Notes for Phase 2 (relay), direct consequences of the two ADRs

- **"First write wins" must be atomic.** `rename()` overwrites the target: two concurrent `PUT`s of two
  variants give "last write wins". Use exclusive creation (`create_new`, or `link` from the
  temporary file to the final name).
- **Storage sharding.** With the PoW, every `block_id` starts with zeros. Sharding into
  subdirectories on the first bytes puts everything in the same directory; shard on the last bytes instead.

## Points checked with no severity (info)

### 1. `block_id` construction: sound

- **`derive_key` mode on public and hostile data: confirmed.** The BLAKE3 paper targets 128 bits of
  security "against (second-)preimage, collision, or differentiability attacks" (§4.1) for the whole
  function; the three modes are "domain-separated" (§2.3) and differ only by the key words and a
  flag present in every compression. The analysis of the mode (§4.3) assumes no secret. With a fixed
  context, `derive_key` is a hash function with a constant public key and the `DERIVE_KEY_MATERIAL` flag:
  collision and preimage resistance unchanged. §6.2 presents this mode as the replacement for the
  BLAKE2 personalisation parameter, which is exactly the use made here. §7.8 ("no key
  derivation function can extract useful security from key material that is not secret") is about the secrecy
  of the output, irrelevant for a public identifier. Caveat: the paper does not state the phrase "public
  material chosen by a third party"; the conclusion follows from its analysis, it is not a quote from it.
- **Context string.** 27 bytes, the ADR's hexadecimal recomputed and correct. Format consistent with the
  recommendation of §6.2 (hard-coded, unique, no variable data).
- **Unambiguous hashed input.** Under rules F1-F9 of ADR 0004, `block[0 .. Offset(Signature)]`
  decodes in only one way: no collision through split ambiguity.
- **Proof of work.** Uniform output, no bias introduced by the mode. The nonce is in the first 64-byte
  block: no reusable upstream intermediate state, and beyond 1,024 bytes only the first
  chunk and the path to the root are recomputed. The cost per attempt is therefore bounded (one compression for a
  minimal block, 54 bytes hashed) and **independent of the payload size**: to be taken into account for Q-06,
  not a defect of the ADR. The PoW reduces the identifier space to `256 − d` bits (collisions at
  `2^((256−d)/2)`): no consequence for realistic `d`.
- **Interoperability: confirmed** in the sources: `noble-hashes` (`context` option), Go
  `lukechampine/blake3` (`DeriveKey`) and `zeebo/blake3` (`DeriveKey`, `NewDeriveKey`), Python `blake3`
  (`derive_key_context`), official C. The official BLAKE3 vectors cover the `derive_key` mode.
- **Consistency with Q-01.** Blobs would be addressed by plain BLAKE3: a `block_id` can then never
  be confused with a blob hash. This is a concrete benefit of the decision.
- **`no_std`: confirmed by reading** (`blake3-1.8.7/src/lib.rs` line 88,
  `#![cfg_attr(not(feature = "std"), no_std)]`), not compiled. Note: the `blake3` `build.rs` compiles
  assembly or C via `cc` unless the `pure` feature is set; no effect on the security of the format.

### 2. Signed message: the intended separation is achieved

- A protocol that signs 32 raw bytes cannot produce a block signature, and vice versa: true.
- No interaction with Ed25519ph/ctx: their `dom2` prefix comes before `R ‖ A`, the SBTP prefix is in `M`.
- Cross-version replay: covered twice (hashed Version byte, `v1` suffix in both strings).
- Ed25519ctx absent from `ed25519-dalek` 3.0.0: **confirmed** (only byte `1`, Ed25519ph, is emitted:
  `verifying.rs` line 539, `signing.rs` lines 986 and 997). Rejecting this alternative is justified; a
  message prefix in pure Ed25519 is common practice (TLS 1.3, SSHSIG) and can still be signed with WebCrypto.
- Signing a hash rather than the content makes the signature depend on BLAKE3 collision resistance.
  No consequence: content addressing already depends on it.
- Residual risk, already written in the ADR: an SBTP key reused in a system that signs arbitrary
  bytes supplied by a third party (a wallet with `signMessage`, for example). To be repeated in the client
  docs: an SBTP key is for SBTP only.

### 3. Criteria V1 to V6: complete and consistent with `ed25519-dalek` 3.0.0

Read in `verifying.rs` (lines 175-183, 200-202, 367-390, 504-562) and `signature.rs` (lines 87-94, 149-160):

| ADR claim | Result |
|---|---|
| `from_bytes`, `is_weak`, `verify_strict` with no Cargo feature | confirmed |
| `verify_strict`: `S < L`, then decoding of `R`, then small order of `R` and `A`, then equation | confirmed, in this order |
| Cofactorless equation, `R` recomputed, compressed and compared byte for byte | confirmed (`RCompute::finish`) |
| `k` reduced modulo `L` | confirmed (`Scalar::from_hash`, `from_bytes_mod_order_wide`) |
| `is_weak` tests `[8]A = 0` | confirmed (`mul_by_cofactor().is_identity()`) |
| `from_bytes` accepts a non-canonical `y` | confirmed (see B-1) |
| `legacy_compatibility` replaces `S < L` with a 3-bit test | confirmed |
| `Signature` (crate `ed25519` 3.0.0) from 64 bytes | **confirmed**: `Signature::from_bytes(&[u8; 64]) -> Signature`, infallible, no validation; `from_slice` only fails on length. Every check is done in `verify_strict`. |
| Equivalence of batches and `verify_strict` | **refuted** (M-1) |

- `verify_strict` gives strong unforgeability (a third party cannot derive a second signature) and, by
  rejecting small-order keys, binds the signature to a single message. The crate's test suite
  (`tests/validation_criteria.rs`) states that the only accepted edge cases are a torsion component in
  `A` or in `R` (mixed order).
- **Mixed order: keep "mod L" in V6 as is.** For a mixed-order `A`, `[k]A` and `[k mod L]A`
  differ; RFC 8032 does not explicitly reduce `k`. The ADR's wording settles it, and it is observable:
  a test vector with a mixed-order `A` is needed. Only the sender can craft such a block; the verdict is
  deterministic under V1-V6. Also requiring a torsion-free `A` would cost one scalar multiplication per
  verification for zero gain: not recommended.
- State in V6 that `R` and `A` enter SHA-512 as received, and that the digest is read as a
  512-bit little-endian integer.
- **Vectors.** The C2SP CCTV `ed25519vectors` (the ones the crate uses) classify each case by
  flag; they cover free-form messages, so equivalent SBTP blocks will have to be crafted (one case
  per criterion V1 to V6, plus `S + L`, plus accepted mixed order).
- **Clients.** `crypto.subtle.verify` (WebCrypto) does not apply the same criteria across browsers:
  the PWA must validate through `sbtp-wasm`, never through WebCrypto. WebCrypto remains usable for signing.

### 4. Identity by `block_id` and "first write wins"

- **Variant crafted by a third party:** impossible under V1-V6, except M-2.
- **Variant served by a relay:** it can only serve invalid bytes or another block; both
  are detected if the recipient validates and compares the identifier (M-3).
- **Several signatures by the author:** harmless, as the ADR says. Consequences to be aware of: two
  relays may return different bytes for the same identifier, so no `ETag`, checksum
  or cross-relay comparison must cover the full bytes (rule 10, sufficient).
- **PoW checked before the signature:** a third party can mine a block in the name of a key it does not hold and
  force a signature verification. It pays for the PoW; acceptable.
- Rejecting the "signature inside the `block_id`" alternative is justified.

## What I could not check

- **Nothing was compiled or run**: no Rust toolchain. `cargo deny check`, `cargo audit`, `cargo tree`
  (actually unified features), the `no_std` build and the `wasm32` build remain to be done. Advisories were
  searched on api.osv.dev for the four crates read, not for their transitive dependencies (`sha2` 0.11,
  `subtle`, `signature` 3, `arrayvec`, `constant_time_eq`, `cc`).
- **Behaviour, not just reading**: no vector was run through `verify_strict`. The conclusions
  of point 3 rest on the source; the Phase 1 negative vectors will be the proof.
- **Third-party libraries**: the presence of the `derive_key` mode was checked in the sources of four
  libraries, not tested against the official vectors. The Ed25519 criteria of libsodium, BoringSSL and
  browsers were not reviewed; the remark on WebCrypto comes from the literature (studies of Ed25519
  validation criteria), not from a test.
- **`cargo deny` syntax** to forbid a feature: not checked.
- **Security of 7-round BLAKE3**: I rely on the paper's claims and on the state of the art it
  cites; no analysis of my own.
- ADRs 0001 and 0004 were read only as context, not audited.
