# Security review: relay milestone 1b (block store, `PUT /block`, `GET /block/{id}`)

- Date of the review: 2026-11-19 (the file name was set by the requester).
- Scope: branch `feat/relay-m1b-blocks`, commits `5b1d4ff` and `c341c2d`, read as
  `git diff main...c341c2d` (10 files, +1,859 −41). Main at `ad73ecb`.
- References: spec `sbtp-core-v0.2.md` §3.4 and §4; ADRs 0003 (rules 9 to 11), 0004, 0007, 0008, 0009,
  0012, 0013, 0018 to 0022; the earlier relay reports of this folder.
- Method: reading of the diff; a scratch copy (`git archive c341c2d`, outside the repository, its own
  target directory) for the existing suite, `clippy -D warnings`, `cargo deny check`, and attack tests
  added in the scratch copy only. Nothing was checked out or modified in the repository except this
  file. All measures below are from a debug build on macOS (APFS), not from the Linux target.

## Verdict

**Mergeable into `main`. Not yet fit for an Internet-exposed deployment: M-1 must be fixed, and L-1
decided, before milestone 1 is exposed.** No critical or high finding. The property that matters most
for this change holds: no client byte takes part in a path, nothing reaches a final name before F1 to
F9, P1, C1, C2 and C3 have passed, a stored file is never replaced, and no partial file is visible.

| Id | Severity | Subject | Blocking |
|---|---|---|---|
| M-1 | medium | The quota is overshot through index growth (measured: 21% over, stays over) | not for the merge; before exposure |
| L-1 | low | A damaged stored file is permanent: `PUT` answers `200`, the block stays unservable or invalid (design questions b and c) | no; owner decision |
| L-2 | low | The block cache holds 2 to 4 times `block_cache_bytes` of real memory | no |
| L-3 | low | Start-up walks the whole store twice and does not listen meanwhile | no |
| L-4 | low | Symbolic links and special files inside `data_dir` are followed (local attacker only) | no |
| I-1 to I-9 | info | See below | no |

Existing suite on the scratch copy: 108 tests pass (49 unit, 16 `blocks`, 26 `http`, 1 `logging`,
16 `startup`); `clippy --all-targets -D warnings` clean; `cargo deny check`: advisories, bans, licenses,
sources ok.

## Findings

### M-1 (medium): `max_store_bytes` is overshot by the growth of the index file

- Where: `crates/sbtp-relay/src/store.rs` lines 145 to 172 (`index_bytes`, `reserve`).
- `reserve` adds the cost of the new block file to the **current** size of `index.redb`. The index
  entries of that block are written afterwards and are not reserved. redb grows its file by doubling.
- Scenario, measured: `max_store_bytes = 2,097,152`, `min_pow_difficulty = 0`, minimum-size blocks with
  8 parents. The index file went 73,728 → 143,360 → 282,624 → 561,152 → 1,118,208 bytes. Block 347 was
  admitted with the index at 561,152; its insert doubled the file. End state after the first `507`:
  block files 1,421,312 + index 1,118,208 = **2,539,520 bytes, 442,368 over the quota (21%)**, and it
  stays over. The bound of the overshoot is the size of the index before a doubling, so up to roughly a
  third of the quota with 8-parent blocks (about 300 MiB on the 1 GiB default).
- Effect: ADR 0013 rule 18 ("bounds the disk space") does not hold against a remote sender who pays
  only the PoW. An operator who sizes the volume to the quota gets real `ENOSPC`, which then hits the
  index (`500`, I-3) and the logs, not only new blocks.
- The concurrent part is fine: the compare-and-swap loop holds (16 threads, 64 blocks of 60 kB, quota
  1 MiB: 17 created, `used = 1,044,480 ≤ 1,048,576`, no temporary file left).
- Fix: reserve room for the index before the block is written. Either count the index as its size
  after its next growth step, or reserve a worst-case per-block index allowance (1 + parents rows)
  together with the file cost and refuse when file + allowance does not fit. Add the test "after the
  first `507`, block files + index ≤ `max_store_bytes`" with 8-parent blocks.

### L-1 (low): a damaged stored file can never be repaired, and `PUT` reports success

- Where: `crates/sbtp-relay/src/blocks.rs` lines 163 to 171 (shortcut and `repair`), 232 to 245
  (`load`); `crates/sbtp-relay/tests/blocks.rs` line 281 asserts the behaviour.
- The `block_id` does not cover the signature (spec §3.4), so R1 on read cannot see a damaged
  signature. Two cases, both measured:
  - **Body damaged** (one payload byte flipped): `GET` → `404`; `PUT` of the valid block → `200`;
    `GET` → still `404`. The `PUT` also adds an index entry for the unservable file, although the
    start-up reconciliation refuses to index the same file.
  - **Signature damaged** (last byte flipped): `GET` → `200` with the invalid bytes and
    `Cache-Control: … immutable`; `store_corrupt` does not move; `PUT` of the valid block → `200`;
    `GET` → still the invalid bytes.
- Not reachable by a remote client: it needs disk corruption or local write access. The cost is a
  client told `200` for a block this relay cannot serve, for as long as the file exists.
- **Question (b), no signature check on `GET`: agreed, keep it.** A recipient MUST validate (§3.4) and
  the relay is not trusted. Verifying on every cache miss would change the cost model of ADR 0018
  rule 18 for a fault that only local corruption produces. Close the gap on the `PUT` side instead.
- **Question (c): yes, replace, under these conditions.**
  1. Only inside a `PUT` permit, and only after the submitted bytes passed C1 to C3.
  2. Only when the stored file fails **full** validation for that id: parse, R1 and signature. The
     check is deterministic, so a valid stored file can never be displaced by a variant: first write
     wins is unchanged for validated bytes, which is the scope spec §3.4 gives the rule.
  3. An I/O error while reading the stored file is never grounds for replacement (`500`, as today).
  4. Mechanics: atomically move the bad file out of the final name (or unlink it; the data is public
     and has no forensic value), `fsync` the directory, then the normal exclusive `link` path, so two
     racing repairs still give one winner. Drop the cache entry. Count it and log one throttled `warn`
     with the 8-character suffix.
  5. Cost to bound: one more signature verification when the bytes differ. Verify the submitted bytes
     first, so that only a key holder can reach the second verification.
  This needs one line in ADR 0003 rule 9 or ADR 0013. Until it is decided: `repair` should not index a
  file that fails parse and R1.

### L-2 (low): the cache bound counts block lengths, not the memory held

- Where: `crates/sbtp-relay/src/store.rs` lines 258 to 260; `crates/sbtp-relay/src/cache.rs` lines 62
  to 84.
- `read_to_end` through `Take` has no size hint: the vector grows by doubling. Measured capacities:
  118 → 256, 4,118 → 8,192, 33,118 → 65,536, 65,653 → 131,072 (ratio 1.6 to 2.2). `Bytes::from` keeps
  that allocation. Each entry also costs a `HashMap` slot, a `BTreeMap` slot and the `Bytes` header
  (roughly 150 bytes, not measured), uncounted.
- Scenario: a sender stores minimum-size blocks and reads each once. The cache then holds about 3.5
  times `block_cache_bytes`: about 7 MiB for the 2 MiB default, against a 12 MiB memory target
  (ADR 0013). Still a function of the settings (ADR 0018 rule 4), but not the function it documents.
- Fix: size the buffer from the file length (capped at `MAX_BLOCK_LEN + 1`) or shrink it before
  `Bytes::from`; charge a fixed per-entry overhead in the bound.
- The rest of the cache is correct: the bound is checked at every insert, an oversized block is not
  cached, keys are the parsed id, and the only insert follows parse and R1 for that same id. I found no
  path that serves one block's bytes under another id.

### L-3 (low): start-up cost is linear in the number of files, twice

- Where: `crates/sbtp-relay/src/store.rs` lines 119 to 121 (`open`) and 347 to 403 (`reconcile`);
  `crates/sbtp-relay/src/lib.rs` (both run before the listener).
- Measured with 20,000 files, warm cache: `Store::open` 1.6 s, `reconcile` 1.7 s with the index
  present; 24.6 s for a full rebuild without index (one non-durable commit per block). Extrapolated to
  a full default store of minimum-size blocks (262,144 files): about 45 s per restart, about 5 minutes
  for a rebuild, here; a cold rotating disk will be worse, a release build on Linux better.
- Lever: a sender who fills the store with minimum-size blocks makes every later restart that slow.
  The bound is `max_store_bytes / 4,096` files, so it is a function of the settings. During that time
  the relay does not listen, although ADR 0013 rule 11 says `GET /block` and `/info` SHOULD be served.
- Correctness after `SIGKILL`, by reading each point: before the `link`, only a temporary file exists
  and `open` removes it; after the `link`, the file is complete (it was `fsync`ed first) and is indexed
  at start-up with its modification time; after a non-durable index insert, the same. The three crash
  tests cover the last two points; the first is not tested.
- Modification time: set by the relay's own write, not by a client. A wrong clock or a restored backup
  shifts `received_at` of repaired blocks only; a time before 1970 becomes 0. Safe.
- Fix: one walk for both the quota sum and the reconciliation; a start-up log line with file count and
  duration; the batch insert and serving `GET` during reconciliation can wait for milestone 1c.

### L-4 (low, local attacker only): links and special files inside `data_dir`

- Where: `crates/sbtp-relay/src/store.rs` lines 100 to 110, 232 to 244, 252 to 260.
- Measured: with `data_dir/tmp` a symbolic link to another directory, `Store::open` deleted the regular
  files of that directory. A shard directory that is a symbolic link is followed by `PUT` and `GET` but
  skipped by the scan. A dangling link at a final name gives `200` on `PUT` and nothing stored; a FIFO
  there blocks a read permit forever.
- Nothing here is reachable over HTTP: `create_new` and `link` never follow a link at the last
  component, and no client byte reaches a path. It matters only if another local account can write in
  `data_dir`.
- Files and directories are created with the process umask (typically `0644` and `0755`). The content
  is public, so this discloses nothing; the directory mode is what protects against the above.
- Fix (cheap): create `data_dir`, `blocks/`, `tmp/` and the shards with mode `0700`, files `0600`;
  refuse to start if `blocks` or `tmp` is not a real directory.

### Info

- **I-1. Milestone 1b has no rate limiter** (`server.rs` line 448, `HOOK(1c)`). With the defaults a
  sender with two client keys can fill 1 GiB in minutes at 16 bits of PoW, and hold all four `PUT`
  permits with slow bodies (accepted in ADR 0018). Do not expose a 1b build.
- **I-2. `GET /sbtp/v1/block/{id}?anything`** is served (`200`, `immutable`): the query string is
  ignored. Harmless for the relay; it lets a client vary the cache key of a CDN in front.
- **I-3. Other space errors give `500`:** `EDQUOT`, and `ENOSPC` from the index insert (the file stays,
  as an orphan repaired later). `507` is produced before any name is visible in every case I read:
  temporary write, `mkdir`, `link`.
- **I-4. A duplicate `PUT` can get `200` before the first writer's directory `fsync`.** A power loss in
  that window can leave an index entry without file: a phantom, tolerated by ADR 0013 rule 8.
- **I-5. `store_corrupt` counts events, not files:** each `GET` of a damaged file adds one, so a client
  can inflate it. Fixed cardinality; no log line.
- **I-6. `tmp/` and `blocks/` must share a file system** (`link`); otherwise every `PUT` gets `500`.
  Worth one line in the deployment notes.
- **I-7. Q-31 confirmed and visible at low fill:** 347 files used 538 directories in the quota test.
  Open and accepted; the inode and free-space watermark is milestone 1c.
- **I-8. Supply chain.** No manifest or lockfile change. `moka` is not in `Cargo.lock` and not used; it
  remains in `[workspace.dependencies]` (cargo warns) with a stale `TODO(1b)` in
  `crates/sbtp-relay/Cargo.toml` line 26. Remove both. `libc` was already a direct dependency.
- **I-9. Logs and counters.** No block byte and no client string reaches a log line. The id appears as
  its last 8 characters, in `block_stored` and `block_rejected`, both `debug`. Error text comes from
  `io::Error` (no path). All new counters have a fixed set of labels.

## Checked and found correct

- **Paths.** Built from a `BlockId` only. `GET` parses the raw path: `400` for uppercase, a
  percent-encoded character, `..%2f`, an encoded slash, `.bin`, `%00`, `;a=b`, 63 characters; `404`
  (no route) for an empty id, a trailing slash, `../`, a double slash. Absolute-form targets behave the
  same. No file or directory was created by any probe.
- **Write path.** Exclusive create in `tmp/`, `write_all`, `sync_all`, shard `mkdir` with parent
  `fsync`, `link`, unlink of the temporary name, `fsync` of the shard. Never a rename. Two `PUT`s of
  the same block: one `201`. The quota bytes of a loser or a failure are returned.
- **`PUT` order.** `413` from `Content-Length` before admission; per-client slot (`429`), class permit
  (`503`), then the body under `body_timeout_ms` with the byte limit; then F1 to F9, P1, C1, the lookup,
  C2 and C3, the store, the index. The shortcut compares the whole stored file with the whole body; it
  skips the signature check only for bytes equal to a file already under a final name. Its one weakness
  is L-1 (a stored file that was damaged afterwards).
- **Permits.** Both are owned by the blocking closure: released on return, on panic (unwinding; the
  release profile forbids `panic = "abort"`) and if the task never starts. A request dropped while it
  waits or reads the body releases them with its future.

## Not checked

- The Linux musl target and a release build: every measure here is from macOS, debug. Start-up times
  and the redb growth steps should be read again on the gate VM.
- Power loss (as opposed to `SIGKILL`), and file systems that do not honour `fsync`.
- A crash between the temporary write and the `link`: read, not tested.
- `HEAD` on the block route: my test client mis-read the response; inconclusive.
- `read_body` and the `413`/`408` paths beyond the existing tests: unchanged since the 1a review.
- redb's own behaviour at `ENOSPC`.
- `cargo audit` is not installed; `cargo deny check advisories` ran offline, on the local advisory
  database.
