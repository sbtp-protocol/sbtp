# Security review: ADR 0019 implementation in `sbtp-relay`

- Date: 2026-11-19
- Reviewed: branch `feat/relay-m1a-adr0019`, commit `3fc75af` (merge base `6c42af9`), read-only.
- References: ADR 0019 rules 28 to 40, ADR 0018 rule 20, `docs/security/2026-11-19-relay-m1a.md` (F-2, R-1).
- Method: code reading of `git diff main...3fc75af` (8 files, all under `crates/sbtp-relay/`), plus attack
  clients run against a scratch copy of the commit over real loopback sockets. Nothing was checked out or
  modified in any worktree.

## Verdict

**OK to merge.** No critical, high or medium finding. Seven low findings and four informative points, none
blocking. F-2 is closed for the documented deployment (behind a reverse proxy that appends
`X-Forwarded-For`); R-1 is closed except for one residual case (L-3). Two of the low findings (L-1, L-5)
should be settled before milestone 1c, because the limiter will reuse the same client key.

The relay still MUST NOT be exposed directly to the Internet: the per-client bound is a bound per key, and
keys are cheap for an attacker with several addresses (I-1).

## What was verified and holds

Measured on the scratch copy unless marked "by reading".

**`X-Forwarded-For` (focus 1).** With 8 requests in flight for `203.0.113.7` through a trusted peer:

| Header sent | Result | Meaning |
|---|---|---|
| `198.51.100.1, 203.0.113.7` | `429` | The rightmost entry is used; a client-written leftmost entry is ignored. |
| `203.0.113.7, 198.51.100.1` | `200` | Same. |
| Two header lines, `198.51.100.1` then `203.0.113.7` | `429` | The last line is the rightmost. |
| Two header lines, `203.0.113.7` then `198.51.100.1` | `200` | Same. |
| `203.0.113.7, 127.0.0.1` and `203.0.113.7,127.0.0.1 ,::1` | `429` | Trusted entries are skipped from the right. |
| `203.0.113.7, ::ffff:127.0.0.1` | `429` | A mapped trusted entry is normalised before the trust check. |
| `::ffff:203.0.113.7` and `::ffff:cb00:7107` | `429` | IPv4-mapped forms map to the IPv4 key. |
| Tab-padded value, lowercase header name | `429` | Whitespace is trimmed. |
| `Forwarded: for=...` next to the header | `429` | `Forwarded` is not read. |
| `203.0.113.7:4711`, `[2001:db8::1]:4711`, `unknown`, empty value, trailing comma, `"203.0.113.7"`, `203.000.113.007`, `0xcb.0.113.7` | `200` | Not an IP address: the request goes to the proxy's key (L-1). |

- A spoofed header from a direct, non-trusted peer has no effect: the ninth connection is closed at accept
  before the request is read (`server.rs:225-243`), and the header is read only inside
  `if let Some(requests)`, which exists only for a trusted peer (`server.rs:250`, `307-308`).
- A client behind an appending proxy cannot collapse other clients into one key or spread itself over
  several: it controls only entries to the left of the one the proxy writes, and the search stops at the
  first untrusted or unparsable entry from the right (`client.rs:89-103`).
- No panic path in the parser by reading: `to_str` failure and parse failure both return the peer address;
  header size is bounded by `max_header_bytes`.

**Per-client bound (focus 2).**

- Direct: 2,000 connections opened over the bound, each with a request written at once: 2,000 closed
  without a byte, 2.9 s in total, one log line (the warning is throttled). The count is taken after
  `accept` and before the connection task exists (`server.rs:226-243`).
- Proxied: the ninth request gets `429` with `Retry-After: 1` and the CORS header. With
  `Content-Length: 60000` and no body sent, the `429` arrives in 76 ms and hyper closes the connection at
  once, so an over-bound request cannot hold a slot or a connection. With `Expect: 100-continue` the first
  response is the `429`, no `100`.
- Release: the key is free again 200 ms after the client aborts 8 requests in flight, after 8 requests end
  in `503` at `request_timeout_ms`, after 20 handler panics in a row, and after 20 over-bound `429`. Three
  pipelined requests on each of 8 proxied connections are all served (one slot per connection, replaced,
  not leaked).
- No leak or underflow by reading: a `Slot` is owned either by the accept task's future
  (`server.rs:252-256`) or by `ConnState` (`server.rs:439`, `472`), both dropped on every exit path
  including a task panic; `Drop` uses `saturating_sub` and removes the entry at 0 (`client.rs:156-165`); a
  poisoned mutex is recovered. The tables hold at most `max_connections` entries each, since every entry is
  backed by an open connection.
- The exemption test runs on the normalised address before the /64 aggregation (`client.rs:69-73`). An
  exempt /128 inside a /64 therefore exempts that address only, and an exempt IPv4 block matches the mapped
  form.
- IPv6 key: `Cidr::network` masks with `checked_shl(128 - prefix)`; the range 32 to 64 excludes the shift
  by 128 for a client key, and the general case falls back to mask 0 (`config.rs:243-258`). Only
  `::ffff:0:0/96` is treated as IPv4. NAT64 (`64:ff9b::/96`) and 6to4 addresses stay IPv6 keys; an attacker
  cannot choose them, so this is correct.

**Keep-alive caps (focus 3).**

- Request cap 3: a burst of 10 pipelined `GET`, 10 HTTP/1.0 `Connection: keep-alive` requests ending in
  `404`, and 10 chunked `POST` each get exactly 3 responses, then the connection is closed. Error responses
  count. The counter is incremented when hyper has parsed a head (`server.rs:528`), so no request type skips
  it.
- Age cap 1 s with a request every 300 ms: 4 served, closed at 1.21 s. A partial head started at 0.8 s is
  cut at 5.8 s (`header_timeout_ms`), and a silent fresh connection at 5.0 s. Both are inside the bound of
  rule 32 (`max_connection_age_ms + header_timeout_ms + request_timeout_ms + 1,000 ms`). See I-3.

**R-1 (focus 4).** The list matches Linux `accept(2)`: the eight pending network errors it says to treat
like `EAGAIN`, plus `ECONNABORTED`, `ECONNRESET`, `EINTR`, `EPERM` and `ETIMEDOUT`. Each of them, except
`EPERM` in one case (L-3), removes the failed connection from the queue, so the retry makes progress.
Everything else, including an error without an `errno`, backs off 50 ms. The log line for the retried class
is throttled to one per 60 s with a count of suppressed events, and carries the OS error text only, never
an address (`server.rs:217-219`, `client.rs:181-190`).

**Profiles (focus 5).** Precedence is as rule 36 states (`config.rs:538-552`, `794-835`); constraints are
checked on the effective values after the profile is applied (`config.rs:635`), so an override that breaks
a constraint with a profile value stops the start-up. Unknown keys, unknown `SBTP_RELAY_*` variables and
out-of-range values stop the start-up; an unknown variable is reported by name, never by value. The
per-setting log prints integers, the listen address, `data_dir` as given, CORS origins and CIDR blocks: no
secret exists among the settings, and no path other than `data_dir` is logged on success. On failure the
message contains the configuration file path and, for a TOML syntax error, the offending line of that
file; both come from the operator and go to the operator's log.

**Supply chain and hygiene.** No change to `Cargo.toml`, `Cargo.lock` or CI files. On the scratch copy:
`cargo test -p sbtp-relay` 59 passed, `cargo clippy --all-targets -- -D warnings` clean,
`cargo deny check` green (advisories, bans, licenses, sources).

## Findings

### L-1 (low): a non-IP `X-Forwarded-For` entry silently collapses every proxied client onto the proxy key

`crates/sbtp-relay/src/client.rs:95-99`.

**Scenario.** A proxy in `trusted_proxies` writes its peer as `ip:port` or `[v6]:port` (Azure Application
Gateway and IIS ARR do; some proxies write `unknown` or an obfuscated identifier). Every request then falls
back to the proxy's address. Measured: 8 requests in flight with `203.0.113.N:4711` (8 different clients),
then a ninth client with `198.51.100.200:1` gets `429`, and so does a request without the header. The whole
relay serves 8 requests at a time through that proxy, and in 1c every client shares one token bucket.

**Risk.** Not triggerable by a client behind a proxy that appends a bare address (Caddy, nginx, HAProxy):
the fallback needs the proxy itself to write the bad entry. It fails closed, which is the right direction.
The problem is that it is silent: the operator sees `429` under light load and nothing in the log.

**Fix.** Keep the fallback. Add a throttled warning (the existing `Throttle`) when the fallback is taken
because an entry did not parse, naming the setting and rule 42, without logging the value. Decide in the
ADR, before 1c, whether `ip:port` and `[v6]:port` are accepted (parse as `SocketAddr` on failure of the
`IpAddr` parse); both forms are unambiguous and proxy-written. State in `deploy/` that the proxy must write
a bare address.

### L-2 (low): loopback is trusted by default, so a TCP-level forwarder on the host hands the key to the client

`crates/sbtp-relay/src/config.rs:574` (default `127.0.0.1/32`, `::1/128`), ADR 0018 rule 20.

**Scenario.** The relay keeps its defaults and is published through something that forwards TCP without
writing `X-Forwarded-For`: `ssh -R`, `socat`, `stunnel`, nginx `stream`, HAProxy `mode tcp`. Every remote
client then arrives from loopback, connections are not counted, and the client writes the header itself.
Measured: 31 requests in flight with 31 different `2001:db8:N::1` values through loopback, 31 served. The
per-client bound and, in 1c, the token buckets are bypassed, and `rate_limit_max_clients` entries can be
created at will.

**Risk.** Requires a deployment that rule 42 already forbids (the proxy MUST set or append the header). The
default is an accepted ADR decision and is right for Caddy on the same host.

**Fix.** Documentation in `deploy/`: with a TCP-level forwarder, set `trusted_proxies = []`. Optionally, a
start-up note when `trusted_proxies` is at its default and `listen` is loopback, saying that everything
local is trusted to write `X-Forwarded-For`.

### L-3 (low): R-1 residual, persistent `EPERM` spins; the back-off path logs without a throttle

`crates/sbtp-relay/src/server.rs:147-170` and `213-221`.

**Scenario A.** `EPERM` is in the retried-at-once list. When it comes from a seccomp filter that answers
with an error number (systemd `SystemCallFilter=` with `SystemCallErrorNumber=EPERM`) the error is
persistent and the pending connection is not removed from the queue. tokio does not clear readiness on an
error other than `WouldBlock`, so the loop retries at once: one core at 100 %, one log line per minute.
Not triggerable from the network; it needs a wrong unit file, and the relay serves nothing in that state
anyway.

**Scenario B.** The back-off branch prints `accept failed, pausing 50ms` on every failure: 20 lines per
second for as long as the condition lasts. On Linux the open-file check at start-up makes `EMFILE`
unlikely. On other targets the check is skipped (`config.rs:964-967`): profile `large` needs 4,176
descriptors against a macOS default soft limit of 256, so an attacker who holds 256 connections keeps the
relay in `EMFILE` and the log grows by about 1.7 million lines per day.

**Fix.** One guard covers both: count consecutive failed accepts and back off once the count passes a small
number (16), whatever the error; reset on success. Route the back-off message through `Throttle` as well.

### L-4 (low): IPv4-mapped CIDR blocks are accepted and never match

`crates/sbtp-relay/src/config.rs:223-241` and `263-270`; `crates/sbtp-relay/src/client.rs:61-64`, `69-73`.

**Scenario (by reading).** The operator writes `trusted_proxies = ["::ffff:10.0.0.0/104"]` (a dual-stack
listener shows peers in that form in other tools). The block parses. Every address is normalised to IPv4
before the test, and an IPv6 block never contains an IPv4 address, so the proxy is not trusted. Result: the
proxy is one direct client bounded at 8 connections. The same holds for `rate_limit_exempt`: the exemption
is silently absent.

**Risk.** Fails closed; the rule 29 warning gives a hint in the first case, nothing in the second.

**Fix.** Reject a block inside `::ffff:0:0/96` at start-up with a message that gives the IPv4 form (rule 7:
nothing is adjusted), or convert it at parse time and log the converted value.

### L-5 (low): ordering risk for the 1c token bucket

`crates/sbtp-relay/src/server.rs:305-319`; `crates/sbtp-relay/src/api.rs:113-120`.

Rule 30 says the request takes its token first, then the in-flight count. Today the count is taken in the
hyper service function, before the router, and the refusal is carried by an extension. A limiter written
as a router middleware in 1c would run after the count. Consequences if that happens:

1. An over-bound request is refused before it pays a token, so a client at its bound can send `429`
   traffic that the rate limit never sees.
2. A request refused by the limiter holds an in-flight slot until its `429` is flushed.
3. The limiter would derive the client key a second time from `ConnectInfo(peer)` and the headers. Two
   derivations can drift (L-1 is one example of a rule that must be identical in both).
4. Rule 31, "requests attributed to the overflow key share one count", has no implementation yet, because
   the overflow key does not exist before the limiter.

**Fix for 1c.** Take the token at the same place as the count, in the service function, in the order token
then count, from one `ClientKey` computed once. Pass that key to the handlers in an extension (the `PUT`
per-client bound of ADR 0018 rule 18 needs it too) and remove the second derivation from the plan. Add a
test: a client at its in-flight bound exhausts its bucket.

### L-6 (low): `max_connections_per_client` may equal `max_connections` without a warning

`crates/sbtp-relay/src/config.rs:718-721`.

**Scenario (by reading).** `profile = "large"` with `max_connections = 32` in the file gives
`max_connections_per_client = 32` from the profile. The constraint `≤` passes. One client key may hold
every slot: F-2 is open again and nothing says so. The same holds for `max_connections = 8` under `small`.

**Fix.** A start-up warning (`Settings::warnings`) when `max_connections_per_client * 2 > max_connections`,
naming both settings and their sources. A hard constraint would be an ADR change.

### L-7 (low): a very broad `trusted_proxies` block is accepted without a warning

`crates/sbtp-relay/src/config.rs:890-902`.

**Scenario (by reading).** `trusted_proxies = ["0.0.0.0/0"]`, or a private /8 on a relay that listens on
that network. Every IPv4 peer is trusted: connections are not counted at accept, and a client that writes
an IPv6 address in `X-Forwarded-For` chooses its key, as in L-2.

**Fix.** A start-up warning for a block shorter than /8 (IPv4) or /16 (IPv6), and a hard error for a
prefix of 0.

## Informative points

**I-1: residual of F-2.** The bound is per key. On a relay reached directly, 4 IPv4 addresses, or 4 of the
256 /64 blocks of a residential /56, hold the 32 slots of `small` with the keep-alive pattern of F-2; the
age and request caps make the attacker reconnect every 300 s and no more. Behind a proxy that buffers
request heads the attack does not reach the relay: idle client connections stay at the proxy, and a relay
connection is held only for a request in flight. This is the design of ADR 0018 rule 20 and ADR 0019 point
10 ("not a defence alone"); `client_ipv6_prefix` can be lowered to 56 or 48. It confirms the standing rule:
no direct exposure.

**I-2: separate tables for direct and proxied counts (focus 2).** A client could hold 8 direct connections
and 8 proxied requests only if it reaches the relay both directly and through the proxy, which means the
relay port is exposed next to the proxy. In the documented deployment the direct table holds nothing but
untrusted local peers. One table would also be wrong in the other direction: an idle direct connection and
a request in flight are different units. The choice is acceptable; a line in the ADR would close the
silence of rule 31.

**I-3: the age cap does not shorten the fresh and head phases (focus 3).** Acceptable. The age is checked
when a response is built and when the idle phase starts (`server.rs:479-492`); a connection that is silent
or inside a head is already bounded by `header_timeout_ms` (5 s by default against an age of 300 s). The
total is the bound written in rule 32. Shortening the head phase at the age would cut a legitimate request
that started just before it. No interaction with the timers was found: the pipelined branch
(`server.rs:549-552`) serves the next request with `Connection: close`, and the other branches enter idle
with `min(idle_timeout, age left)`. One consequence to know: a connection that reaches its age while idle
is closed without notice, so a proxy that sends a request at that instant sees a reset, at most once per
connection per `max_connection_age_ms`. Rule 33 already states that every request is safe to repeat.

**I-4: review range.** `main` moved after the branch point (`cdc4670` applied the ADRs to the spec), so
`git diff main..3fc75af` shows reverts of `docs/spec/`, two ADRs, the VM spec and the implementer
prompt. They are not in the branch: `git diff main...3fc75af` touches only `crates/sbtp-relay/`. Merge or
rebase; do not apply the two-dot diff as a patch.
