- Date: 2026-11-19
- Scope: `git diff main...b400254` (branch `feat/relay-adr0020`, one commit), crate `sbtp-relay`:
  `client.rs`, `config.rs`, `lib.rs`, `server.rs`, `tests/http.rs`, `tests/startup.rs`
- References: ADR 0020 (accepted), `docs/security/2026-11-19-relay-adr0019.md` (L-1 to L-7),
  `docs/security/2026-11-19-relay-m1a.md` (R-1, F-6)
- Method: reading of the diff and of the library code it relies on (tokio 1.54.1, hyper 1.12.0,
  axum 0.8.9, tower-http 0.7.1, http 1.5.0, from the local registry); the branch's tests and extra attack
  tests run on a scratch copy exported with `git archive` (nothing checked out, no worktree touched)

## Verdict

**Mergeable.** The commit implements ADR 0020 as written, closes L-1 to L-7 and R-1 as far as they are in
scope, and adds no panic path and no dependency. No finding blocks the merge.

One finding is **medium** and is not a regression: M-1 exists on `main` in the same form, and it comes
from a sentence of ADR 0020 rule 7 itself, which the code follows. It needs an ADR amendment (owner's
decision) and a change of about ten lines. It **must be fixed before milestone 1c** (token buckets) and
before a relay is published behind a proxy, because the limiter of 1c inherits the same key.

| Id | Severity | Subject |
|---|---|---|
| M-1 | medium | A client behind an appending proxy moves itself onto the proxy key with one non-ASCII byte |
| L-1 | low | The `OPTIONS` relabel is sound today but depends on layer order, with no test that pins it |
| I-1 | info | "Before routing" is not exact: the layers run after path matching; a `429` may carry `Allow` |
| I-2 | info | A refused preflight fails in the browser whatever its headers; the CORS headers on it change nothing |

## Findings

### M-1 (medium): one non-ASCII byte moves a proxied client onto the proxy key

File: `crates/sbtp-relay/src/client.rs`, `ClientPolicy::forwarded_client` (lines 162 to 177 at `b400254`):

```rust
let Ok(list) = line.to_str() else {
    return Forwarded::Unreadable;
};
```

ADR 0020 rule 7, last sentence: "A field line that contains a byte outside visible ASCII, space and
horizontal tab is one invalid element." The code does exactly that. The whole **line** is invalid, and
that includes the element the proxy wrote on it.

Scenario. The reverse proxy appends its peer to the client's value on the same line (nginx
`$proxy_add_x_forwarded_for`, Caddy, Traefik and Go's `ReverseProxy` all join with `, `). The client sends
`X-Forwarded-For: \xff`. The relay receives `X-Forwarded-For: \xff, 203.0.113.7`. `to_str` fails on the
line, the search ends as case (b), and the request is counted on the **proxy's** key, not on
`203.0.113.7`. Bytes 0x80 to 0xFF are legal in a header value for hyper and for the `http` crate (measured:
the request is served, not refused with `400`).

Measured on the scratch copy, `max_connections_per_client = 1`, loopback trusted:

| Step | Result |
|---|---|
| Client `203.0.113.7` holds one request with `X-Forwarded-For: \xff, 203.0.113.7` | accepted |
| A request with `X-Forwarded-For: 203.0.113.7` (the client's own key) | `200`: its own key is still free |
| A request without the header (a health check from the proxy host) | `429` |
| Another client whose proxy path writes `unknown` | `429` |
| Same, with `rate_limit_exempt = 127.0.0.1/32` (the overlap that rule 15 warns about): 6 poisoned requests at once, bound 1 | 6 of 6 served: the client is exempt |

What the attacker gains:

1. A second budget: `max_connections_per_client` in flight on the proxy key on top of its own.
2. Denial of service on everything that legitimately uses the proxy key (rule 10): health checks without
   the header, and every client behind a proxy path that writes an unreadable element. A health check that
   gets `429` may make an orchestrator restart the relay or take it out of rotation.
3. Full exemption when the proxy address is also in `rate_limit_exempt`. Rule 15 warns about that
   configuration but describes it as affecting requests "without a client address"; here the client
   chooses to be such a request.
4. In milestone 1c, the proxy's token buckets as well, by the same route.

This is the "client picks its own key" case of the review brief, restricted to one key (the proxy's). The
client cannot spread over many keys, and cannot move **other** clients: it only affects requests it sends
itself. The throttled warning of rule 11 is logged, with a text ("the proxy must write a bare address")
that points the operator at the wrong cause.

A proxy that adds its own field line instead of appending (HAProxy `option forwardfor`) is not affected:
the lines are read from the last one, and the client's line is never reached (measured).

Not a regression: `main` returns the peer address on the same `to_str` failure. The ADR 0019 review missed
it.

Recommended fix (needs an amendment of rule 7, last sentence):

- Split the raw bytes of each line at `,` first; an element with a byte outside visible ASCII, space and
  tab is one invalid **element**, not one invalid line. Read from the right, the proxy's own element is
  then found before the client's bytes are looked at, which is the invariant rule 9 already relies on
  ("elements to the left of the one that ended the search are not read").
- Test: `[b"\xff, 198.51.100.7"]` gives `Client(198.51.100.7)`; `[b"198.51.100.7, \xff"]` and
  `[b"198.51.100.66, 10.0.0.2\xff"]` stay `Unreadable`.
- `deploy/` (rule 12): prefer a proxy setting that **replaces** the header with the peer address when
  the proxy is the only hop (`proxy_set_header X-Forwarded-For $remote_addr`), which removes client
  bytes from the header altogether.

### L-1 (low): the `OPTIONS` relabel is sound today, and fragile

File: `crates/sbtp-relay/src/server.rs`, `admit` (lines 424 to 432); `crates/sbtp-relay/src/api.rs`,
`layered` (lines 69 to 74).

Checked, and it holds:

- Only `OPTIONS` is relabelled, and only in the branch that has just set `OverClientBound`. A direct
  connection returns before that branch (`requests?`). No other method can be relabelled, and a request
  that is not refused is never relabelled.
- `RequestClient.class` is computed before the relabel, so the request keeps its `block` class (and a
  refused `OPTIONS /sbtp/v1/query` keeps `query`).
- The relabelled request cannot reach a handler: `per_client_bound` answers every request that carries
  `OverClientBound`, and that layer wraps every route, the method fallback and the path fallback. Measured
  on `/sbtp/v1/block` (no route), `/sbtp/v1/info`, `/test/hold` and `OPTIONS *`: `429`, body
  `RateLimited`, `Retry-After: 1`, and the handler of `/test/hold` did not run.
- CORS headers on the `429` are those of a normal response (`Access-Control-Allow-Origin`,
  `Access-Control-Expose-Headers`), identical to the `429` of a refused `GET`. The preflight-only headers
  (`Allow-Methods`, `Allow-Headers`, `Max-Age`) are absent, which is correct for a refusal: nothing is
  cached by the browser.
- A preflight under the bound is unchanged: `200`, `Access-Control-Allow-Methods: GET,PUT`,
  `Access-Control-Allow-Headers: content-type`, `Access-Control-Max-Age: 86400`, allow-origin. It holds an
  in-flight slot until it is written, as rule 23 requires.

The weakness is the coupling, not the behaviour. The soundness rests on two facts that live in another
file: `per_client_bound` sits inside the CORS layer, and nothing between the two reads the method. A layer
added later outside `per_client_bound` (the limiter of 1c, the metrics and logs of ADR 0021) sees a `GET`
that never existed; a metric per method would count refused preflights as `GET`. If `per_client_bound`
were ever moved or made conditional, a refused preflight would be routed as a real `GET` and run a
handler.

Recommended, in order of preference:

1. Keep the relabel, but make it local and explicit: do it in `api.rs`, in a small layer placed directly
   outside the CORS layer, which reads `OverClientBound` and swaps the method there; `admit` only sets
   the marker. The trick then sits next to the layer it exists for.
2. Whichever place is kept: store the original method in the request (`RequestClient`, or the marker
   itself: `OverClientBound { preflight: bool }`), so that later layers and logs read the truth.
3. Add a test that fails if the order changes: a refused `OPTIONS` on a route whose `GET` handler has a
   visible side effect must not run it.

A cleaner fix without a relabel exists but departs from the letter of rule 22: answer a refused request
outside the CORS layer. For a preflight this costs nothing (see I-2), but a refused `GET` or `PUT` would
lose `Access-Control-Allow-Origin` and the browser client could not read the `429` or its `Retry-After`,
so the CORS headers would have to be written by hand, which duplicates the CORS policy. The relabel is the
smaller evil; I do not recommend replacing it.

### I-1 (info): the layers run after path matching; a `429` can carry `Allow`

`Router::layer` in axum 0.8 wraps each route and each fallback; it does not wrap the router. The comments
"before routing" (`api.rs`, `per_client_bound`) and "it is never routed" (`server.rs`, `admit`) are
therefore not exact: the path is matched first, then the layers run, then the method is dispatched.
Visible effect, measured: a refused `PUT /sbtp/v1/info` gets `429` **with `Allow: GET,HEAD`**, added by
axum's method router after the middleware. A refused preflight relabelled to `GET` on a route without a
`GET` handler (`PUT /sbtp/v1/block` in 1b) will get the same header. Harmless: no handler runs, the body
is not read, and the header reveals only the public method list. Correct the two comments; no code change
needed.

### I-2 (info): CORS headers on a refused preflight have no effect in a browser

The Fetch standard fails a preflight whose status is not 2xx, whatever its headers. The page sees a
network error and cannot read the `429` or `Retry-After`. Rule 22 ("with the error body and CORS headers")
is satisfied to the letter and is useful for non-browser clients and for consistency; it does not make
the refusal readable by a PWA. Worth one sentence in the client guidance for 1c: a failed preflight should
be retried with a delay.

### I-3 (info): element forms that are accepted

All conform to rule 7; listed so that nobody is surprised. Measured through `forwarded_client`:

| Element | Result | Note |
|---|---|---|
| `1.2.3.4:0`, `1.2.3.4:00000`, `[2001:db8::1]:080` | address | port 0 and leading zeros are "1 to 5 digits, at most 65,535" |
| `2001:db8::1:80` | `2001:db8::1:80` | an unbracketed `v6:port` is a valid IPv6 address when the address is compressed; it stays in the same /64, so the key is right |
| `0.0.0.0`, `::` | address | only a trusted proxy can write the element that is used |
| `::1.2.3.4`, `64:ff9b::102:304`, `2002:102:304::1` | IPv6 address | only `::ffff:0:0/96` is normalised (rule 8); the others are IPv6 keys |
| `1.2.3.4:65536`, `1.2.3.4:99999`, `1.2.3.4:+1`, `[::1]:80]:80`, `1.2.3.4 :80` | invalid | |
| `fe80::1%eth0`, `fe80::1%25eth0`, `[fe80::1%1]:80` | invalid | zone identifiers |
| `::ffff:01.2.3.4`, `01.2.3.4`, `1.2.3`, `16909060`, `1.2.3.4.` | invalid | |
| full-width digit, Arabic-Indic digit in the port, no-break space | invalid | (the whole line: see M-1) |

### I-4 (info): the prefix of a CIDR block accepts a sign and leading zeros

`config.rs`, `Cidr::parse`: `prefix.parse::<u8>()` accepts `10.0.0.0/+8` and `10.0.0.0/008`. Operator
input only, no bypass: the checks of rules 13, 14 and 19 use the parsed value (`0.0.0.0/+0` is refused).
Tighten to digits only when the file is next touched, for the same reason the port check does it.

### I-5 (info): rule 13 can be written around

`trusted_proxies = 0.0.0.0/1, 128.0.0.0/1` starts, with two warnings of rule 14. This is what the ADR
decided (refuse the prefix 0, warn below /16 and /32); the operator who does this has read two warnings.
No change recommended.

## What was verified and holds

**X-Forwarded-For (focus 1).** `ip:port` and `[v6]:port` give the address; empty elements and empty
lines are stepped over; several lines form one list read from the last line and from the right;
`unknown` ends the search and the forged address on its left is never used; cases (a) and (b) fall back
to the proxy key; both warnings are throttled, and neither carries a value or an address. Zone
identifiers, ports above 65,535 and signs are invalid. The header name is matched without regard to
case. `Forwarded` and `X-Real-IP` are read nowhere in the crate (`grep`, and the unit test). Apart from
M-1, I found no input by which a client behind an appending proxy changes its key: every byte it writes
is to the left of the proxy's element, and the search stops there. I found no input by which one client
moves another client's key. The cost of parsing is bounded by `max_header_bytes` and is linear.

**Accept errors (focus 3).** Read on the real loop (`serve`, lines 287 to 309). tokio's `accept` clears
the readiness of the listener only on `WouldBlock` (`runtime/io/registration.rs`), so a persistent error
of the list (`EPERM` from a seccomp filter with a connection pending) returns at once on every call: the
loop would spin without the guard. With it: `consecutive` is incremented on every failure of both
classes, reset only in the `Ok` arm, and from the 17th failure each iteration awaits
`tokio::time::sleep(1 ms)`, whose timer never fires early. At most 1,000 calls per second, for as long as
the error lasts. The pause is awaited outside the `select!`, so a stop request waits at most 50 ms
(rule 5). The permit is dropped and taken again on each iteration; none leaks. A peer cannot keep the
count high: each `ECONNABORTED` costs it one connection, and a success resets the count. Logging: one
`Throttle` per class, both branches go through `ready()`, first line at once, then one per 60 s with the
suppressed count; the line carries the operating system text only.

**Trust bounds (focus 4).** Prefix 0 in `trusted_proxies` stops the start-up from every source
(`parse_cidrs` is the only path, file and environment); accepted with a warning in `rate_limit_exempt`.
Warnings below /16 and /32, one per block; one per overlapping pair. An IPv4-mapped block with a prefix
of 96 or more is refused with the IPv4 block to write (`prefix - 96` cannot underflow). Exemption and
trust are tested on the normalised address before the /64 aggregation (`ClientPolicy::key`,
`is_trusted`), and an IPv6 block never matches an IPv4 or mapped address.

**Panic paths (focus 5).** None found in the diff: no indexing, no `unwrap` outside tests, the shifts in
`Cidr::network` are checked, the counters saturate, poisoned mutexes are recovered. `cargo clippy` on the
crate is clean under the workspace lints. No new dependency, no change to `Cargo.toml`, `Cargo.lock`,
`deny.toml` or CI.

**Tests.** The 26 tests of `tests/http.rs` and the 15 of `tests/startup.rs` pass on the scratch copy.

### M-1: closed

`forwarded_client` now splits `HeaderValue::as_bytes()` at `0x2C` and only then checks each element
(`parse_raw_element`: valid UTF-8 and every byte in `0x21..=0x7E`, space or tab). A comma byte cannot be
part of a multi-byte sequence, so the split cannot be shifted by the client's bytes. Rule 9 is unchanged:
an invalid element met first from the right still ends the search.

Measured on the scratch copy, `max_connections_per_client = 1`, loopback trusted, same attack as before:

| Step | `b400254` | `3f03b88` |
|---|---|---|
| Client holds one request with `X-Forwarded-For: \xff, 203.0.113.7`, then sends on its own key | `200` | `429`: the held request is on its own key |
| Header-less request (health check on the proxy key) during the hold | `429` | `200` |
| Another client behind a path that writes `unknown`, during the hold | `429` | `200` |
| `\xff,\x80\xfe , ,203.0.113.7:99` and `é, [::ffff:203.0.113.7]:1, 127.0.0.1` during the hold | not run | `429`: same key as the client |
| `rate_limit_exempt = 127.0.0.1/32`, 6 poisoned requests at once | 6 of 6 served | 1 of 6 served: no exemption |
| `8.8.8.8, \xff` then a trusted line (the proxy itself writes the bad element) | proxy key | proxy key, with the rule 11 warning (intended) |

A client that sends only `\xff` through a peer that does **not** append is on the proxy key, as before.
That is rule 10 and the deployment rule 17, not M-1: such a peer must not be in `trusted_proxies`.

### L-1: closed

- `admit` only calls `api::refuse`, which stores `Refused { refusal, method }` with the method as
  received. The relabel is `relabel_refused_preflight`, the outermost layer in `layered`, directly outside
  the CORS layer. It changes the method only when the method is `OPTIONS` **and** the request carries
  `Refused`. That extension type is set only by `refuse`; a client cannot supply it.
- Measured: a refused preflight gets `429`, `RateLimited`, `Retry-After: 1`, allow-origin and
  expose-headers, without the preflight-only headers, on a routed path, an unknown path and `OPTIONS *`;
  a preflight under the bound gets the unchanged `200` with the three preflight headers; refused `GET` and
  `PUT` are answered `429` with their method untouched; the handler of `/test/hold` did not run.
- `refused_preflight_layer_order` fails if the relabel moves inside the CORS layer (the answer becomes
  `200`) or if `refused` stops wrapping the route (the handler's counter moves). That is the pin asked for.

### CR5, fallback key on the proxy's exact address

Sound. `ClientKey` is now `(network, prefix)`; `proxy_key` uses /32 or /128, `forwarded_key` uses /32 or
`client_ipv6_prefix`. A real client in the proxy's /64 no longer shares a count with header-less
requests (unit test, and the logic of `key_of`). The two keys can only be equal for the proxy's own
address (IPv4, or IPv6 with `client_ipv6_prefix = 128`), and an element equal to a trusted peer's address
is stepped over by rule 9, so no client can be given that key. Exemption is still tested on the address
before aggregation in the single place `key_of`. Only trusted peers can create these keys, so the number
of entries is still bounded by the in-flight requests.

### Other changes read

- `Throttle` is lock-free (one compare-exchange decides who logs). Two threads that find the line due
  cannot both log; a clock reading older than the stored one saturates to "not due". No panic path. In a
  race the suppressed count may be attributed to the next line instead of this one; harmless.
- `is_port`: at most 5 digits, digits only, then `u16`. Same accepted set as before (empty, sign, 65536
  and six digits refused; measured through the unchanged table of forms).
- `Cidr::parse(s, zero_prefix)`: the prefix-0 refusal for `trusted_proxies` now lives in the parser and
  covers every source. `::ffff:0:0/96` in `trusted_proxies` is refused without suggesting `0.0.0.0/0`.
  The defaults go through the same parser.
- `Admission::{Direct, Proxied}` replaces the two options; a direct connection still never reads the
  header and is never marked refused.

### R-I1 (info): layers run after method dispatch too

`api.rs`, module comment: "the layers run after the path is matched and before the method is dispatched".
Measured at `3f03b88`: a refused preflight on `/sbtp/v1/info` now gets `429` with `Allow: GET,HEAD`, which
it did not at `b400254`. axum's `Router::layer` wraps each method handler and the method fallback
separately, so the method is dispatched on the request as it enters the route, before any layer. The
relabelled request therefore travels the method-fallback branch and is answered there by `refused`.

This is harmless, and slightly stronger than what the comments claim: after the relabel a refused
`OPTIONS` cannot reach a `GET` handler even if `refused` were removed (it would get `405`). Two
consequences to write down, no code change required:

- correct the comment (and the doc of `refused`: "before its method is dispatched");
- a route that one day registers an `OPTIONS` or `any` handler is still protected, because `refused`
  wraps that handler as well; the pinning test covers a `GET` route only. Add an `any` route to the test
  if such a handler is ever introduced.
