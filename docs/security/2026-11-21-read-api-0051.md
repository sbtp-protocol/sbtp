# Security review: relay read API (ADR 0051) and the replication/ingest review fixes

- Date: 2026-11-21
- Range: `origin/main` (a96c102) to `main` (e85bc8b): `5dc8a5a`, `a3c57f8`, `f60e589`, `81886ee`, `2530490`, `e85bc8b`
- Scope: `crates/sbtp-relay` (batch route, request weight, `/query` order, `head`, grouped parents, `fields=parents`,
  `read_query`), the fixes of `2026-11-21-replication-ingest-pre-push.md` (M-1, L-1, L-2, I-1, I-2), `deploy/README.md`,
  the clients (`web/src`, `examples/cli-demo`).
- Rules: ADR 0051, core spec §4.

## Verdict

**OK to push and to release `relay-v0.2.0`.** There is nothing critical, high or blocking on the relay side. The batch route,
the weights and the new `/query` forms hold up against hostile input, and the review fixes are correct.

There is one **medium** finding, and it is on the client side (web cold start, M-1). The relay image does not depend on it.
Fix it before anyone relies on the web client's subgraph load across several relays. Everything else is low or info.

## End-to-end result (real relay, not a fake)

Setup: `target/debug/sbtp-relay` with `SBTP_RELAY_LISTEN=127.0.0.1:18431`, a temporary `SBTP_RELAY_DATA_DIR` and the
`small` profile. `/info` returned `read_api: 2`. Twelve blocks were published with `cli-demo mine` and `publish`: two
roots, six children of root 1, three blocks with both roots as parents, and one more child published later.

- **`get` with several ids (batch):** 8 ids (7 held, 1 unknown) gave the 7 blocks verified. The unknown one was reported
  as "length 0 in POST /sbtp/v1/blocks", exit 1. With 11 held ids and `--out-dir`, 11 files were written, exit 0.
  With 301 ids, split into 256 + 45, the 6 held blocks were fetched and 295 were reported as length 0. The raw `curl`
  response for `[held, unknown]` was 130 bytes (`4 + 122 + 4 + 0`), with `Cache-Control: no-store` and chunked
  transfer.
- **Refusals:** each of these behaved as specified.
  - `Transfer-Encoding: chunked`: `400` plus `connection: close`.
  - Both `Content-Length` and `Transfer-Encoding`, sent raw over `nc`: `400`.
  - An 8,224-byte body: `413`.
  - A duplicate id: `400 InvalidParameter`.
  - `Sbtp-Replication: 1`: `cache-control: no-store` and `cdn-cache-control: no-store`.
  - CORS preflight: `GET,PUT,POST`.
- **`query --desc`:** the listing was the exact reverse of the `asc` listing (9 ids). `--desc --limit 2` paged down to
  all 9, and `head` was printed.
- **Repeated `--parent`:** the grouped asc and desc walks returned every child of each parent. The raw grouped
  response is in request order, with per-parent cursors and `head`.
  - A child published afterwards was returned alone by a poll with `--parent <id>.<head>` on both parents.
  - A forged cursor beyond `head` (desc) returned the newest block only, so it grants nothing beyond `since`.
  - A cursor from another epoch got `InvalidCursor`.
  - 33 parents, `fields` with `parent`, and `.cursor` on a single `parent` each got `400 InvalidParameter`.
- **`query --fields parents --desc`:** printed `len=` and `parents=`, and they matched the published headers.
- **Web client `Relay` (`web/src/relay.js`) under Node against the same relay:** `fetchBatch` (8 records, 7 served, not
  truncated), `queryPage` desc with `head`, `queryGroup` desc and `fields` hints all parsed correctly. This exercised
  the parsers only, not the WASM validation or the browser CORS path.
- **Relay log:** no block id, client address or query parameter appeared in any line other than the settings and the
  listen address.

## Findings

### M-1 (medium): a hostile relay can hide another relay's blocks in the web cold start, because `fields=parents` hints are merged first-wins

- `web/src/relays.js:696`: `walkAll` merges hints with `if (!hints.has(id)) hints.set(id, h)`, so the first relay in
  run order wins for each id.
- `web/src/view.js:216`: `loadDescendants` builds the parent-to-children map **only** from those merged hints. Then it
  traverses that map, and only traversed ids are fetched.

ADR 0051 says a hostile `parents` hint "can only make a client skip a block, which omitting it from the listing already
allows". That argument holds for one relay. It does not hold for the merge. Without hints, a block listed by an honest
relay B is in the union whatever relay A does. With first-wins hints, relay A takes over B's listing.

Scenario:
1. The user's relay list is `[A, B]`. A is hostile and B is honest. Both announce `read_api: 2`.
2. Block X (for example a retraction, or a moderation block) is a child of a block under the root. B lists it with its
   true parents.
3. A also lists X (its id is public, through B) with `"parents": []`, or with an unrelated parent.
4. A's hint wins. X is never reached by `traverse`, never fetched and never shown. `partial` stays `false`, so the cold
   start reads as complete.

Effect: A can silently suppress any block it knows the id of, even though an honest relay in the list serves it. That
defeats the multi-relay model (see the round-robin fix L-2 of the earlier review) for the cold-start path. The view path
(`loadView` and `refreshView`) is not affected: it uses grouped listings, merged as a union.

Fix: union the hints across relays. Keep a set of claimed parents per id, the union of every relay's `parents` for it,
or build `children` from every run's hints instead of from the merged map. A hint only causes a fetch, and the fetched
header decides what is shown (`keep` loop, `view.js:236`), so a union is safe. Its cost is bounded by
`traverseMaxVisited`. For `len`, keep the largest claimed length, which errs on the side of smaller batches. Add a test
with two fake relays where the first one lies about the parents of a block the second one lists.

### L-1 (low): a `rate_block_burst` below 64 (or a `rate_query_burst` below 4) raises the blocks-per-token ratio of a batch

- `crates/sbtp-relay/src/limiter.rs:92`: `need = min(tokens × UNIT, cap)`.
- `crates/sbtp-relay/src/config.rs:145`: `rate_block_burst` accepts 1 to 1,000,000.

Rule 7 caps the weight at the burst, so that a request can always be admitted from a full bucket. With a burst `b < 64`,
a 256-id batch costs `b` tokens, which is `256 / b` blocks per token instead of 4. Operators who lower the burst want a
stricter relay, and they get the opposite. With `b = 1` and the default 3,000 per minute, one client key can ask for
768,000 block reads per minute instead of 12,000.

This does not matter for this release. The defaults (block 200, query 20) and every profile are far above 64 and 4. The
global guards also stay in place whatever the bucket says: `block_max_readers` and the reader queue bound the concurrent
reads, and the byte ceiling bounds each response.

Fix, any one of:
- refuse `rate_block_burst < 64` and `rate_query_burst < 4` at start-up;
- or, when the weight exceeds the burst, have the batch handler serve at most `4 × burst` records (rule 3 allows a
  prefix);
- or document it next to the setting.

### L-2 (low): in the view, children listings are marked complete without asking the relays that lack `read_api: 2`

- `web/src/view.js:85` and `:148` call `walkGroupAll(..., compat: "skip")`.
- `web/src/relays.js:738` and `:790`: a skipped relay is counted neither in `completeOn` nor in `incompleteOn`, so
  `complete` can be `true`.

With a mixed list (one `read_api: 2` relay and one older relay), an item can be shown "replies N (complete)" (`app.js`)
although the older relay was never asked about that item's children. Rule 29 forbids deriving absence from a listing
that is not complete. The older relay may hold a reply, or a retraction. No relay can exploit this to forge content; it
is a wrong completeness label.

Fix: when `compat` is `"skip"`, add every skipped available relay to `incompleteOn` for each parent, or label the item
"complete on <relays>". Per-relay completeness is what rule 28 actually defines.

### I-1 (info): with one relay and a broken batch route, a bulk fetch fails instead of falling back to `GET`

- `web/src/relays.js:498` (`batchFrom`): `stopped = error`.
- `examples/cli-demo/src/commands.rs` (`batch_from`): `return` after `Err`.

A batch refusal (`400`, `404`, `405`) or a network failure ends that relay for the operation. The ids go to the next
relay, but with a single relay they end as failed. `forgetReadApi` makes the next operation read `/info` again, and that
reads `2` again, so the failure repeats. In practice this only happens if something in front of the relay alters the
batch request. One example is a proxy or CDN that forwards the body chunked: the relay then answers `400 NoLength` by
design. No security impact.

Recommended:
- After the `relay-v0.2.0` deploy, check through Cloudflare that the origin receives `Content-Length`: from a browser
  (HTTP/2), `POST /sbtp/v1/blocks` must return `200`.
- Optionally, retry the failed ids of that relay with single `GET`s in the same operation.

### I-2 (info): `redact_userinfo` does not redact a password that contains `/`, `?` or `#`

`crates/sbtp-relay/src/peers.rs:235` ends the authority at the first `/`, `?` or `#`. With
`https://user:abc/def@relay.example`, the authority is `user:abc` with no `@`, so the error prints the whole URL. A
base64 token can contain `/`.

The impact is limited: the text goes only to the operator's own start-up error, and such a URL is refused anyway.

Fix: when the text after `://` contains an `@` before the first `/` **or anywhere at all**, redact up to the last `@`.
In a `peers` value, an `@` is always a mistake.

### I-3 (info): M-1 of the earlier review moves group-throttled `PUT`s into the permit queue

`crates/sbtp-relay/src/blocks.rs:1016`: `check_groups` now runs after `relay.put.acquire()`, as recommended. This is
correct for the floor of ADR 0049 rule 3: only the `put_max_in_flight` permit holders can be uncharged.

There is a side effect. A group over its budget now waits in the `put` queue before it gets `429`, so it can briefly
take queue slots from other groups. This is bounded: the per-client `PUT` slot is taken before the queue, the per-client
`put` bucket is 20 tokens, and a refused request gives its permit back at once. It is acceptable. Nothing to change
unless measurements show queue starvation.

## Reviewed and found correct

**Relay, batch route (`batch.rs`)**
- **Request parsing.** `413` is decided from `Content-Length` before the body is read. `read_body` is also capped at
  8,192 bytes. Hyper reads exactly `Content-Length` bytes, so a client cannot send more than the length it was charged
  for. The parser refuses an empty body, a length that is not a multiple of 32, and duplicates (sorted scan).
- **Missing length.** No `Content-Length`, or any `Transfer-Encoding`, gives `400` with `connection: close`, before any
  byte of the body is read. The weight is 64 tokens, capped at the burst. Both behaviours were verified live.
- **First record.** It decides the status: busy gives `503`, an I/O error gives `500`, a missing block gives `200` with
  `length = 0`.
- **Streamed records.** Each record is read only when hyper polls for more data. The ceiling is checked before each
  record. The time budget is checked before each read starts.
- **Memory.** Hyper's write buffer is capped by `max_buf_size(max_header_bytes)` (16 KiB, `server.rs:358`; hyper 1.12
  `WriteBuf::can_buffer`). So a batch holds at most one block beyond about 16 KiB of send buffer (rule 5). A slow
  reader holds no reader thread.
- **Client disconnect.** It drops the in-flight `fetch`. Any blocking job finishes and releases its permit, exactly as
  for a single `GET`.
- **Same read path as `GET`.** Every record goes through `Relay::fetch`: the cache, or the reader permit, a blocking job,
  full validation and R1 (shared with `GET /block`).
- **Demand.** It is recorded through the demand set (once per epoch), never for a copy. The unit test covers both cases.
- **Cost per token.** About 1 MiB per 64 tokens, which is below the single `GET` worst case.

**Relay, weights and query (`server.rs`, `limiter.rs`, `query.rs`)**
- **Weight from the head only.** `request_weight` reads only the method, path and headers. `Content-Length` together
  with `Transfer-Encoding` is charged 64 tokens and refused. A huge `Content-Length` is charged the burst (saturating
  arithmetic) and gets `413`.
- **Token taking.** `take_n` takes all the tokens or none. The `Retry-After` it returns is the wait for the full amount.
- **Query weight.** It counts `parent=` pairs exactly as the parser names them: the parser does no percent-decoding,
  `%70arent` is refused, and an empty pair is refused.
- **`parent` parsing.** The id is checked before the count (the 33rd parent is refused) and before the duplicate check.
  `.cursor` is allowed only when `parent` is repeated. `fields` with `parent` is refused.
- **Cursors.** One bad cursor fails the whole request. A cursor reused across parents or orders gives only a gap
  bounded by `lower = max(since, expiry)`, in both orders. A forged cursor beyond `head` is harmless (verified live).
- **Response sizes.** The exact-size writers use their length only as a capacity hint. A wrong estimate would only
  reallocate, never corrupt.
- **Per-parent limit.** It is `max(1, ⌊max_limit / N⌋)`, which gives at most 992 entries at 32 parents. A response
  with `fields` has at most 200 entries.
- **`head`.** It discloses the time of the latest acceptance, which an unfiltered `/query` already discloses.

**Relay, index reads (`index.rs` `read_query`)**
- All listings and `head` come from one read transaction.
- **Desc ranges.** They are guarded by `from >= upper`, which gives an empty page with `more = false` (`:765`), so redb
  never receives an inverted range.
- **Asc ranges.** They are inclusive up to the parent's maximum key.
- `Position::next` saturates.
- **Corrupt rows.** `entry_fields` refuses a short row, a partial parent and more than 8 parents with `CorruptRow`,
  which gives `500` and a throttled log line with no detail.

**Review fixes**
- **M-1.** `check_groups` now runs after `put.acquire()` and before `read_body`, which matches the rule 3 floor.
- **L-1.** The blocking floor adds `replication_max_in_flight + 1` when replication runs, both in the default and in
  the validation.
- **L-2.** `check_cap` now runs after C2 and C3, so a bad signature gets `422`. A cap refusal now costs one signature
  check, which is acceptable under the `put` bucket.
- **I-1.** These are refused correctly: NAT64 local-use `64:ff9b:1::/48`; 6to4 judged on bits 16 to 47; Teredo judged
  on the server address and on the inverted client address; `192.0.0.0/24`; `198.18.0.0/15`.
- **I-2.** Redaction works for the common cases (see I-2 above for the edge case).

**Deploy:** `deploy/README.md` restricts the cache rule to `/sbtp/v1/block/` with its trailing slash and `GET`, and warns
that a `/sbtp/v1/block*` prefix would also match the batch route. That is correct.

**Clients**
- **Record parsing.** `parseRecords` and `parse_records` read the length as u32 big-endian. A length above 65,909, or
  more records than ids requested, fails the whole response. A record cut short keeps the complete records before it,
  flagged as `truncated`. An empty `200` fails. The records are copied (`slice`, `to_vec`).
- **Per-record validation.** Each record is checked against the id at its own position (`checkServed(... ask[i])`,
  `Wanted::receive` on `rest[i]`).
- **Budget and termination.** The budget is charged for every id asked, not for every id served. Each loop shrinks by
  at least one record, or stops on a failure. `walkGroup` and `GroupWalker` stop on `groupMaxRequests`, `walkMaxIds`
  or `MAX_SEEN`, on idle pages, and on restart limits.
- **Feature detection.** Only `read_api >= 2` (a strict integer) enables the new forms. A refusal of a new form makes
  the client read `/info` again on the next operation. A hostile `/info` gains at most one extra request per operation.
- **Display.** What is shown is decided by the signed headers: `realChildren` in the view, and the `keep` pass in the
  cold start. The completeness flag requires `more = false` from every relay asked and no relay backing off (but see
  L-2 for relays that are skipped). `nextPoll` moves a parent's cursor to `head` only when its listing is complete on
  that relay. Otherwise the parent keeps its own cursor.
- **Memory.** Seen sets are bounded per parent and in total (web: `groupMaxIdsPerParent`, `walkMaxIds`; CLI: 1,000,000
  ids). The hints map is bounded by `walkMaxIds × maxRelays`: about 80,000 entries of at most 8 parents each, so tens
  of MB in the worst case, and only from relays the user listed. That is acceptable.

  live. They are reviewed in code only.

  is still unmeasured.

- **Fuzzing.** No fuzzing campaign: `sbtp-core` is unchanged in this range, and the new relay parsers are small and
  covered by unit tests.
