# Supply-chain review: `redb` 4.4.0 → 4.6.0 (dependency exception)

- Review dates: 2026-11-18 and 2026-11-19. Reviewer: security reviewer.
- Scope: source diff of the two published crate tarballs, read only. Nothing from the tarballs was
  built or run. `AGENTS.md`, `CLAUDE.md` and scripts found in the 4.4.0 tarball were treated as data.
- Exception under review: `docs/security/dependency-exceptions.md`, entry of 2026-11-18 (status
  "pending").

## Verdict

**Approved with conditions.** No sign of tampering or of a supply-chain payload. The diff is ordinary
database engineering by the same sole publisher, and the bump moves no other crate. The conditions
below cover what reading alone cannot prove: on-disk compatibility with an index written by 4.4.0, and
a checksum code path that is new and not in the CHANGELOG.

### Conditions

1. **Only `redb` changes in `Cargo.lock`**, and its checksum is
   `096b1dd5ec053c9c2a5a26a93aafeadf73ebcb710ea54dc3151f17a8e20535ef`. Any other moved line in the lock
   diff voids this approval.
2. **Exact pin `redb = "=4.6.0"`, default features only.** Do not enable `experimental-api-5` or
   `experimental-niches`. Keep the default `ConcurrencyMode::ExclusiveWriter`: do not call
   `Builder::set_concurrency_mode()`. The multi-process modes are 13 days old and were not reviewed
   in depth; they also refuse `Durability::None`, which the index relies on.
3. **Upgrade test before merge.** Open with 4.6.0 an index written by 4.4.0, in two states: closed
   cleanly, and killed (`kill -9`) during writes. Check that the open succeeds, and that the row
   count, the epoch and the last position match. Reason: finding F-2.
4. **Keep a copy of `index.redb` before the first start on 4.6.0** wherever a real index exists, so
   that a rollback to 4.4.0 does not depend on the downgrade path, which is not tested upstream.
5. **Run the kill and recovery tests on the deployment CPU architecture**, not only on the
   development Mac (aarch64). Reason: finding F-1.
6. **Full test suite and `cargo deny check` green after the bump** (already a condition of the
   exception; `cargo deny check` was not run in this review, see "Not checked").
7. Update the comment above the pin in `Cargo.toml` (it still says 4.4.0 is the newest release older
   than two weeks) so that it points to the exception entry.

## `unsafe`

Lines containing `unsafe` in `src/`: 54 in 4.4.0, 40 in 4.6.0. Outside
`src/tree_store/page_store/xxh3.rs` the set is identical in both versions (`sync.rs`,
`transactions.rs`, `multimap_btree.rs`, `file_backend/range_lock.rs`, `file_backend/optimized.rs`):
nothing new and nothing modified.

`xxh3.rs` was rewritten, from upstream `xxh3` commit `e91f09d` to `f5a89eb`:

- **Narrower than before.** Raw pointer arithmetic over the input and the secret
  (`ptr.add(i)` in loops) is replaced by safe slicing (`as_chunks`, `first_chunk`, `last_chunk`).
  `unsafe` is now confined to eleven load and store helpers, each taking a reference to an array of
  exactly the size the intrinsic reads or writes, and to the six call sites of the
  `#[target_feature]` functions. Assessment: sound. The unaligned intrinsics (`loadu`, `storeu`,
  `vld1q_u8`) have no alignment requirement, and `vld1q_u64` and `vst1q_u64` receive `[u64; 2]`.
- **Call sites.** Each `unsafe { hashN_large_<isa>() }` follows a runtime feature check
  (`is_x86_feature_detected!`, `is_aarch64_feature_detected!`). Assessment: sound. NEON was called
  unconditionally on aarch64 in 4.4.0; it is now checked.
- **New AVX-512 path** (`avx512f`), chosen before AVX2 on x86. See F-1.

## Findings

No critical, high or medium finding.

### F-1 (low): new AVX-512 checksum path, absent from the CHANGELOG

File: `src/tree_store/page_store/xxh3.rs` (4.6.0), functions `hash128_large_avx512`,
`gen_secret_avx512`, `accumulate_stripe_avx512`, `scramble_accumulators_avx512`.

`xxh3_checksum()` protects every page and both commit slots. On an x86 CPU with AVX-512F, 4.6.0
computes it with code that did not exist in 4.4.0. Read lane by lane, it is the AVX2 code widened to
512 bits and looks correct. The package has no test that compares the SIMD paths with the generic
one on inputs above 240 bytes, and the only unit test of the file (`test_empty`) was removed.

Scenario: if the AVX-512 result differed from the others, an index written by 4.4.0 would fail its
checksums on first open with 4.6.0 on such a CPU (`StorageError::Corrupted`), or an index would stop
opening after a move between machines. This is a correctness risk, not an attack.

Fix: condition 5. The development Mac exercises only the NEON path.

### F-2 (low): stricter parsing of the stored allocator state

Files: `page_store/buddy_allocator.rs` (`BuddyAllocator::from_bytes`), `page_store/region.rs`
(`RegionTracker::from_bytes`), `page_store/bitmap.rs`, `page_store/page_manager.rs`
(`load_allocator_state`).

4.4.0 indexed and unwrapped. 4.6.0 validates (order count, bitmap length per order, non-zero page
count) and returns `StorageError::Corrupted("Malformed allocator state")`. This matches the 4.5.0
CHANGELOG ("reports a malformed allocator state as `Corrupted` instead of panicking").

By reading, `BuddyAllocator::new()` and `resize()` in 4.4.0 always produce what 4.6.0 accepts, and
the `RegionTracker` order count is the same constant in both. This was not executed. If an edge case
existed, an index closed cleanly by 4.4.0 would refuse to open, with no automatic repair.

Fix: conditions 3 and 4.

### F-3 (info): material changes that the CHANGELOG does not explain

- The `xxh3` rewrite and its AVX-512 path (F-1). The 4.5.0 "Performance" section mentions only
  `&str` and `String` keys.
- The development files dropped from the package through `exclude`.
- `ConcurrencyMode` is now `#[non_exhaustive]`.
- `close_database()` takes the writer lock with `try_lock_writer()` instead of `lock_writer()`. In
  `ExclusiveWriter` mode the lock taken at open is returned in both cases, so nothing changes for us.

Nothing here looks hidden: each item is a normal refactor and is commented in the source.

### F-4 (info): behaviour changes that reach the relay

- **Close waits for I/O in progress** (`io_gate` in `cached_file.rs`). Shutdown can last as long as
  the slowest read or write under way. This is the fix we want.
- **`commit()` returns `TransactionPoisoned` if a table of the transaction was leaked.** Our index
  drops every table before `commit()`, and no `mem::forget` is used. No effect.
- **A new database starts at 72 KiB** instead of about 1 MiB, then doubles. An existing file is
  untouched. Size-based tests or benchmarks on an empty index will see different numbers.
- **`Database::close()`** (4.5.0) returns the error that `drop` swallows. Recommended for the
  graceful shutdown path, as a follow-up, not as a condition.
- **`Builder::set_check_integrity_on_open()`** (4.5.0) verifies every page on open and returns
  `Corrupted` where a plain open of an externally damaged file may panic. Costs a full read of the
  file. Worth a decision in ADR 0013, not a condition.

## API changes against our use

Read from `main` (a8445ae), `crates/sbtp-relay/src/index.rs`. It calls
`Builder::new().set_cache_size(..).create(path)`, `begin_write`, `begin_read`, `open_table`,
`get`, `insert`, `range`, `last`, `len`, `set_durability(Durability::None)`, `commit`, `abort`.

- `Builder::create_file()` is deprecated since 4.5.0. **We do not call it.** `Builder::create(path)`
  is unchanged. No deprecation warning is expected.
- `WriteTransaction::print_allocated_page_debug()` is deprecated: not used.
- `Entry`, `OccupiedEntry` and `VacantEntry` keep their 4.x signatures without `experimental-api-5`:
  not used.
- `StorageBackend`, `FileBackend`: not used.
- `Durability::None` is still accepted in `ExclusiveWriter` mode. The shared modes refuse it.
- Key ordering changed only for `&str` and `String` (byte comparison, same order as before). Our keys
  are byte arrays and integer tuples: unaffected.
- `rust-version` stays 1.90.

## File-format compatibility 4.4 → 4.6

- Magic number and `FILE_FORMAT_VERSION3` are unchanged. No migration code was added.
- One new header flag, `PRIMARY_UNFLUSHED` (bit 3 of the "god byte"). It is written only in the
  `SingleWriter` and `MultiWriter` modes, never in `ExclusiveWriter`. 4.4.0 does not read that bit.
- Page, B-tree, region and allocator-state layouts are unchanged. Only their validation is stricter
  (F-2).
- Lock ranges taken by an `ExclusiveWriter` writer are the same three ranges, in the same order.
- The layout fix for a file of exactly one full region (4 GiB) changes how a size is computed, not
  how bytes are laid out.

Expected: 4.6.0 opens a 4.4.0 index, clean or after a crash, and 4.4.0 can reopen an index that 4.6.0
wrote in the default mode. Both rest on reading and are to be confirmed by condition 3. The
downgrade direction is not tested upstream: hence condition 4.

## Consistency with the CHANGELOG

Every entry of 4.5.0 and 4.6.0 that touches the default mode was found in the diff: no fallback to
a commit slot that failed its checksum (`repair_primary_corrupted` returns `false`), a page budget
in `verify_checksum_helper` (exponential-time fix), the `<` in `layout.rs` (4 GiB fix), the I/O gate
on close, `Database::close()`, `try_begin_write()`, `set_check_integrity_on_open()`, verification of
persistent savepoint trees, the smaller initial size. The remainder of the diff is multi-process
locking (generation bytes, `LockProtocolMismatch`), error-type plumbing for the redb 5 preview, and
tests. The differences are listed in F-3.

## Not checked

- Nothing was compiled or run: no upstream test, no SBTP test against 4.6.0, no fuzzing.
- `cargo deny check` and `cargo audit` were not run against a lock containing 4.6.0. The RustSec
  page for `redb` returned 404, which suggests no advisory but proves nothing.
- Equality between the tarball and the upstream git tree at `7e54679`. Only the existence and the
  title of the commit were checked.
- The multi-process code paths (about half of the diff) were read for payloads and for `unsafe`, not
  for correctness.
- The numerical equivalence of the AVX-512 path, which needs a CPU that has it.
- The test files of the tarball (`tests/`, about 2,000 changed lines) were scanned for process,
  network and environment access, not read line by line. They are not compiled into the relay.
- `libc` and the rest of the lock: unchanged by this bump, so outside this review.
- The account security of the publisher (2FA, token scope) cannot be assessed from outside.
