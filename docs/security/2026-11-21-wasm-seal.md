# Security review: sealing in the browser (`sbtp-wasm` seal bindings, two-phase `sbtp-seal`)

- Date: 2026-11-21
- Scope: branch `feat/seal-external-signer`, `git diff main...feat/seal-external-signer` (commits
  `2a19a0b`, `d328716`, `97d7ef3`, `c21ea56`, `60b3211`): `crates/sbtp-seal/` (`seal_prepare`,
  `PendingSeal::finish`, the in-place item encoder), `crates/sbtp-wasm/` (layer 2 validation, `seal`,
  `sealPrepare` / `SealPending.finish`, `openSealed`, `EncKeyPair`, tags, `OsRng`, error mapping),
  `crates/sbtp-wasm/tests-js/smoke.mjs`, `web/README.md`, root `Cargo.toml` and `Cargo.lock`.
- Reference: `docs/spec/l2-grammar.md` §1.2 and §5 (§5.1 to §5.5, §5.9), `docs/spec/sbtp-core-v0.2.md`
  §3.2 and §3.5, ADR 0039, and the earlier review `docs/security/2026-11-21-sbtp-seal.md`.
- Method: read-only review of the diff and of the `sbtp-core`, `sbtp-l2`, `hpke`, `ed25519-dalek` and
  `js-sys` code it calls; the commands listed under "Builds and tests run".

## Verdict

**Mergeable.** No blocking, high or medium finding. The in-place encoder is byte for byte the
deterministic encoding of the grammar at every head size that a bucket can hold. `finish` verifies the
signature strictly (V1 to V6) before any HPKE work. `PendingSeal` is single use, on errors too. No caller
can pass a generator, and an entropy failure is an error, never a panic. Every open failure reaches JS as
the same `OpenFailed`. The external-signer design is sound: the two signed message families are
disjoint. The two low findings are memory residue of the same class as the earlier L-1. They concern
copies left in WASM linear memory, which only a script running in the page or a memory dump can read.
They can go to the roadmap, but L-1 also corrects a claim in the README, so fixing it before the web
client uses `sealPrepare` is cheap and worthwhile.

## What was checked and holds

**In-place item encoder (`seal.rs` `encode_item_into`, `item_len`).**
- Map head `0xa3`. Keys in the bytewise order of their encodings, which §1.2 requires: `0x63 "msg"` <
  `0x63 "sig"` < `0x64 "from"`. RFC 8949 length-first order would give the same order here, so no
  ambiguity can arise.
- Byte-string heads in shortest form: `0x40|n` below 24, `0x58 n` up to 255, `0x59` + u16, `0x5a` + u32.
  `sig` is always `0x58 0x40` followed by 64 bytes; `from` is always `0x58 0x20` followed by 32 bytes.
- `item_len` = 114 fixed bytes + head (1, 2, 3 or 5) + `msg`, with checked additions.
- The tests compare against `cbor::encode` at `msg` lengths 0, 1, 23, 24, 255, 256, 1,000 and 65,312.
  65,312 is the largest `msg` that fits the 65,429-byte plaintext exactly. The 5-byte head cannot be
  reached: an item above 65,535 bytes fits no bucket and is refused before encoding.
- `seal_output_is_pinned` proves that the single-phase output is unchanged from before the refactor.
  `two_phase_equals_seal` proves that both paths give the same output. The `Cursor` writes only through
  `get_mut` and returns `TooLong` on overflow. It cannot panic.
- The `sig` slot is written through `get_mut(sig_start..sig_start + 64)` after verification. The padding
  is never touched, so it stays `0x00`.

**Strict verification and single use.**
- `finish` rebuilds the typed message from the stored plaintext (`msg_in`) into its own buffer. It then
  calls `verify_sealed`: `check_public_key` (V1, V2), then `verify_strict` (V3 to V6). This happens
  before `hpke_seal`.
- Tests cover a flipped bit, S = L, another signer, a signature under another `recipient_id`, the
  all-zero signature, the identity point and a non-canonical `y = p`.
- `finish(self)` consumes the value, and a doctest (`compile_fail,E0382`) proves that a second call does
  not compile.
- In WASM, `finish_with` runs `self.inner.take()` before any check, so every error after argument
  decoding consumes the state, entropy failure included. A wrong-shape signature (`InvalidArgument`,
  `InvalidLength`) does not consume it, which is documented and tested. A signature can never be reused
  across two pendings, because it binds the fresh outer key.

**Secrets in `Debug`, errors and JS-visible state.**
- `PrepareRequest`, `PendingSeal`, `SealPending`, `SealedEnvelope`, `OpenedMessage` and `EncKeyPair`
  print lengths, the bucket, or public keys only. The tests check that `msg`, `from`, the recipient key,
  `recipient_id`, the outer key and the tag do not appear.
- Error messages are constants or `sbtp-l2` rule names.
- The getters expose only public values (`payload`, `tag`, `bucket`, `publicKey`, `signed`, `used`,
  `message`). The exceptions are intended: `OpenedMessage` and `exportSecret`. The ephemeral private key
  has no getter and no export.

**Ephemeral key.**
- `SealedEnvelope::sign` checks that the block carries the tag as its only parent and the envelope's
  payload, before it signs. It then sets `self.ephemeral = None`, which runs `SigningKey::drop`
  (`zeroize`) in place.
- On an error the key is kept, so the caller can retry with the right block.
- After a failed `finish`, the dropped `PendingSeal` wipes its key.
- After a successful `finish`, a copy stays behind in the `SealPending` object (L-1).

**Entropy.**
- `OsRng` implements `TryRng<Error = Infallible>`. A failed draw fills the buffer with zeros and sets a
  sticky flag. `check` then drops the result, whose secret types wipe on drop, and returns
  `EntropyUnavailable`.
- Neither X25519 nor Ed25519 key generation loops on bad randomness, so a zero fill cannot hang.
- The failure path is tested for `seal`, `sealPrepare`, `finish` and `EncKeyPair.generate`.

**Opaque `OpenFailed` and timing.**
- Steps 2, and 4 to 8, take different amounts of time. Only code on the recipient's own machine can
  measure the difference, and the recipient answers no one (§5.3).
- Only a sender who sealed to the recipient's key can produce failures after step 4, and that sender
  already knows the plaintext. At this layer the timing differences carry no information an attacker
  lacks.

**External-signer design.**
- `SIG_PREFIX` is `SBTP-v1-block-sig`, and a block message is always exactly 49 bytes.
  `SEALED_SIG_PREFIX` is `SBTP-v1-sealed-sig`, and a sealed message is always at least 114 bytes.
- The two prefixes differ at byte 8 (`b` / `s`), and neither is a prefix of the other (`consts.rs`
  test). No byte string belongs to both families, so a signature over one can never verify as the other.
- The sealed message is built in WASM by the typed builder, and the caller only receives a copy of it.
  This conforms to §5.3: "through a typed builder only, never a generic signature of arbitrary bytes".
- `from` is checked in `finish`, after the external key has signed. That costs nothing: the signature
  covers a message bound to a fresh outer key and is then discarded.
- Web Crypto Ed25519 is pure Ed25519 (RFC 8032 §5.1), and the smoke test shows it gives the same bytes
  as the in-WASM signer.
- The remaining risk is on the JS side, the same as for block signing: a page script can use a
  non-extractable key to sign anything. I-1 below covers the wrapper the web client should use.

**JS boundary.**
- Every byte argument goes through `typed` (`instanceof`, which the glue wraps in a `try`). Its length is
  checked against a cap before the single allocation.
- `allowedKinds` is read with one `typeof` check (`as_string`), so the glue never reads an array-like or
  runs a `length` getter on it.
- `sealPrepare` returns a class rather than a plain object, so no property setter runs while WASM frames
  are live.
- Getters that run while an object is borrowed remain possible through polluted prototypes (I-2). They
  require hostile code in the page.

**No panic on input.**
- Non-test code of `sbtp-seal/src/seal.rs`, `sbtp-wasm/src/seal.rs` and `sbtp-wasm/src/l2.rs` has no
  `unwrap`, `expect`, `panic!` or slice indexing.
- The only cast, in `bucket_in`, follows an integer range check.

**Supply chain.**
- `Cargo.lock` gains two edges only, `sbtp-l2` and `sbtp-seal` on `sbtp-wasm`, both path crates inside
  the repository. The new root entry `sbtp-seal` has a path and an explicit version.
- The dev-dependency `ed25519-dalek` is already locked.
- The wasm32 normal graph is the reviewed set: `hpke` 0.15.1 without default features, `rand_core`
  0.10.1, and one `getrandom` (0.4.3).
- `cargo deny check` is green.

**Size budget.**
- `web/wasm-budget.py` (unchanged on this branch) reports 160,107 bytes gzip -9 for the default release
  module as an upper bound. That is 80 % of the 200,000-byte budget.
- The README gives 122,212 bytes after `wasm-opt`, 61 %. See I-5.

## Findings

### L-1 (low): after `finish`, the `SealPending` object keeps a stale copy of the ephemeral key and the seal metadata

- Where: `crates/sbtp-wasm/src/seal.rs:546` (`self.inner.take()`); the claims at `seal.rs:501` ("wiped on
  `finish` or `free()`") and `crates/sbtp-wasm/README.md` ("the ephemeral Ed25519 key and the encoded
  plaintext of a `SealPending` (also wiped by `finish`)").
- Scenario: `Option::take` copies the `PendingSeal` bits out of the `WasmRefCell` heap cell and writes
  `None`. `Option<PendingSeal>` uses a `Vec` pointer as its niche, so writing `None` overwrites only that
  word. The 32-byte ephemeral secret, `from`, `recipient_x25519`, `recipient_id` and the tag stay in the
  cell.
- Nothing wipes that copy later. `free()` drops `None`, which runs no destructor, and deallocates without
  zeroing. The copy therefore stays until the allocator reuses the memory.
- The plaintext and the signature message are separate `Zeroizing` heap buffers moved by pointer, so
  they are wiped correctly. The `signBlock` path is also correct, because assigning `None` drops the key
  in place.
- An attacker who can read the WASM linear memory gets a copy of a key that may still be unused. This
  means an injected script that re-imports the glue module and reads `memory.buffer`, or a memory dump.
  With it, the attacker can sign other blocks under the outer `PubKey`: linkable decoys, or the same `enc`
  and `ct` re-filed elsewhere, which fails `aad` at the recipient. The attacker also learns the sender's
  identity and the recipient, which §5.9 keeps from everyone but the recipient. The impact is low
  because such an attacker can usually read the live objects too.
- Fix: keep the ephemeral key at a fixed heap address from creation to drop. Use
  `ephemeral: Box<SigningKey>` in `PendingSeal` and `Sealed`, and `Option<Box<SigningKey>>` in
  `SealedEnvelope`, so that moves copy only a pointer and `SigningKey::drop` wipes the one heap copy.
  Alternatively, in `SealPending`, box the pending state, `inner: Option<Box<PendingSeal>>`, together with
  the boxed key. Then correct the two documentation claims, or state the residue as best effort, as the
  module documentation already does for stack moves.

### L-2 (low): the bindings' byte getters and `validateL2Payload` leave plaintext copies in freed WASM heap

- Where: `crates/sbtp-wasm/src/seal.rs:562-564` (`SealPending.message`, which contains `msg`), `:435-437`
  (`OpenedMessage.msg`), `:449-451` (`OpenedMessage.kind`); `crates/sbtp-wasm/src/l2.rs:139`
  (`bytes_in` into a plain `Vec`) and `:68-71` (`rawBody`, plain `Vec`, cloned by the getter).
- Scenario: a getter returning `Vec<u8>` or `String` allocates a copy in WASM memory. The glue copies it
  into JS and then calls `__wbindgen_free`, which does not wipe. Each read of `pending.message` or
  `opened.msg` therefore leaves one freed plaintext copy in linear memory.
- The natural next step after `openSealed` makes it worse. Running the kind's checks (§5.3 step 10)
  through `validateL2Payload(new Uint8Array(0), opened.msg)` copies the plaintext twice more, into the
  input `Vec` and `raw_body`, and neither copy is wiped.
- The README's sentence "no freed buffer of its own holds `msg`" is true for `sbtp-seal` only. The same
  attacker as in L-1 gets past plaintexts after the application has freed every object.
- Fix:
  - Return `js_sys::Uint8Array::from(&self.msg[..])` (and the same for `message`), as `exportSecret`
    already does. That copies straight from the `Zeroizing` storage into a JS buffer, with no
    intermediate WASM allocation.
  - Expose the opened message's body on `OpenedMessage` itself, from the already validated `Payload`,
    so that applications do not round-trip it through `validateL2Payload`. Otherwise, make the input
    and `raw_body` of `validateL2Payload` `Zeroizing`.
  - Add to the README list of "cannot be wiped" that a plaintext passed to `validateL2Payload` is copied.

### I-1 (info): the web signing wrapper for sealed messages is not yet written

- Where: `web/src/keys.js` signs only `signingMessage(block)`, which is correct today. The seal path
  is not wired into the web client on this branch.
- Point: §5.3 forbids a generic signature of arbitrary bytes. The bindings comply, but Web Crypto
  `sign` does not distinguish what it signs.
- Fix: when the web client adopts `sealPrepare`, add one function, for example
  `signSealed(identity, pending)`, that takes a `SealPending`, never raw bytes. Before signing,
  it checks that `pending.message` starts with the 18 bytes `SBTP-v1-sealed-sig` and is at least
  114 bytes long. The page should have no `sign(bytes)` helper that accepts anything else.

### I-2 (info): JS code can still run while a key object is borrowed, through polluted prototypes

- Where: `crates/sbtp-wasm/src/lib.rs:92-113` (`length` getter and `copy_to` on typed array
  arguments); `crates/sbtp-wasm/src/error.rs:148-152` (`Error.name` is assigned with a property set).
- Scenario: `seal(sender, ...)`, `openSealed(key, ...)` and `SealPending.finish` hold the wasm-bindgen
  borrow of the key object while they copy arguments and while `?` builds the JS `Error`.
- A script can make JS code run at those points:
  - by defining an own `length` accessor on a `Uint8Array` instance, or replacing
    `%TypedArray%.prototype.length`;
  - or by replacing `Error.prototype.name` with an accessor.
- If that code throws, the exception unwinds through the WASM frames without running destructors. The
  object stays borrowed, `free()` then fails, and the key is never wiped.
- The README gives this hazard as the reason `allowedKinds` is a string and `sealPrepare` returns a
  class, but these two paths remain open.
- This needs hostile code in the page, which can call `exportSecret()` directly, so the practical
  impact is nil.
- Fix: none required. Optionally:
  - build errors without a property set, for example a static JS helper imported with
    `#[wasm_bindgen(catch)]`, or an exported error class;
  - state in the README that a polluted realm voids the wipe guarantees.

### I-3 (info): `allowedKinds` fails closed, silently, on a malformed list

- Where: `crates/sbtp-wasm/src/seal.rs:701-717, 834-838`.
- Point: the design is sound. A kind matches `[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+` (§2.5), so neither
  a space nor a comma can occur inside one, and an empty token is dropped.
- A typo such as `"app.note;app.reply"`, a tab or a newline is treated as one unknown kind. Every
  block then fails with `OpenFailed`, which the application is told to ignore silently. This is safe,
  because it always errs toward not opening, but hard to debug.
- Fix: optionally, check each token against the kind syntax and throw `InvalidArgument` (an argument
  shape error, not an open failure). That would not weaken the opacity of `OpenFailed`.

### I-4 (info): the key rotation loop runs in JS, which differs slightly from the in-crate key order

- Where: `crates/sbtp-wasm/src/seal.rs:807-818` ("call it for each, newest first, and keep the first
  success").
- Point: with several keys, `sbtp_seal::open` stops at the first key that HPKE-opens. If a later step
  then fails, it rejects the block.
- The JS loop goes on to the next key after any `OpenFailed`. ChaCha20Poly1305 is not key-committing,
  so a sender who knows two of the recipient's public keys could build one ciphertext that opens under
  both. The loop can then accept the second plaintext where the crate would have rejected the block.
- That sender could have sealed the second plaintext directly to the second key, so the divergence gives
  no attacker any gain.
- Fix: none required. Optionally, accept several `EncKeyPair`s in one call once there is a safe way
  to pass them.

### I-5 (info): size figures differ between the two READMEs

- Where: `web/README.md:28-30` (237,091 bytes raw, 119,069 gzip) and `crates/sbtp-wasm/README.md:32`
  (244,078 bytes raw, 122,212 gzip).
- Point: the web figures probably predate the two-phase commit. Both are well within the budget. The
  upper bound measured here is 160,107 bytes gzip, 80 %. About 40 KB of headroom remains on the
  conservative measure, so the next feature added to the default module should be measured before
  merge.
- Fix: update `web/README.md` from the same measurement.

### I-6 (info): the `sbtp_seal::application_tag` rustdoc lacks the framing SHOULD

- Where: `crates/sbtp-seal/src/tag.rs:30-32`.
- Fix: copy the sentence of the JS binding: inputs SHOULD be of fixed length or length-prefixed by the
  application's specification.

## Builds and tests run

- `cargo test --workspace`: all suites pass. `sbtp-seal`: 39 unit tests and 1 doctest (the single-use
  `compile_fail` doctest). `sbtp-wasm`: 28 unit tests and the vector replay.
- `cargo clippy --workspace --all-targets -- -D warnings`: clean. `cargo fmt --all --check`: clean.
- `cargo deny check`: advisories, bans, licenses and sources ok.
- `cargo build -p sbtp-wasm --target wasm32-unknown-unknown --release`, and `--no-default-features`:
  both build. `cargo build -p sbtp-core --no-default-features`: builds.
- `wasm-bindgen` 0.2.130 `--target nodejs`, then `node crates/sbtp-wasm/tests-js/smoke.mjs`: 16 checks
  passed. They include Web Crypto Ed25519 with a non-extractable key signing `pending.message`, the
  opaque open failures, single use, and the size budget.
- `python3 -I web/wasm-budget.py` on the release module: 160,107 bytes gzip -9, under 200,000.

## Not checked

- Heap residue in practice (L-1, L-2): inferred from the `Option` layout and the wasm-bindgen return
  convention, not measured in a memory dump.
- Behaviour in real browsers: only Node's Web Crypto was used. `wasm-opt` was not run, so the 122,212
  figure is the README's.
- The web client's future seal integration and its CSP (not on this branch).
- The CLI's use of `sbtp-seal` and its RNG (out of scope).
- Constant-time behaviour of `verify_strict` and of the AEAD under a WASM JIT (best effort, as in the
  earlier reviews).
