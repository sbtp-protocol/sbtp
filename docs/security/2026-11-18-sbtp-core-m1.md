## Low-severity findings

### L-1. Tests run against an `ed25519-dalek` built with more features than the shipped one

- Where: `crates/sbtp-core/Cargo.toml:24`.
- Fact: `cargo test` compiles `ed25519-dalek` with `digest, fast, hazmat, signature, zeroize`. Every
  shipped build compiles it with `fast, zeroize`. The 90 tests, the `S + L` vector included, therefore
  never run against the exact library configuration that a relay or a browser runs.
- Scenario: a future `ed25519-dalek` release gates part of the verification path on `digest` or `hazmat`.
  The tests keep passing; the shipped binary behaves differently.
- Today this is harmless. I read every `cfg` of 3.0.0: `VerifyingKey::from_bytes`, `is_weak`,
  `to_edwards`, `verify_strict`, `RCompute` and `check_scalar` do not depend on `digest` or `hazmat`.
  `digest` only adds the prehashed (`Ed25519ph`) entry points and trait impls; `hazmat` only makes
  `raw_sign` and `StreamVerifier` public. `sbtp-core` itself calls none of them outside tests.
- Is the dev-only exposure acceptable: **yes**, for this milestone. See point 6 for the feature trees.
- Fix (before the end of Phase 1): freeze the mixed-order blocks as JSON vectors in
  `docs/test-vectors/`, generate them with a separate tool (`publish = false` crate or an example that is
  the only place enabling `hazmat`), and drop line 24. The test suite then runs on the shipped feature set.
  The relay self-test of rule 16 covers the remaining gap at run time.

### L-2. `mine` and `BlockBuilder::build` can loop for 2^64 attempts

- Where: `crates/sbtp-core/src/builder.rs:238-240` (`mine(&mut out, difficulty, u64::MAX)`) and
  `builder.rs:286-313`.
- Scenario: a caller passes a difficulty taken from a relay response or a user field. With `d > 256` no
  identifier can match and the loop runs 2^64 BLAKE3 hashes; with `d = 60` it is merely years. In the WASM
  runtime this freezes the tab; a hostile relay that announces an absurd difficulty stalls every client
  that trusts it.
- Impact: sender side only, self-inflicted or relay-inflicted client stall. No effect on a validator.
- Fix: return `PowNotFound` at once when `difficulty > 256`; give `build` a `max_attempts` parameter (or
  remove mining from `build`); the WASM binding must mine in bounded slices and apply its own ceiling on
  the difficulty it accepts from a relay.

### L-3. Proptests do not reach the checks after F8; no fuzz target yet

- Where: `crates/sbtp-core/tests/properties.rs:78-87` and `:91-110`.
- Fact:
  - `arbitrary_bytes_never_panic`: random bytes carry the magic and version with probability 2^-24. All
    256 cases stop at F1 or F3.
  - `structured_garbage_never_panics`: `len` is drawn from 0 to 70,000 independently of `N` and `P`, so the
    exact length needed to pass F8 comes up about once in 70,000 cases; 256 cases never reach F9, R1, C1,
    C2 or C3. The constant fill also makes all parents identical, so any case with `N ≥ 2` that did pass F8
    would stop at F9.
  - Only `mutated_valid_block_never_panics` reaches the cryptographic checks, from one fixed block.
  - No property covers a well-formed frame with arbitrary PubKey and signature bytes.
  - `fuzz/decode_block` does not exist yet (the roadmap (not published), open item; ADR 0004 "Security" requires it).
- Risk today: low. The scratch tests listed under "Method" cover that space and found nothing. The point
  is that the committed suite would not catch a regression there.
- Fix (before the end of Phase 1): derive `len` from `N` and `P` in the structured test (exact, ±1, ±64),
  fill with random bytes; add the "arbitrary PubKey / `R` / `S` in a valid frame" property; add the fuzz
  target with the "no panic, accepted block re-encodes identically" oracle of ADR 0004.

### L-4. Mixed-order tests classify blocks with the function under test

- Where: `crates/sbtp-core/tests/validation.rs:711-760`.
- Fact: `mixed_order_blocks` sorts blocks into "accepted" and "rejected" by calling `validate`, then the
  two tests assert that accepted blocks validate and rejected ones return `InvalidSignature`. The claim in
  the test name, "valid only under the cofactored equation", is never checked, and neither is the rule
  "accepted if and only if `k ≡ 0 (mod 8)`". A verifier that reduced `k` wrongly, or rejected every
  mixed-order key, would only be caught by the `assert_ne!(len, 0)` lines.
- I checked the rule from outside: over 400 nonces, `validate` agrees 400 times out of 400 with
  `(SHA-512(R ‖ A ‖ M) mod L) mod 8 == 0` (47 accepted, 353 rejected). In 86 of the 400 cases the unreduced
  digest gives the opposite prediction, so the set does pin the "mod L" of V6.
- Fix: freeze a few of these blocks as vectors with the expected verdict written down (at least one
  accepted, one rejected where the reduced and unreduced predictions differ), and assert on the vectors.

### L-5. Rule 16 half done: the `S + L` vector is not frozen or exported

- Where: `crates/sbtp-core/tests/validation.rs:597-608`; ADR 0003 rule 16.
- Fact: the vector is built at test time by signing with key A and adding `L`. It is effective (point 7).
  But nothing in `sbtp-core` exposes it, so the relay and the other shipped binaries cannot replay it at
  start-up as rule 16 requires.
- Also note: `cargo test -p sbtp-core` resolves features for that package only. If another workspace member
  enabled `legacy_compatibility`, only `cargo test --workspace` (and `cargo deny check`) would see it.
  `CLAUDE.md` already requires `--workspace` before a commit.
- Fix (before Phase 2 starts): a frozen `S + L` block as a constant, and a public
  `sbtp_core::self_test() -> Result<(), SelfTestError>` that validates the unmodified block (expects `Ok`)
  and the `S + L` block (expects `InvalidSignature`). The relay, the CLI and the WASM init call it.

### L-6. API shape makes two integration mistakes easy

- Where: `crates/sbtp-core/src/lib.rs:29-34`, `verify.rs:42-46`.
- Scenarios:
  1. `parse` is public and returns a `BlockRef` with every accessor. A relay or client author who calls
     `parse` where `validate` was meant stores or displays an unauthenticated block. The doc comment says
     so, the type name does not.
  2. `validate(bytes, d, None)` on a `GET` path silently skips R1. A hostile relay then answers with
     another valid block (ADR 0003, rule 11).
  3. The shortcut of ADR 0003 rule 10 (format, PoW, lookup, then signature) cannot be written with
     `validate`; the relay will assemble `parse` + `block_id` + `meets_difficulty` + `verify_signature` by
     hand, and may reorder or drop a step.
- Fix (can wait for the first relay PR, must be decided before it): two entry points with explicit names
  (`validate_submitted(bytes, d)` and `validate_requested(bytes, d, &id)`); a staged form that keeps the
  order in the types (`parse` → `PowChecked` → `ValidatedBlock`), so that storage functions accept only
  `ValidatedBlock`; consider renaming `BlockRef` to `UnverifiedBlock`.

## Points checked with no severity (info)

### 1. Panic, overflow and out-of-bounds paths in `parse` and `validate`: none found

- `block.rs:127-219`: no indexing, no `unwrap`. Every read goes through `zerocopy` prefix casts,
  `split_at_checked`, `try_from` and `get`. `clippy::indexing_slicing` and `clippy::unwrap_used` are on and
  clippy is clean.
- Arithmetic before F5: none on `N`. F1 and F2 compare `len` with constants; the header cast needs 52
  bytes and F1 guarantees 118.
- Arithmetic after F5: `block_len(count, 0)` with `N ≤ 15` is at most 598; `block_len(count, payload_len)`
  is at most 66,133. Even with `N = 255` the helpers of `layout.rs` peak at 73,813, far below `usize::MAX`
  on 32-bit targets (wasm32 included). On a 16-bit target `MAX_BLOCK_LEN` does not fit in `usize` and the
  crate fails to compile, which is the safe outcome.
- `block.rs:205`: `len - SIGNATURE_LEN` cannot underflow (`len ≥ 118`).
- `check_distinct_parents` (`block.rs:222-235`): at most 105 comparisons, no allocation.
- `block_id.rs:46-57`: the counter tops out at 256.
- `verify.rs`: fixed-size arrays only. `Signature::from_bytes` is infallible; the library code behind
  `from_bytes`, `is_weak` and `verify_strict` has no panic path on input data.
- Five error branches are unreachable (`block.rs:141`, `:176`, `:178`, `:196-203`, `:206`). They return a
  plausible variant instead of panicking, which is the right choice. Two of them would report `TooShort`
  for a buffer of 118 bytes or more; harmless since they cannot run.
- Suggestion: enable `clippy::arithmetic_side_effects` for `sbtp-core` so that the next arithmetic
  expression on a length gets a reviewer's attention. Every current site is bounded.

### 2. Check order and errors: conform to ADR 0004

- F1, F2, F3, F4, F5, F6, F7, F8, F9 in that order in `block.rs`; R1, C1, C2, C3 in that order in
  `verify.rs:48-71`. Confirmed variant by variant by the differential test.
- F6: `Truncated { expected_min: 118 + 32·N }`, Payload Len not read. F7: `expected_min` is the exact
  length. F8: `TrailingBytes { expected, len }`. Boundaries `len = 118 + 32·N − 1`, `= 118 + 32·N`,
  `exact − 1`, `exact`, `exact + 1` all checked. F2 fires before F8 at 66,134 bytes.
- F9 reports the first pair in `(first, second)` order; indices fit `u8`.
- Twelve variants, names identical to spec §2.2 (`error.rs:82-97`).
- Expensive work: `parse` hashes nothing. The single BLAKE3 pass (`verify.rs:49`) runs after F9 and is
  needed by R1 and C1. Point decompression, the small-order tests and the double scalar multiplication all
  come after C1. `mine` keys the hasher once (ADR 0002 "Cost").
- R1 uses an ordinary comparison on public data: fine.

### 3. `verify.rs` and ADR 0003 rule 13: conform

- Step 1 `VerifyingKey::from_bytes` (`verify.rs:91`), step 2 recompression
  `key.to_edwards().compress().as_bytes() != pubkey` (`:94`), step 3 `is_weak()` (`:98`), step 4
  `verify_strict` on the 49-byte message (`:119-122`). Order as in the ADR.
- The library does what the ADR states: `verify_strict` checks `S < L` through
  `Scalar::from_canonical_bytes`, decompresses `R`, rejects small-order `R` and `A`, and compares the
  recomputed `R` byte for byte.
- No path without the prefix: the only producer of the signed message is `BlockId::signed_message`
  (`block_id.rs:69-75`), used by `verify_signature` and `sign_block_id`. `Verifier::verify`,
  `verify_prehashed` and `verify_stream` are not called anywhere in `src/`. Test
  `c3_signature_over_raw_block_id_without_prefix` covers the negative case.
- `verify_batch`: not called; the `batch` feature is not enabled in any tree; `cargo deny` bans it.
- Non-canonical PubKey: 26 encodings exist; the tests cover `y + p` for `y = 0, 1, 3` and `x = 0` with the
  sign bit for `y = 1` and `y = −1`, and check through `KeyRejection` that the intended step fired.

### 4. `derive_key` and the covered range: correct

- `blake3::derive_key(BLOCK_ID_CONTEXT, hashed)` (`block_id.rs:114`) is the `derive_key` mode with a
  32-byte output. `Hasher::new_derive_key` in `mine` gives the same result (unit test).
- Context string: 27 bytes, asserted byte for byte against spec §3.1 (`consts.rs:22-29`). `SIG_PREFIX`: 17
  bytes, asserted against §3.2; message length 49.
- Range: `hashed = bytes[.. len − 64]` and `len == 118 + 32·N + P` at that point, so the range is exactly
  `block[0 .. Offset(Signature)]`. The differential test compares `hashed_bytes()` and `block_id()` with
  direct slicing on every accepted buffer.

### 5. PoW leading-zero count: correct

- Exact for every `k` from 0 to 256, at byte boundaries (8, 16, ..., 248) and inside bytes. `d = 0` accepts
  everything; `d = 256` accepts only the all-zero identifier; `d = 257` and `u32::MAX` reject everything
  with `InsufficientPow { required: d, actual }`. No shift, no subtraction, so no overflow for large `d`.

| Build | Features |

| `-p sbtp-relay -e normal,build`, `-p cli-demo -e normal,build` | `fast, zeroize` |
| `--workspace -e normal,build --target all` | `fast, zeroize` |
| `--workspace --target all` (dev edges included: test builds) | `digest, fast, hazmat, signature, zeroize` |

- `batch` and `legacy_compatibility`: absent from every tree, on `ed25519-dalek` and on
  `curve25519-dalek` (`digest, precomputed-tables, zeroize`). `deny.toml` bans them with
  `all-features = true`; I confirmed the ban fires (`feature-banned`) when the feature is added.
- Acceptable: yes (L-1). One caution: a build with `--all-targets` or a `cargo test` build unifies the dev
  features into the library. Release artefacts must come from `cargo build --release -p <crate>`, never
  from a test or `--all-targets` build.

### 7. Does the `S + L` vector prove that `legacy_compatibility` is off: yes

- With the feature on, `check_scalar` only tests the top three bits of `S`. `S + L` stays below `2^253`
  for the fixed vector, so the lax build accepts it.
- Experiment in a scratch copy with `legacy_compatibility` added to the workspace dependency:
  `c3_v3_s_plus_l_is_rejected` fails (the block validates) and the 89 other tests still pass. It is the
  only test that detects the feature, which is why L-5 matters.

### 9. Smaller notes

- `sign_block_id` (`builder.rs:351-355`) signs any 32-byte value as a `block_id`. Correct for a library.
  The WASM bindings must not expose it to page scripts: only "sign this block" after `parse`, never "sign
  this identifier".
- `sign_block` checks that the key matches the PubKey field (`builder.rs:333-335`). Good.
- Secrets: `SigningKey` is built with `zeroize`; signing is deterministic (RFC 8032), no randomness source
  in the crate; `Debug` of `BlockRef` and `Display` of `Error` print public data only. Test keys come from
  public seeds.
- `BlockRef::block_id()` rehashes on each call (up to 66 KB). Callers should keep the value from
  `ValidatedBlock::block_id()`.
- `ValidatedBlock` has private fields and a single constructor, `validate`. Good basis for L-6.

## What I could not check

- **Real `no_std` target.** Only the host and `wasm32-unknown-unknown` targets are installed. The
  `--no-default-features` build passes on the host, which proves `sbtp-core` itself does not use `std`, not
  that the dependency tree links on a bare-metal target.
- **Fuzzing.** No fuzz target exists and I did not run a coverage-guided fuzzer. The differential and
  random tests above are bounded enumerations, not a substitute.
- **32-bit behaviour at run time.** The wasm32 build compiles; I did not run the tests on wasm32.
  Arithmetic bounds were checked by reading.
- **Release-profile behaviour.** All tests ran in the debug profile (overflow checks on). I did not run
  them in release.
- **Maintainer-level supply-chain review.** I checked checksums, ages, yank status, build scripts and
  procedural macros of the shipped graph. I did not audit the full source of the 31 shipped crates, nor
  the ownership history of each crate. The 27 test-only crates were checked for age, checksum and yank
  status only.
- **Constant-time properties** of signing in `ed25519-dalek` / `curve25519-dalek`: taken on trust from
  upstream.
- **Other Ed25519 implementations.** Agreement of V1 to V6 with a third-party verifier (browser
  `crypto.subtle`, libsodium) was not tested; only `ed25519-dalek` 3.0.0 and one external recomputation of
  `k` for the mixed-order case.
- **Relay, WASM bindings, CLI, CI.** Outside this diff; they contain no code yet.
- **Authorship of the commit.** `git log` shows an author name; it is not evidence of who pushed. Check
  the forge's activity or security log if that matters for this branch.
