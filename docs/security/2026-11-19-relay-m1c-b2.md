# Security and correctness review: relay milestone 1c-b2 (limiter ordered by full time, index read failures)

- Date: 2026-11-19
- Branch: `feat/relay-m1c-b2` (commit `4eca0fd`), against `main` (`9f4da35`)
- Scope: `git diff main...feat/relay-m1c-b2`, 11 files, `crates/sbtp-relay/` only
- References: ADR 0027 (all rules and Consequences), ADR 0018 rules 21 and 35 as amended, ADR 0019
  rules 29 to 31, ADR 0012 clarification K2, ADR 0021 clarifications X1 to X4 and the rule 7 event
  table, ADR 0023, review `2026-11-19-relay-m1c-b.md` finding L-4
- Combined pass (security and correctness), per the cost discipline of `CLAUDE.md`

## Verdict

**Mergeable.** No blocking or medium finding. L-4 is resolved: no limiter operation passes over the
table any more. The work per request is one hash lookup plus at most two B-tree changes, and the
`/query` read-failure path matches K2 and X1 to X4. Four low findings and some info notes follow. None
needs a re-review. L-1 and L-2 touch the wording of ADR 0027 (rules 1 and 5) and need a short
the specification editor amendment or note. L-3 and L-4 are small code fixes for the next relay milestone.

## What was verified and holds

- **Per-request cost (ADR 0027 rule 1).** `take_at` (`limiter.rs:179-215`) does one `HashMap::get_mut`.
  For a known key it does at most one `BTreeSet::remove` and one `insert`. For an unknown key it does
  `first`, `remove`, `HashMap::remove` and `insert`. `pin`/`unpin` (`limiter.rs:220-247`) do one hash
  operation and at most one B-tree operation. No `retain`, `iter` or `len`-proportional work remains
  on any path. The only hidden linear cost is the amortised `HashMap` growth (L-2).
- **Table bound.** An insert happens only under `map.len() < max_clients`, after at most one eviction,
  so the map never exceeds `rate_limit_max_clients`. The order holds only keys of the map. It cannot
  hold more entries than the map.
- **Full-time invariant (rule 2).** `full_at` is unchanged by `refill` while the key is not full. If a
  bucket is not capped after `dt`, its wait exceeds `dt`, so the maximum shifts by exactly `dt`. That
  is why the stored order entry `(before, key)`, computed before `refill`, always matches. When all
  three buckets are capped, the key is full and its stored time is `<= now`. `per_min >= 1` is enforced
  by the setting ranges (`config.rs:114-119`), so `per_min.max(1)` never hides a non-refilling bucket.
- **Exact rule (rules 3 and 4).** Only `order.first()` with `full <= now` is evicted, and pinned keys
  are not in the order. A key that is not full or is pinned cannot be dropped. A `now` read before
  the lock (`take`, line 175) can only be stale towards the past, so eviction stays conservative.
- **Cheap eviction of legitimate keys.** It is not possible. Only full keys are dropped, and dropping
  a full key loses nothing (a new entry starts full). An attacker who wants to keep the table full
  must keep each of its keys short of full, which is the cost ADR 0027 intends.
- **Pin/unpin accounting.** The pin is taken after the count increment and before the `Slot` exists
  (`client.rs:278-295`). The unpin runs in `Slot::drop`, after the count decrement
  (`client.rs:304-319`). Every `Slot` therefore unpins exactly once, including on response-body drop
  without flush, forced shutdown, and unwinding. Both counters are commutative, so the interleavings
  of concurrent acquire and drop on one key cannot underflow or leak. An unbalanced `unpin` is a
  no-op. The two mutexes are never held together, and the limiter never calls into `Counts`, so there
  is no deadlock. A pin on `ClientKey::OVERFLOW` (a proxied request attributed to the overflow key) is
  harmless: that key is never in the map.
- **Poisoning.** Both locks ignore poisoning. No operation under the limiter lock can panic: the
  arithmetic is saturating or guarded, and B-tree and hash operations only abort on OOM. A torn
  map/order state is therefore not reachable through a panic.
- **`/query` read failure (K2, X1, X3, X4).** `query.rs:318-324` returns `ApiError::internal()`. The
  test confirms `{"error":"Internal"}`, `Cache-Control: no-store` and no `Retry-After`. The counter is
  incremented before the throttle. The event carries only `op` and `errno` (`query.rs:237-249`): no
  cursor, no parameter, no `block_id`, no error text. Nothing changes state, and the test shows the
  same cursor working afterwards. The queue-refusal path stays `503`/`shed`. A panic still ends the
  process (I-1 of the previous review), which agrees with X2 ("a panic ... is the event `panic`").
- **Removal of `msg`** from `index_write_failed` (`blocks.rs`, `pool.rs`). Rule 2 makes `msg` optional,
  and rule 7 lists `op`, `step`, `errno`, `suppressed`, so this conforms. It also removes the one place
  where backend error text, which the relay does not control, reached the log.
- **Event table test** (`log.rs`). `event_tables` parses every `| \`event\` | Level |` table. The test
  pins two tables in ADR 0021 and one in ADR 0023, so a fourth table or a reordered row fails it.
- **Startup memory figures** (`tests/startup.rs`). They match `4 × max_connections × 64` for the three
  profiles.
- **Tests run on the branch:** `cargo test -p sbtp-relay`, all green (91 unit tests plus the
  integration suites). `cargo clippy -p sbtp-relay --all-targets -- -D warnings` is clean.

## Low

### L-1. The limiter entry estimate (100 bytes) is about 1.7 times too low; ADR 0027 Consequences asked for it to be recomputed

`crates/sbtp-relay/src/config.rs:41` (`EST_LIMITER_ENTRY = 100`), used at `config.rs:1027-1028`. ADR 0027
rule 5 and its Consequences ("The per-entry size and the start-up bound of rule 35 are recomputed").

**Measurement.** I wrote a standalone program in the scratchpad, using the same types and a counting
global allocator, with no project code:

- `size_of::<ClientKey>()` = 18, `(ClientKey, Entry)` = 56, `(u64, ClientKey)` = 32.
- `HashMap<ClientKey, Entry>`: 114.0 bytes per entry at a full table (4,096, 262,144 and 1,048,576
  keys). A power-of-two bucket count at 7/8 load leaves the table just over half full at these sizes.
- `BTreeSet<(u64, ClientKey)>`: 63.6 bytes per entry after append-ordered inserts, and 53.9 after churn.
  Full times mostly increase, so leaves split at 6 of 11.
- Total: about **168 to 178 bytes per entry**, against 100 counted.

**Scenario.** The table is filled by remote clients. Distinct IPv6 /64s are cheap, and a /48 gives
65,536 keys. The process then exceeds the logged rule 35 bound by about 75 bytes × `rate_limit_max_clients`:
- default (4,096 keys): +0.3 MiB on a bound of about 13 MiB;
- `large` profile (262,144 keys): +19 MiB;
- the accepted maximum (16,777,216 keys): about +1.2 GiB, which the logged bound does not show.

The `HashMap` alone was already over 100 bytes before this branch, as L-4 noted. The branch adds the
order and leaves the figure unchanged.

**Fix.** Set `EST_LIMITER_ENTRY` to 192. Add a unit test that keeps it at or above
`2 × (size_of::<(ClientKey, Entry)>() + 1) + 2 × size_of::<(u64, ClientKey)>()`. Have the specification editor
correct the "100 bytes" of ADR 0027 rule 5 and ADR 0018 rule 35, and update the figures of the profile
table. The Linux gate measurement remains the real figure.

### L-2. `HashMap` growth is a one-off linear rehash under the limiter mutex (ADR 0027 rule 1, letter)

`crates/sbtp-relay/src/limiter.rs:147-149` (`HashMap::new()` for `map` and `pins`).

The map starts empty and doubles as it grows. The doubling that crosses 7/8 of 2^24 buckets rehashes
about 14.7 M entries (SipHash plus a 1.9 GB copy) while every limited request waits on the mutex. That
is several hundred milliseconds at the maximum setting and microseconds at the default. Capacity never
shrinks, so each doubling happens at most once per process lifetime. This is not a repeatable stall
like the L-4 sweep, but rule 1 says the work for one request "MUST be bounded by a constant or by a
logarithm", and amortised growth does not meet that literally. It needs an operator who raised the
setting and an attacker with millions of keys. The cost was the same on `main`.

**Fix (either).**
- Pre-size: `HashMap::with_capacity(max_clients)` and `BTreeSet` as is. Only the control bytes
  (1/57 of the reservation) are touched up front, and resident memory then grows with use and matches
  the rule 35 term exactly. Optionally size `pins` with `with_capacity(2 × max_connections)` as well.
- Or have the specification editor add a note to rule 1 that amortised growth up to the bound is accepted.

### L-3. Pinned keys can occupy the whole table when `max_connections` is not much smaller than `rate_limit_max_clients`

`crates/sbtp-relay/src/limiter.rs:220-247`, `server.rs:327-350`. Settings at `config.rs:96` (range of
`max_connections` up to 65,535) and `config.rs:120` (`rate_limit_max_clients` from 64).

This follows directly from the rule (ADR 0019 rule 31, ADR 0027 rule 4: an entry with a unit in
flight is never dropped). No setting constraint keeps pins from being a large share of the table.

**Scenario.**
- An operator sets `max_connections = 1024` and `rate_limit_max_clients = 64`. Both values are
  accepted.
- An attacker with 64 IPv6 /64s (a /58, cheap from most cloud providers) opens one keep-alive
  connection per /64 and sends one `/query` on each. That pins 64 entries.
- The attacker keeps the connections alive below `idle_timeout_ms` with cheap `block`-class requests.
- No key can be evicted, so every other client in the world shares the single overflow allowance for
  `/query`, while the attacker uses only 64 of the 1,024 connection slots.

With the defaults (32 connections, 4,096 keys) the attacker would need the whole connection cap first,
which is a denial of service already accepted by ADR 0018. Before this branch, a held connection did
not protect a full entry, so this is a new, configuration-dependent surface.

**Fix.** Have the specification editor add a start-up constraint to ADR 0018 rule 22:
`rate_limit_max_clients ≥ 2 × max_connections`, or at least a `config_warning` when it does not hold.
The ADR 0019 rule 31 figure "at most `max_connections` such entries" makes that constraint enough to
leave half the table evictable.

### L-4. The tests do not cover a known key taking a token while pinned; a mutation that breaks rule 4 survives

`crates/sbtp-relay/src/limiter.rs:187`, tests at `limiter.rs:438-505`.

I ran a mutation in a scratch copy (not in the repository): `if before != after && !t.pins.contains_key(&key)`
became `if before != after`. All 9 limiter tests still pass, `an_entry_in_flight_is_kept`,
`counted_units_pin_their_keys` and `many_keys_keep_the_bound` included.

In every test, keys are either pinned before their first take (insert path) or pinned after their last
take. No test has a key that is already in the map take a token while pinned. Under the mutation:

1. A pinned key is put back into the order. It can then be dropped while it has a unit in flight,
   which breaks rule 4.
2. On `unpin` the key is inserted a second time. The order then holds a stale `(time, key)` entry.
3. A later unknown key can pop that stale entry and drop the key while it is not full. Its client gets
   a fresh allowance.

The shipped code is correct. The test does not discriminate the rule it names.

**Fix.** Add a case to `an_entry_in_flight_is_kept`:
1. take for `a`;
2. `pin(a)`;
3. take for `a` again at a later time, so that its full time moves;
4. assert `consistent()`;
5. at a time after `a`'s full time, an unknown key goes to the overflow key (`a` is still pinned);
6. `unpin(a)`, then assert `consistent()` and that the unknown key now replaces `a`.

## Info

- **I-1. Narrow window between `take` and the request pin on proxied connections**
  (`server.rs:473` then `server.rs:493`). The key enters the order at `take` and is pinned a few
  microseconds later. A concurrent unknown key can drop it in between only if it is already full
  (`full_at >= now + 1` right after a take). Dropping a full key loses nothing, and the in-flight count
  lives in `Counts`, not in the entry. This does not conform to rule 4 to the letter but has no
  security effect. Taking the slot before the token would contradict ADR 0019 rule 30 ("the request
  takes its token first"), so I recommend leaving it as is.
- **I-2. The `pins` comment overstates the bound.** `limiter.rs:96-98` says "at most
  `2 × max_connections` keys". Direct connections are counted at accept and trusted ones are not.
  HTTP/1.1 carries one request in flight per connection, so distinct pinned keys are at most
  `max_connections`, as ADR 0019 rule 31 says. The memory term (`4 × max_connections × 64`) is
  therefore conservative, which is fine.
- **I-3. Operators lose the backend error text** of `index_write_failed` and of the flush failure,
  because `msg` was removed. That conforms to the specification, and `errno` remains. If diagnosis
  needs more, the variant name (`CorruptRow`, `Db`) could be added as a fixed field, since rule 11
  allows "error variant names". It is not needed now.
- **I-4. The `index_read_failed` test** relies on the 60 s throttle period (`log.rs:226`) to expect one
  line for three failures. That period is far longer than the test, so it will not flake. It does not
  exercise `op=query` with `errno` absent on the logged line (the corrupt-row case is suppressed). That
  is acceptable: the `errno` gate is the same code as for `index_write_failed`, which is tested
  elsewhere.
- **I-5.** `ClientKey` derives `Ord` only for the order. `OVERFLOW` (`0.0.0.0`, prefix 255) can never
  equal a real key. Ordering by `(time, key)` makes ties deterministic and cannot be gamed in any
  useful way: ties are broken by address, and only among full keys.
