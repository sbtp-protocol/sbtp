# Security review: relay milestone 1c-a (`feat/relay-m1c-a`, ce82d53)

- Date: 2026-11-19
- Reviewer: security reviewer (independent: diff and spec, not the author's conclusions)
- Scope: `git diff main...feat/relay-m1c-a` (`crates/sbtp-relay/`, about 1,400 insertions). ADR 0025

  by the start-up walk), `GET /sbtp/v1/query` (parsing, cursor, expiry floor, limit, reader semaphore).
- Reference: `docs/spec/sbtp-core-v0.2.md` §4, `docs/spec/architecture.md` §2, ADRs 0012, 0013, 0018,
  0019, 0021, 0023, 0024, 0025, conventions of `CLAUDE.md`.

  `Cargo.lock` are unchanged: no new dependency, so `cargo deny` was not rerun.

## Verdict

**Mergeable.** No blocking or medium finding. The `/query` handler parses hostile input without a
panic path. Every request has bounded work: at most `limit + 1` index rows, with `limit` clamped twice.
Cursor forgery gains nothing over `since`, and the epoch renewal is durable before the first orphan
insert. The low findings below can be fixed in 1c-b. They do not need a re-review.

## Blocking

None.

## Medium

None.

## Low

### L-1. The expiry floor is computed before the wait for a reader permit

`crates/sbtp-relay/src/query.rs:275-287`. `expiry_floor(q.block_ttl_ms, log::unix_ms())` is evaluated
before `q.readers.acquire().await`, which can wait up to `queue_timeout_ms` (default 1 s, up to
10 s). Scenario: a block with `received_at = now - block_ttl_ms + 1` (500 ms from expiry), request
queued behind a busy reader. The page is built about 1 s later and still lists a block that expired
while the request waited. ADR 0013 rule 14 says `/query` MUST NOT list an expired block and that the
bound is applied "when it builds a response". The effect is a small window and no exposure, because the
block is still held and `GET /block` MAY serve it until the sweeper runs. It is still a rule the code
states it follows.

Fix: read the clock inside the `spawn_blocking` closure, after the permit is held, and compute `from`
there. It is one line to move, and one test with a slow index (like `SlowQueries`) and a short TTL
would cover it.

### L-2. Interim reader design: `/query` work runs on the shared blocking pool, which is not sized for it

`crates/sbtp-relay/src/query.rs:225-228, 302-306`; `crates/sbtp-relay/src/config.rs:630-631`.

What is bounded: concurrent `/query` index calls (`index_max_readers` permits, default 2), waiters
(`index_max_queue`, default 32, with `queue_timeout_ms`), and work per call (at most 1,001 rows read and
about 70 KiB of body). The permit moves into the blocking closure, so a client that disconnects or
times out cannot raise the number of running index reads. Cancellation while queued leaves the queue
(the `Waiting` guard). Per-client concurrency is already capped by `max_connections_per_client`.

What is not: ADR 0018 rule 19 sizes the blocking pool at `block_max_readers + put_max_in_flight + 2`
by default, on the premise that index reads run on dedicated threads (rules 9-11). With this branch,
up to `index_max_readers` `/query` jobs also occupy blocking threads. When every class is busy, a
`GET /block` file read can wait in tokio's blocking queue behind a `/query` job, instead of being
isolated from it as rule 32 intends ("refuses `/query` and `PUT` before `GET /block`"). The queue stays
bounded (total permits plus 2 plus `index_max_readers`), so this is a latency coupling and not
unbounded growth. `contains` on the `PUT` path still runs inside the `PUT` permit, as in 1b. Also, a
job that has taken its permit always runs, even if its requester is gone before a blocking thread
picks it up (rule 13 asks for it to be dropped). There is no per-client `query` token bucket yet
(HOOK 1c-b), so one client within its connection allowance can keep the readers and the queue full and
make other clients' `/query` get `503`. It cannot affect `PUT` or `GET /block` beyond the coupling
above.

Assessment: acceptable for a relay that is not exposed, until milestone 1c-b. Do not expose a relay
built from this branch to untrusted clients before rules 9-13 and the `query` bucket of rule 29 are in.
If 1c-b slips, there is a cheap interim fix: add `index_max_readers` to `blocking_floor`, and to the
validation of `max_blocking_threads` (`config.rs:978-983`).

### L-3. Tests do not pin the order "renew the epoch, then insert the first orphan" (ADR 0024 rule 3)

`crates/sbtp-relay/src/store.rs:865-875`. The code is correct: the renewal is a redb commit with
default durability, which is `Immediate` in redb 4.6.0 (checked in the vendored source). It runs once,
before the first `insert`, only for an orphan that passed full validation. But no test would fail if
the renewal moved after the insert, or after the walk. `renewed_epoch_is_new_and_durable` shows that
`renew_epoch` alone is durable. `cursors_across_restarts` and the crash test in `tests/blocks.rs:578`
check that the epoch changed, not when it changed.

Fix: a test `IndexBackend` wrapper that records the order of the calls and asserts that `renew_epoch`
comes before the first `insert`. Add a second case where the walk finds only a damaged file
(quarantined, nothing indexed) and assert `epoch_renewed = false` (rule 1).

## Info

### I-1. Cursors are unauthenticated and carry the epoch in clear (by design)

`query.rs:158-205`. A cursor is `hex(epoch ‖ received_at ‖ n)`. Anyone who has seen one cursor can
forge a cursor for any position under the current epoch. This gains nothing, because such a cursor is
equivalent to a `since` (any position is reachable that way), and it cannot move `from` below the
expiry floor (`max` of the three). A cursor too far ahead returns an empty page. The epoch is a stable
64-bit identifier of the relay's index, readable by any client. That is fine: it is not a secret, and
`received_at` can be found by bisecting `since` anyway. No MAC is needed. Decoding is strict (exactly
40 lowercase hexadecimal characters, `as_chunks` and `split_first_chunk`, no indexing, no `unwrap`).

### I-2. Query-string parsing: no finding

`query.rs:95-152`. The input is read raw, without percent-decoding. Each pair is split on the first `=`.
A pair without `=` or an empty pair is `UnknownParameter`. A repeat is `RepeatedParameter`. `since`
accepts digits only and a checked `u64` parse. `limit` accepts digits only, `0` is an error, and an
overflowing value saturates and is then clamped. `cursor` is checked against its length and alphabet
before decoding. The work is linear in the URI length, which hyper's header limits already bound.
Messages are static and nothing from the client is echoed or logged. `tests/logging.rs` checks this
with the marker cursor.

### I-3. `Position::next` at `received_at = u64::MAX` goes backwards (pre-existing, not reachable)

`index.rs:76-86`: `(u64::MAX, u32::MAX).next()` gives `(u64::MAX, 0)`. A page whose last entry sits
there would return a cursor that does not move. Positions come from the relay clock, and orphans are
capped at `now` (I-4 of an earlier review), so no entry can sit there. A forged cursor there returns no
entry and `next = from`. Not exploitable; it could be noted in the `next` rustdoc.

### I-4. Shard check, then `link`: TOCTOU against a local writer only

`store.rs:579`. `check_shard` uses `symlink_metadata`, then `hard_link` resolves the path again. A
process that can swap `blocks/xx` for a symbolic link between the two calls would get the link created
in the target. That process needs write access to `blocks/` (mode `0700`, the relay's user), so it can
already write anything. The same applies to `read` (`O_NOFOLLOW` covers only the final component) and
to existing directories whose mode or owner is not checked. A robust fix (`linkat`/`openat` on an
`O_DIRECTORY | O_NOFOLLOW` descriptor) needs `rustix` or `unsafe`, which is not worth it now.

### I-5. Missing-shard path: correct accounting, with two edge cases

`blocks.rs:284-287`, `store.rs:537-563, 572-586`. On a missing or wrong-kind shard, `settle` goes to
the create path. The reservation is taken and then released (`NotLinked`). The temporary file is
removed. The response is `500` with `op=write`, and the directory is not recreated.
`shard_removed_at_run_time` discriminates this: the `op=write` counter rises, `used_bytes` is
unchanged, and `tmp/` is empty. Two edge cases:
- If the quota is also full, `reserve` fails first, and the `PUT` gets `507 quota` instead of `500`.
  This is harmless and arguably right.
- Each `PUT` into a missing shard still writes and `fsync`s a temporary file of up to 64 KiB before it
  fails. This is bounded by `put_max_in_flight`, and only happens on an already broken store.

`is_shard_error` keys on `ErrorKind::NotADirectory`. An `ENOTDIR` from opening the final name (only
possible in a race with a local writer) is classified the same way, which is the conservative outcome.

### I-6. Stores written by 1b are not migrated

The scan skips subdirectories inside a shard. Files in a 1b layout (`blocks/ef/cd/<id>.bin`) become
invisible and uncounted, and their index entries become phantoms (`/query` lists them, `GET` gets
`404`). No relay is deployed. Delete development `data_dir`s from 1b before running this build.

### I-7. Quota changes (ADR 0025): checked

`TREE_CHARGE = 259 × 4,096`. `cost = round_up(len, 4,096) + 128` is used the same way for
reservations, the walk, quarantined files and purges, so a move to quarantine leaves the sum unchanged.
`used` starts at `T` in `open` and is reset to `T + quarantine` in `reconcile`. `release` saturates.
`max_store_bytes ≥ 4 MiB` leaves room after `T` and the 64 KiB index growth floor. `Store::open` checks
or creates the three top directories, `fsync`s `data_dir`, then does the same for the 256 shards and
`fsync`s `blocks/`. A file or a symbolic link at a shard name stops the start-up and is never followed
(test `wrong_kind_of_shard_stops_start_up`). The write path no longer creates directories, which
closes I-7 of the 1b review: a client can no longer make the relay create uncounted directories.

### I-8. Minor

- Stale `HOOK(1c)` comments remain (`blocks.rs:86`, `lib.rs:131`, `error.rs:97`, `metrics.rs`,
  `store.rs:445`, `server.rs:448`). They should read `1c-b` where the work moved.
- `cargo` warns about an unused workspace dependency, `thiserror`. It is not in this diff; remove it
  from `[workspace.dependencies]` if nothing uses it, which means one less entry to audit.
- `index_readers_are_bounded` covers the case of a full queue (`index_max_queue = 0`), but not a queue
  wait that expires, nor a cancelled waiter. `Class` is shared with the block classes, which 1b
  tested, so this is low priority.

## Not checked

- Behaviour on Linux file systems (ext4, XFS): `ENOTDIR` and `EEXIST` semantics, `fsync` of
  directories, the real directory growth behind `E = 128`. The tests ran on macOS (APFS) only.
- Load or soak testing of `/query` under concurrent `PUT` and `GET /block`, including the latency
  coupling of L-2. Peak memory was not measured.
- Fuzzing of `parse_params` and `decode_cursor`. They were reviewed by reading, and their unit tests
  cover the rules; there is no fuzz target for them.
- hyper's exact URI and header length limits for the configured listener (relied on for I-2).
- Whether redb's crash recovery after a `SIGKILL` during `renew_epoch`'s commit itself leaves either
  epoch, never a torn value. This relies on redb's commit atomicity, which was not verified beyond its
  documentation.
