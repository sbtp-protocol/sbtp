# Test vectors

Layer 0 interoperability vectors, to be produced in Phase 1 by the implementer, from ADRs 0001 (endianness),
0002 (domain separation), 0003 (strict verification, block identity), 0004 (rejection rules) and 0014
(parent limit of 8, maximum block size of 65,909 bytes).
Every implementation (native Rust, WASM, future third-party implementation) must pass them identically.

**Current set: `v1/`, 82 vectors. Not published yet.** The set was frozen on 2026-11-18 after the security
review `docs/security/2026-11-18-sbtp-core-m2.md`, then regenerated in place once for ADR 0014: four files
replaced (`valid_8_parents`, `valid_max_size`, `f2_65910_bytes`, `f5_9_parents`), the 78 others
byte-identical. This is the last change to `v1/` before publication.

Layer 2 vectors (none exist yet): vectors for the grammar of `docs/spec/l2-grammar.md`, the `sbtp.*`
kinds and the sealed envelope will live in this repository, in a separate folder, generated by `sbtp-l2`
and the sealed envelope implementation. Vectors for application kinds belong to each application's
specification.

Graph access vectors (planned, ADR 0040, accepted; not generated yet, not frozen): `graph-v1/uri.json` (SBTP URI parsing) and
`graph-v1/view/` (block bytes to JSON block view, compared as parsed JSON values), generated by
`sbtp-graph`. The case list is in ADR 0040, "Test vectors". They are frozen only after the ADR is
accepted and the security review has checked each negative case.

Publication is the first time the set leaves this repository: a push to a remote, a release, or a copy
handed to another implementation. A published set never changes; a format change then creates `v2/`.

- Generator: `crates/sbtp-core/examples/gen_vectors.rs`. It computes every expected outcome without calling
  `sbtp-core` (own `block_id` recomputation, own evaluation of V1 to V6).
  - `cargo run -p sbtp-core --features vector-gen --example gen_vectors -- --check` verifies the set and
    writes nothing.
  - Without flag, it writes only missing files and never overwrites an existing one.
  - `--fuzz-seeds [DIR]` writes fuzz seeds (default `fuzz/corpus/decode_block/`, see `fuzz/README.md`).
- Loader test: `crates/sbtp-core/tests/vectors.rs`, run by `cargo test --workspace`.
- Keys: public seeds `[0x01; 32]` and `[0x02; 32]` (`crates/sbtp-core/tests/common/mod.rs`), test only.
- Naming of the C2/C3 point cases:
  - `*_only_*` vectors fail **exactly one** criterion (V2 or V5) and satisfy V6. They are the ones that
    discriminate a verifier missing that criterion. The test `isolating_vectors_discriminate_v2_and_v5` proves
    it: a non-strict verifier accepts every one of them.
  - `*_and_v6` vectors also fail V6. They pin the error name and the C2-before-C3 order, but cannot detect a
    missing V2 or V5 on their own.
  - Every negative vector's description lists all the criteria it fails.

## Format

One JSON file per case:

```json
{
  "name": "…",
  "description": "…",
  "block_hex": "…",
  "params": { "difficulty": 0, "requested_block_id": null },
  "expect": { "valid": true, "block_id": "…", "signed_message_hex": "…", "error": null }
}
```

- `params.difficulty`: difficulty `d` used for check C1. Default `0`.
- `params.requested_block_id`: identifier the block was requested by (check R1). `null` when the block is
  validated as a `PUT`.
- `expect.block_id` and `expect.signed_message_hex` (the 49 bytes `SIG_PREFIX ‖ block_id`) are given whenever
  the block is well-formed (checks F1 to F9 pass), valid or not. They let an implementation locate a
  divergence in the hash or in the signed message.
- `expect.error`: the error name of spec §2.2 (`TooShort`, `TooLong`, `BadMagic`, `UnsupportedVersion`,
  `TooManyParents`, `Truncated`, `TrailingBytes`, `DuplicateParent`, `BlockIdMismatch`, `InsufficientPow`,
  `InvalidPublicKey`, `InvalidSignature`), or `null` for a valid block. The first failing check, in the
  order F1 to F9, R1, C1 to C3, determines the error.

## Rules

- The keys used are **derived from a documented public seed** (for example 32 bytes of `0x01`). They are
  test keys, never reused elsewhere; no real key in this folder.
- Signatures of valid vectors are deterministic (RFC 8032 §5.1.6), so that the vectors can be regenerated.
- An invalid vector fails exactly one check, unless its description says otherwise.
- A published vector never changes. If an ADR changes the format after publication, a new set is created
  (`v2/`). `v1/` was not published when ADR 0014 changed the parent limit, so it was regenerated in place
  (ADR 0014, "Test vector set").

## Required cases

### Valid blocks

| Case | Purpose |
|---|---|
| 0 parents, empty payload (118 bytes) | Minimum size. |
| 1 parent | Offsets with `N = 1`. |
| 8 parents | Parent limit (F5 boundary, ADR 0014). |
| 8 parents, payload of 65,535 bytes (65,909 bytes) | Maximum size (F2 boundary). |
| Empty payload with parents; maximum payload with 0 parents | `P = 0` and `P = 65,535`. |
| A parent whose 32 bytes are zero | A parent hash is opaque (ADR 0004). |
| Parents in non-sorted order | Order is significant and kept. |
| Timestamp `0` and timestamp `2^64 − 1` | No format rule on Timestamp. |
| Nonce with distinct bytes (for example `0x0102030405060708`) | Big-endian encoding (ADR 0001). |
| PoW exactly at the threshold (`d` leading zero bits, `difficulty = d`) | C1 boundary. |
| Mixed-order public key with a valid signature | Fixes the `mod L` reduction of `k` in V6 (ADR 0003). Accepted. |
| Valid block with `requested_block_id` equal to its `block_id` | R1 passes. |

### Format errors (F1 to F9)

| Case | Expected error |
|---|---|
| Empty buffer | `TooShort` |
| 117 bytes | `TooShort` |
| 65,910 bytes (the maximum-size block plus one byte) | `TooLong` |
| Wrong first magic byte; wrong second magic byte | `BadMagic` |
| Version `0x00`; version `0x02` | `UnsupportedVersion` |
| 9 parents | `TooManyParents` |
| 255 parents | `TooManyParents` |
| Truncation in the middle of the parents (F6) | `Truncated` |
| Truncation in the middle of the payload (F7) | `Truncated` |
| Last signature byte missing (F7) | `Truncated` |
| One extra byte after the signature | `TrailingBytes` |
| Two identical adjacent parents | `DuplicateParent` |
| Two identical non-adjacent parents | `DuplicateParent` |

### Receipt (R1)

| Case | Expected error |
|---|---|
| Valid block, `requested_block_id` set to another identifier | `BlockIdMismatch` |

### Proof of work (C1)

| Case | Expected error |
|---|---|
| `d − 1` leading zero bits with `difficulty = d` | `InsufficientPow` |

### Public key (C2, criteria V1 and V2)

| Case | Expected error |
|---|---|
| `y` not on the curve (V1) | `InvalidPublicKey` |
| Non-canonical encoding, `y ≥ 2^255 − 19`, point not of small order (V1) | `InvalidPublicKey` |
| Non-canonical encoding of a small-order point (V1, before V2) | `InvalidPublicKey` |
| `x = 0` with the sign bit set to 1 (V1) | `InvalidPublicKey` |
| Canonical small-order key (V2), one case per small-order point | `InvalidPublicKey` |

### Signature (C3, criteria V3 to V6)

| Case | Expected error |
|---|---|
| **`S + L`**: valid signature whose `S` is replaced by `S + L` (V3). Mandatory; replayed by the relay at start-up (ADR 0003, rule 16). | `InvalidSignature` |
| `R` does not decode to a point (V4) | `InvalidSignature` |
| `R` of small order (V5) | `InvalidSignature` |
| Non-canonical encoding of `R` (V6) | `InvalidSignature` |
| Signature valid only under the cofactored equation (V6) | `InvalidSignature` |
| One bit flipped in `R`; one bit flipped in `S` | `InvalidSignature` |
| One bit flipped in the payload, signature unchanged | `InvalidSignature` |
| Signature over the raw `block_id`, without `SIG_PREFIX` (ADR 0002) | `InvalidSignature` |
| Signature valid for a `block_id` computed with plain BLAKE3 instead of `derive_key` (ADR 0002) | `InvalidSignature` |
| Valid signature by another key than PubKey | `InvalidSignature` |

The C2SP CCTV `ed25519vectors` classify Ed25519 edge cases, but they are over free messages: the cases above
must be built as SBTP blocks.
